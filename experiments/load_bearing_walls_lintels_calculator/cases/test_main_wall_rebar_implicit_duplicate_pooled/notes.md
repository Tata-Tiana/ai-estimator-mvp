# Две строки без явного code, одинаковые floor/component/steel_class/diameter_mm — теперь пулятся

До 2026-08-09 это был негативный тест: две строки `main_wall_rebar_items` с одинаковыми
`floor`/`component`/`steel_class`/`diameter_mm` и без явного `code` считались коллизией
(риск, найденный 2026-07-26 при разборе "подоконного армирования" — вторая строка тихо
перезаписывала контрольные суммы первой), и калькулятор должен был падать с `ValueError`.

С 2026-08-09 коллизия по этому ключу — больше не ошибка, а сигнал "эти строки нужно объединить в
одну закупку арматуры". Сравнение с реальными сметами ТРЦ/АРК/ЮСВ показало, что реальная арматура
одного диаметра/класса стали в пределах этажа/компонента у Елены всегда закупается ОДНИМ пулом
прутков, а не по отдельности на каждую строку спецификации (см.
`reports/trc_vs_original_comparison/04_load_bearing_walls_lintels.md`). `rebar_from_spec_length_items_pooled()`
группирует строки именно по этому ключу и округляет прутки один раз на объединённую сумму — тот
самый прежний риск "тихой перезаписи" больше не может произойти в принципе, поскольку обе строки
явно суммируются перед округлением (`pooled_item_codes` в `calculation_blocks` хранит происхождение
каждой объединённой строки для трассировки).

Числа: 1070 + 4.4 = 1074.4м базовой длины → ×1.05 = 1128.12 → /11.7 = 96.42 → 97 прутков × 11.7 =
1134.9м, одна смётная строка `load_bearing_walls_floor_1_rebar_a500_d10`. Пара к
`test_main_wall_rebar_subwindow_unique_code` (тот же сценарий, но одна из строк с явным `code`) —
доказывает, что наличие/отсутствие явного `code` больше не влияет на объединение.
