# Подоконное армирование (уникальный code) — теперь пулится, а не сохраняется отдельной строкой

Раньше (до 2026-08-09) этот кейс проверял, что явный уникальный `code` на "подоконной" строке
спасает её от коллизии с основной строкой (обе floor=1/load_bearing_walls/A500/Ø10) — обе строки
жили в смете раздельно, каждая округлялась до прутка независимо (1070→1134,9м, 4,4→11,7м, сумма
1146,6м).

С 2026-08-09 это устарело: сравнение с реальными сметами ТРЦ/АРК/ЮСВ (см.
`reports/trc_vs_original_comparison/04_load_bearing_walls_lintels.md`) показало, что реальная
арматура одного диаметра/класса стали в пределах этажа/компонента у Елены ВСЕГДА закупается ОДНИМ
пулом прутков, не по отдельности на каждую строку спецификации — раздельное округление каждый раз
даёт лишний "хвостовой" пруток и не сходится с её реальными числами. Теперь `code` на отдельной
строке — это просто метка для трассировки внутри `pooled_item_codes`, а не способ удержать строки
раздельными; обе строки (1070 + 4,4 = 1074,4 м базовой длины) сливаются в ОДНУ смётную строку с
единым округлением прутков: 1074,4×1,05=1128,12 → 1128,12/11,7=96,42 → 97 прутков × 11,7 = 1134,9м
(меньше, чем 1146,6м при раздельном округлении — экономия ровно на одном "хвостовом" прутке, как и
предсказывает находка). Пара к `test_main_wall_rebar_duplicate_line_code_rejected`, которая теперь
проверяет то же самое (несколько строк с одинаковыми floor/component/steel_class/diameter_mm без
явного `code`) — коллизия больше не ошибка, а штатное объединение.
