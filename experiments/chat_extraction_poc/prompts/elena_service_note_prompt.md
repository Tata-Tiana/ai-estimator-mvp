# Промпт для второй служебной записки для Елены

Используй этот промпт после того, как уже получены:

1. `extraction_output.json` — результат извлечения из проекта;
2. техническая служебная записка или аудит JSON, если она есть;
3. при необходимости исходная записка из первого прогона.

PDF повторно загружать не обязательно. Если PDF загружен, не извлекай данные заново и не исправляй JSON по памяти. Твоя задача — переписать уже найденные сомнения человеческим языком.

---

Ты готовишь вторую служебную записку для сметчицы Елены.

Елена не должна знать внутреннее устройство JSON, калькуляторов и кода. Поэтому основная записка должна быть написана обычным профессиональным языком сметчика и проектировщика.

Цель записки:

- показать, какие данные из проекта можно принять;
- какие места требуют проверки;
- где проект даёт несколько вариантов или компоненты без общего итога;
- какие решения нужны от сметчицы или проектировщика перед расчётом;
- какие конструкции пока не входят в текущий сметный контур.

Записка не должна считать смету и не должна выбирать спорные значения за Елену.

---

## Что обязательно использовать

Перед написанием записки внимательно пройди по:

- всем строкам со статусом `needs_review`;
- всем отсутствующим важным параметрам;
- всем важным `notes`;
- всем строкам, которые сохранены только как исходные строки таблиц, но могут влиять на смету;
- всем предупреждениям по PDF, штампам, конфликтам листов, плохой читаемости или неоднозначным таблицам.

Если есть техническая записка-аудит, используй её как полный список тем, но перепиши человеческим языком.

Не сокращай записку так, чтобы потерять смысл. Лучше объединять одинаковые сомнения в один понятный пункт, чем выбрасывать их.

---

## Как писать

Пиши по разделам сметы, в обычном порядке:

1. Земляные работы.
2. Фундаментная плита.
3. Гидроизоляция и утепление бортов плит.
4. Несущие стены и перемычки.
5. Плита перекрытия 1-го этажа.
6. Плита перекрытия 2-го этажа.
7. Плоская кровля.
8. Вентиляционные каналы.
9. Конструкции вне текущих разделов, если они есть.

Внутри каждого раздела используй формат:

```text
<Номер>. <Короткое название проблемы>

Где в проекте:
<PDF, страница, название листа или таблицы, если известно>

Что видно в проекте:
<простое описание строк и чисел из проекта>

Почему это требует проверки:
<человеческое объяснение риска>

Что нужно решить:
<конкретное действие для Елены или проектировщика>
```

Если в проекте есть несколько компонентов без общего итога, пиши так:

```text
В проекте есть несколько отдельных строк/зон/марок, но нет одной готовой итоговой строки.
Автоматически складывать их можно только после подтверждения, что это один и тот же вид работ и один расчётный контур.
```

Если есть конфликт чисел, пиши так:

```text
В разных местах проекта указаны разные значения. Нельзя молча выбрать одно из них для расчёта.
Нужно подтвердить, какое значение считать расчётным.
```

Если значение найдено, но оно используется для двух разных сметных сущностей, пиши так:

```text
В проекте дана одна площадь/длина/объём. В смете это может использоваться отдельно для материала и отдельно для работы.
Нужно подтвердить, что одно проектное значение действительно подходит для обеих строк сметы.
```

Если значение есть только в компонентах, но итог нужен калькулятору, пиши так:

```text
Калькулятору для расчёта нужен общий итог, но в проекте даны только компоненты.
Нужно либо разрешить автосуммирование этих компонентов, либо оставить значение на ручную проверку.
```

Если в проекте есть конструкция вне текущего сметного контура, пиши так:

```text
В проекте есть конструкция, для которой сейчас нет отдельного места в восьми целевых разделах.
Чтобы не задвоить и не потерять объёмы, нужно отдельно решить, где она должна учитываться.
```

---

## Чего нельзя делать

Не используй в основной части записки технические имена полей и коды, например:

- `target_code`;
- `sections[*].needs_review`;
- `raw_table_rows`;
- `found`;
- `missing`;
- `candidates`;
- `confidence`;
- любые имена вроде `floor_slab_1_edge_eps_work_length`.

Если без технических кодов совсем нельзя, вынеси их в отдельное приложение в самом конце под заголовком:

```text
Техническое приложение для разработчика
```

Но основная записка для Елены должна быть понятна без этого приложения.

Не пиши длинные JSON-фрагменты.

Не пересказывай все найденные нормальные значения. Пиши только то, что влияет на проверку, ручной ввод, риск ошибки или решение по методике.

Не исправляй проект.

Не придумывай отсутствующие итоги.

Не превращай объём в площадь или длину без явного правила.

Не складывай зоны, марки, материалы или работы, если в исходном аудите написано, что это требует решения.

Не обвиняй проектировщика. Формулируй нейтрально:

- "нужно подтвердить";
- "требуется уточнение";
- "возможно, ошибка оформления";
- "нет готового итога";
- "есть риск двойного учёта".

---

## Стиль

Пиши спокойно, понятно и по делу.

Не делай текст слишком техническим.

Не используй жаргон разработчика.

Не используй эмодзи.

Не используй английские слова, если есть нормальный русский вариант.

Можно писать числа из конкретного проекта, потому что записка относится к конкретному прогону. Но не называй эти числа "правильными", если они спорные.

Если одно сомнение повторяется в нескольких строках, объедини его в один пункт и перечисли затронутые марки, зоны или листы.

---

## Итоговый формат

Верни только текст записки.

Структура:

```text
СЛУЖЕБНАЯ ЗАПИСКА ДЛЯ СМЕТЧИЦЫ

Проект:
<кратко, если известно>

Что проверялось:
<PDF/JSON/аудит, если известно>

Краткий итог:
- <самые важные решения, 5-10 пунктов максимум>

1. <Раздел сметы>

1.1. <Проблема>
...

2. <Следующий раздел>
...

Итоговый список решений:
1. <конкретное решение>
2. <конкретное решение>
...
```

Если явных сомнений нет, напиши:

```text
СЛУЖЕБНАЯ ЗАПИСКА ДЛЯ СМЕТЧИЦЫ

Явных нестыковок, влияющих на расчёт сметы, по переданному JSON и аудиту не выявлено.
```
