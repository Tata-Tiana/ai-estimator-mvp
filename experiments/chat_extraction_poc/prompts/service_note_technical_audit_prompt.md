ПРОВЕРКА И ПОЛНАЯ ПЕРЕГЕНЕРАЦИЯ СЛУЖЕБНОЙ ЗАПИСКИ

У тебя есть:

1. исходные PDF-файлы проекта;
2. исходный промпт извлечения и его требования;
3. схема выходного JSON;
4. уже сформированный JSON с результатами извлечения;
5. ранее сформированная служебная записка.

Твоя задача — не редактировать старую записку поверхностно, а провести полный контрольный аудит JSON по исходным PDF и затем создать служебную записку заново.

Старая записка используется только как материал для сравнения. Не доверяй ей и не считай, что перечисленные в ней замечания уже покрывают требования.

ОСНОВНАЯ ЦЕЛЬ

Новая служебная записка должна исчерпывающе объяснять сметчику:

- какие данные требуют ручной проверки;
- какие поля не заполнены;
- почему каждое поле не заполнено;
- какие значения конфликтуют;
- какие данные представлены в PDF в другой структуре, чем ожидает JSON;
- где значение найдено только частично;
- где есть риск двойного учёта;
- где значение рассчитано, а не прямо указано в проекте;
- какие решения должен принять сметчик.

Записка не должна быть общим резюме проекта. Это контрольный документ по всем спорным, отсутствующим, неоднозначным и структурно несовместимым данным.

ЭТАП 1. ПОЛНЫЙ АУДИТ JSON

До написания записки последовательно проверь весь JSON, включая все разделы и все вложенные структуры.

Обязательно собери отдельные полные списки:

1. всех элементов с:
   - `needs_review: true`;
   - статусом `needs_review`;
   - аналогичным статусом ручной проверки;

2. всех элементов из:
   - `missing`;
   - списков незаполненных полей;
   - полей со значением `null`, если null означает отсутствие результата;

3. всех значимых замечаний из:
   - `found[*].notes`;
   - `raw_table_rows[*].notes`;
   - `candidates[*].notes`;
   - `extraction_warnings`;
   - `warnings`;
   - `validation`;
   - `conflicts`;
   - иных полей, содержащих предупреждения или пояснения;

4. всех случаев, когда:
   - scalar-поле не заполнено, но данные сохранены в repeated group;
   - найдено общее значение, но отсутствует разбивка по подполям;
   - найдено несколько значений для одного target;
   - единица PDF отличается от единицы целевого поля;
   - значение можно получить только расчётом;
   - конструкция изображена на чертеже, но итоговая величина отсутствует;
   - данные есть в таблице, но не могут быть однозначно сопоставлены с target;
   - одно значение может быть ошибочно учтено дважды;
   - проект содержит арифметическое несоответствие;
   - в штампах или названиях листов присутствуют реквизиты другого объекта.

Проверь не только значения со статусом `needs_review`, но и поля со статусом `found`, если в их `notes`, источниках или соседних строках есть конфликт, ограничение или неоднозначность.

ЭТАП 2. ПРОВЕРКА ПО ИСХОДНЫМ PDF

Для каждого спорного элемента повторно проверь соответствующие страницы PDF.

Не делай вывод только по ранее сформированному JSON.

Для каждого элемента установи:

- что буквально указано в PDF;
- где это указано: файл, страница, лист, таблица или фрагмент чертежа;
- является ли число готовым проектным итогом;
- является ли число промежуточной величиной;
- является ли число результатом твоего расчёта;
- есть ли другое противоречащее значение;
- относится ли значение ко всему разделу или только к отдельной зоне;
- можно ли безопасно записать его в целевое поле.

Не исправляй проектные значения молча.

Если в спецификации указан итог, а контрольное перемножение даёт другое число:

- проектный итог сохраняй как проектное значение;
- арифметическое расхождение выноси в записку;
- не заменяй проектный итог собственным расчётом.

ЭТАП 3. ОБЯЗАТЕЛЬНАЯ ПРОВЕРКА ПОКРЫТИЯ

Перед созданием записки выполни coverage-аудит.

Требования покрытия:

1. Каждый элемент с `needs_review: true` или статусом `needs_review` обязан присутствовать в новой записке.

2. Каждый `target_code` из `missing` обязан быть учтён:
   - отдельным пунктом;
   - либо в тематической группе, где перечислены все входящие `target_code`.

3. Несколько полей разрешено объединить в один пункт только тогда, когда:
   - у них одна причина;
   - сметчику требуется одно и то же решение;
   - в пункте явно перечислены все объединённые `target_code`.

4. Нельзя писать:
   - «остальные поля не найдены»;
   - «часть данных отсутствует»;
   - «есть и другие пропуски»;
   - иные обобщения без списка конкретных кодов.

5. Для каждого значимого warning или note должно быть принято одно из решений:
   - включить в записку;
   - признать техническим и не влияющим на смету;
   - признать дублирующим другое замечание.

Внутренне сформируй таблицу соответствия:

`JSON-элемент → пункт новой записки`

Не завершай работу, пока для каждого обязательного элемента не найден соответствующий пункт.

ЭТАП 4. ЧТО ДОЛЖНО БЫТЬ В КАЖДОМ ПУНКТЕ

Каждый пункт ручной проверки должен содержать:

1. понятное название проблемы;
2. раздел сметы или конструкцию;
3. все связанные `target_code`;
4. фактический статус в JSON;
5. значение и единицу, если значение найдено;
6. `confidence`, если он присутствует в JSON;
7. источник:
   - имя PDF;
   - номер страницы или листа;
   - название таблицы, спецификации или чертежа;
8. точное описание проблемы;
9. объяснение, почему модель не могла принять окончательное решение;
10. конкретное действие для сметчика.

Формулировка действия должна быть предметной, например:

- выбрать одно из двух проектных значений;
- подтвердить толщину материала;
- определить, к какой зоне относится строка;
- предоставить итоговую площадь;
- подтвердить возможность суммирования;
- разделить общее значение между двумя полями;
- не переносить одно общее значение одновременно в два target;
- подтвердить использование repeated group вместо scalar-поля.

Недостаточно написать только «требуется проверка».

ЭТАП 5. ОБЯЗАТЕЛЬНЫЕ ТИПЫ ЗАМЕЧАНИЙ

Отдельно проверь и обязательно отрази следующие ситуации.

А. Repeated group вместо scalar-полей

Если данные извлечены в повторяющуюся группу, а соответствующие scalar-поля остались в `missing`, напиши:

- где сохранены фактические данные;
- почему scalar-поля намеренно не заполнены;
- должен ли сметчик использовать repeated group;
- требуется ли агрегирование.

Не создавай впечатление, что данные полностью потеряны.

Б. Общее значение без разбивки

Если PDF даёт одно общее значение для нескольких типов, толщин, этажей или зон:

- укажи общее значение;
- перечисли незаполненные частные поля;
- предупреди о риске двойного учёта;
- запрети автоматически копировать общее значение в каждое частное поле.

В. Конструкция есть, итога нет

Если на чертеже показаны конструкция, материал, шаг, толщина или схема армирования, но нет итоговой длины, площади, объёма или количества:

- не рассчитывай итог без разрешения;
- перечисли соответствующие `target_code`;
- сообщи, какие исходные данные есть;
- сообщи, какого готового итога не хватает.

Г. Конфликт значений

Для каждого конфликта укажи:

- оба или все найденные значения;
- страницы и источники;
- возможное различие охвата;
- какое значение записано в JSON;
- что должен выбрать или подтвердить сметчик.

Д. Различие единиц

Если PDF даёт м³, а target ожидает м², либо есть другое различие:

- не конвертируй без достаточных исходных данных;
- укажи, какой размер или толщина нужны для пересчёта;
- объясни, почему поле осталось незаполненным или отправлено на проверку.

Е. Арифметический контроль

Когда в PDF указаны все множители, выполни короткую контрольную проверку.

Например:

`длина × ширина × глубина = контрольный объём`

В записке разделяй:

- проектное значение;
- контрольный расчёт модели;
- величину расхождения.

Контрольный расчёт не должен молча заменять проектный итог.

Ж. Чужие реквизиты в штампах

Титульный лист и основное содержание комплекта считай приоритетными.

Если на отдельных листах остались реквизиты другого проекта, формулируй нейтрально:

«В штампе листа сохранились реквизиты другого объекта. Это похоже на ошибку оформления или копирования штампа. Данные извлекались по содержанию текущего комплекта».

Не утверждай без доказательств, что в PDF смешаны разные проекты.

ЭТАП 6. ПРОВЕРКА КАЧЕСТВА JSON

Во время повторной проверки оцени не только записку, но и сам JSON.

Если обнаружено, что:

- `needs_review` не установлен там, где он нужен;
- поле ошибочно находится в `missing`;
- значение записано не в тот target;
- потеряна строка спецификации;
- неверно объединены разные конструкции;
- в JSON есть необоснованный расчёт;
- повторяющаяся группа неполна;
- значение продублировано;
- неверно указаны страница, единица или источник,

создай в записке отдельный раздел:

`Обнаруженные ошибки или возможные ошибки JSON`.

Не исправляй JSON молча, если задание прямо не требует пересоздать и JSON. Чётко перечисли необходимые исправления.

ЭТАП 7. СТРУКТУРА НОВОЙ ЗАПИСКИ

Создай записку заново в следующей структуре:

1. Назначение записки.
2. Краткий итог проверки.
3. Критические конфликты, влияющие на стоимость.
4. Все элементы `needs_review`.
5. Все незаполненные поля и причины:
   - данные отсутствуют в PDF;
   - есть частичные данные;
   - данные находятся в repeated group;
   - отсутствует разбивка;
   - невозможно привести единицы;
   - итог требует расчёта;
   - раздел не входит в поддерживаемую смету.
6. Арифметические и логические контрольные проверки.
7. Обнаруженные ошибки или возможные ошибки JSON.
8. Замечания по оформлению проектной документации.
9. Итоговый список решений, которые должен принять сметчик.
10. Контроль покрытия.

В разделе «Контроль покрытия» обязательно укажи числа:

- всего элементов `needs_review` в JSON;
- сколько из них отражено в записке;
- всего `target_code` в `missing`;
- сколько из них объяснено;
- сколько значимых warnings/notes найдено;
- сколько включено в записку;
- сколько признано техническими или дублирующими.

Корректный итог должен выглядеть примерно так:

- `needs_review`: 29 из 29 отражено;
- `missing`: 34 из 34 объяснено;
- значимые warnings/notes: 12 из 12 обработано.

Числа возьми из фактического JSON. Не используй числа из примера.

ЭТАП 8. ФИНАЛЬНАЯ САМОПРОВЕРКА

Перед сохранением файла проверь:

- нет ли `needs_review`, отсутствующих в записке;
- учтён ли каждый `target_code` из `missing`;
- перечислены ли коды всех объединённых полей;
- указаны ли источники;
- указаны ли найденные значения;
- указаны ли единицы;
- указан ли `confidence`, когда он есть;
- сформулировано ли конкретное решение для сметчика;
- не выданы ли расчётные значения за проектные;
- не потеряны ли данные, сохранённые в repeated groups;
- нет ли риска двойного учёта;
- не повторяются ли одинаковые замечания без необходимости;
- соответствует ли итоговая статистика фактическому содержанию записки.

Если хотя бы один обязательный элемент не покрыт, записка считается незавершённой. Продолжай проверку и исправление до полного покрытия.

РЕЗУЛЬТАТ

Создай новую служебную записку целиком, а не дополнение к старой.

Сохрани её отдельным текстовым файлом.

Если в ходе аудита выявлены ошибки JSON, но пересоздание JSON не запрошено, сам JSON не изменяй — перечисли необходимые исправления в записке.

В ответе в чат не публикуй содержимое записки. Пришли только ссылку на готовый TXT-файл.
