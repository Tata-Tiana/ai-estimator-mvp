# Промпт для извлечения данных сметы из PDF (вставить в Claude-чат)

Загрузи вместе с этим промптом:
1. PDF проекта (все страницы/чертежи, которые у тебя есть).
2. `calculator_targets_compact.json` — что именно нужно найти, по 8 разделам.
3. `target_aliases_ru.yaml` — русские названия строк/алиасы для сопоставления
   PDF-таблиц с техническими `target_code`.
4. `section_guide.json` — на каких листах это обычно бывает (названия листов, не номера страниц).
5. `unit_normalization_guide.json` — таблица единиц измерения.
6. `claude_extraction_output_schema.json` — форма ответа.

---

Ты извлекаешь данные из строительной проектной документации (PDF) для 8
разделов сметы коробки дома: земляные работы, фундаментная плита,
гидроизоляция, несущие стены и перемычки, плита перекрытия 1-го этажа,
плита перекрытия 2-го этажа, плоская кровля, вентканалы Schiedel.

Список того, что искать по каждому разделу — в `calculator_targets_compact.json`
(поля `targets` и `extract_groups`). Ориентируйся на него, но если увидишь
в PDF явно относящиеся к разделу данные, которых нет в списке — тоже извлеки
их, отдельно пометив в `notes`, что это вне списка целей.

Русские формулировки строк в PDF сопоставляй через `target_aliases_ru.yaml`.
Это обязательный словарь для маппинга. Нельзя выбирать `target_code` только
по английскому/техническому имени вроде `main_formwork_area` или
`eps100_edge_volume`: сначала найди строку/ячейку в PDF, затем сопоставь её
по русским алиасам, `section_code`, `expected_unit`, `required_context` и
`negative_context`. Если один и тот же технический код встречается в разных
разделах, различай его по `section_code`.

## Жёсткие правила

1. **Не считай смету.** Твоя задача — извлечение, не расчёт.
2. **Не придумывай значения.** Если числа нет явно на странице — не пиши его.
3. **Не дописывай строки, ГОСТы, названия материалов или числа, которых нет в PDF.**
   Если не уверена в точном написании — процитируй как есть в `raw_text`,
   не "причёсывай" и не восстанавливай "по смыслу".
4. Если значение не видно явно — верни `null` и добавь код параметра в
   `missing` для этого раздела.
5. Нельзя использовать "логически похоже на нужное" без `raw_text`,
   подтверждающего именно это значение на этой странице.
6. **Для каждого ненулевого значения обязательны источники**:
   - `source_pdf` — имя файла PDF, если их несколько;
   - `page_number` — номер страницы по счётчику PDF (не номер листа с чертежа);
   - `page_title` — заголовок листа, если виден;
   - `raw_text` — дословная цитата или описание ячейки таблицы, откуда взято число;
   - `confidence` — твоя оценка уверенности от 0 до 1;
   - `needs_review` — true, если ты не полностью уверена, значение неоднозначно,
     таблица нечитаема, или ты в чём-то сомневаешься.
7. Если таблица двумерная (строки × столбцы) — сохрани структуру таблицы,
   не превращай её в одно число. Это особенно важно для таблиц маршрутов
   коммуникаций/траншей и спецификаций арматуры/труб — используй `extract_groups`
   из `calculator_targets_compact.json`.
8. **Сначала извлекай таблицы как `raw_table_rows`, потом маппь значения.**
   Для каждой спецификации/ведомости, из которой ты берёшь хотя бы одно
   значение, добавь в раздел `raw_table_rows`: заголовок таблицы, строки,
   колонки как они видны в PDF, исходный текст ячеек, единицы и источник.
   Только после этого создавай элементы `found`, сопоставляя строки с
   `target_aliases_ru.yaml`.
9. Если таблица нечитаема, размыта, наложена на чертёж, или ты не уверена
   в разбиении по строкам — верни `needs_review: true`, а не угадывай
   структуру. Лучше честно сказать "не уверена", чем красиво оформить
   неверные данные.
10. Если есть сомнение между двумя возможными значениями для одного
   параметра (например, непонятно, какое число к какому уровню/каналу
   относится) — верни оба как `candidates`, не выбирай молча одно.
11. Если поле по смыслу — расчётное (например, "итоговая длина
    коммуникаций"), не выдавай его как "найденное" значение параметра —
    вместо этого извлеки исходные данные, из которых оно должно
    считаться (см. правило про `communications_length_m` ниже).

## Порядок работы с таблицами

1. Найди лист/страницу и заголовок таблицы.
2. Выпиши таблицу в `raw_table_rows` без сокращений: `table_title`,
   `columns`, `rows`, `source_pdf`, `page_number`, `page_title`.
3. Для каждой строки проверь `target_aliases_ru.yaml`:
   - совпадает ли `section_code`;
   - есть ли русский алиас или близкий русский смысл;
   - совпадает ли единица с `expected_unit`;
   - есть ли `required_context`;
   - нет ли слов из `negative_context`.
4. Только после этих проверок добавляй `found`.

Особенно важно не смешивать:
- ЭППС 100 мм торец плиты (`m3`) и площадь опалубки торца плиты (`m2`);
- ЭППС 100 мм низ/под плитой (`m3`) и площадь опалубки под плитой (`m2`);
- бетон плиты, бетон балок и строку "Итого" по таблице Ж/Б балок;
- площадь опалубки плиты перекрытия 2-го этажа и площадь кровли другого уровня.

## Правило про арматуру

В проектных спецификациях арматура обычно дана в `м/п`, а рядом может
быть колонка `Масса ед. шт.` или похожая колонка с массой одного
погонного метра (`кг/м`).

Не вычисляй общий вес арматуры в кг.

Если строка арматуры содержит:
- `Кол-во` = длина в `м/п`;
- `Масса ед. шт.` = масса одного погонного метра;
- `Примечание` или единица строки = `м/п`;

то в JSON запиши:
- `length_m`;
- `mass_per_m_kg`, если колонка массы 1 м есть;
- `weight_kg: null`;
- `unit: "м/п"`;
- `normalized_unit: "linear_m"`.

Если в PDF явно дана строка в `кг`, только тогда можно записать:
- `weight_kg`;
- `unit: "кг"`;
- `normalized_unit: "kg"`.

Любой общий вес, полученный умножением `length_m * mass_per_m_kg`, не
является найденным значением из PDF. Такой вес должен считать код после
extraction.

Особенно это относится к:
- `foundation_rebar_items`;
- `floor_slab_1_rebar_items`;
- `floor_slab_2_rebar_items`;
- `lintel_rebar_items`;
- `masonry_rebar_a500_d10_weight`.

## Отдельное важное правило про коммуникации

**`communications_length_m` НЕ извлекай как одно число из текста.**
Даже если на чертеже написано похожее число — не бери его напрямую.
Вместо этого извлеки `communications_pipe_items` (позиции труб/фитингов:
название, диаметр, длина одной штуки/погонные метры, количество) построчно.
Суммарная длина коммуникаций считается кодом отдельно, не тобой.

То же самое для `trench_volume_m3`: если в таблице траншей есть готовая
строка "Итого" с суммой — извлеки её отдельно как
`trench_volume_total` с `raw_text`, но также обязательно извлеки
`trench_routes` по каждому маршруту отдельно — код должен иметь возможность
пересчитать сумму и сверить с твоим "Итого".

## Единицы измерения

Пиши единицу как она написана в PDF (`unit`), а также нормализованную
(`normalized_unit`) по таблице из `unit_normalization_guide.json`. Если
единицы нет в таблице — оставь `normalized_unit: null` и укажи как есть
в `unit`.

## Формат ответа

Верни **только JSON**, без пояснений вне JSON и без markdown-код-блоков
вокруг него, строго по схеме из `claude_extraction_output_schema.json`.

Если PDF большой и не помещается целиком в один ответ — можно обработать
по разделам (по одному сообщению на раздел из списка выше), но в конце
дай единый JSON-объект, объединяющий все разделы.
