# Промпт для извлечения данных сметы из PDF (вставить в Claude-чат)

Загрузи вместе с этим промптом:
1. PDF проекта (все страницы/чертежи, которые у тебя есть).
2. `calculator_targets_compact.json` — что именно нужно найти, по 8 разделам.
3. `target_aliases_ru.yaml` — русские названия строк/алиасы для сопоставления
   PDF-таблиц с техническими `target_code`.
4. `section_guide.json` — на каких листах это обычно бывает (названия листов, не номера страниц).
5. `unit_normalization_guide.json` — таблица единиц измерения.
6. `claude_extraction_output_schema.json` — форма ответа.

---

Ты извлекаешь данные из строительной проектной документации PDF для 8 разделов сметы коробки дома:

1. земляные работы;
2. фундаментная плита;
3. гидроизоляция;
4. несущие стены и перемычки;
5. плита перекрытия 1-го этажа;
6. плита перекрытия 2-го этажа;
7. плоская кровля;
8. вентканалы Schiedel.

Твоя основная задача — извлечь данные из PDF и подготовить корректный JSON для Telegram-бота, который потом создаст Google-таблицу проверки для сметчицы.

Список того, что искать по каждому разделу, находится в `calculator_targets_compact.json`:
- `targets`;
- `extract_groups`.

Ориентируйся на этот список, но если увидишь в PDF явно относящиеся к разделу данные, которых нет в списке, тоже извлеки их и отдельно пометь в `notes`, что это вне списка целей.

Русские формулировки строк в PDF сопоставляй через `target_aliases_ru.yaml`.

Это обязательный словарь для маппинга.

Нельзя выбирать `target_code` только по английскому или техническому имени вроде:
- `main_formwork_area`;
- `eps100_edge_volume`;
- `main_wall_rebar_items`.

Сначала найди строку или ячейку в PDF, затем сопоставь её по:
- русским алиасам;
- `section_code`;
- `expected_unit`;
- `required_context`;
- `negative_context`.

Если один и тот же технический код встречается в разных разделах, различай его по `section_code`.

Важно: `target_code` — это фиксированный технический идентификатор, придуманный не по тексту PDF, а
под конкретное поле в коде калькулятора. Он часто не будет похож на формулировку в PDF ни по-русски,
ни по смыслу названия (например, код `membrane_area_m2` для строки PDF "Профилированная мембрана
PLANTER" — это нормально, не ошибка и не повод придумать свой код). Никогда не изобретай новый
`target_code` и не меняй регистр/написание существующего, даже если он кажется неточным или
неудобным — используй ровно то значение `code`, которое дано в `calculator_targets_compact.json`.
Формулировку из PDF записывай в `raw_text` / `name` строки, а не в сам `target_code`.

## Жёсткие правила

1. Не считай смету. Твоя задача — извлечение, не расчёт.

2. Не придумывай значения. Если числа нет явно на странице — не пиши его.

3. Не дописывай строки, ГОСТы, названия материалов или числа, которых нет в PDF.

4. Если не уверена в точном написании — процитируй как есть в `raw_text`, не причёсывай и не восстанавливай по смыслу.

5. Если значение не видно явно — верни `null` и добавь код параметра в `missing` для этого раздела.

6. Нельзя использовать "логически похоже на нужное" без `raw_text`, подтверждающего именно это значение на этой странице.

7. Для каждого ненулевого значения обязательны источники:
   - `source_pdf` — имя файла PDF, если их несколько;
   - `page_number` — номер страницы по счётчику PDF, не номер листа с чертежа;
   - `page_title` — заголовок листа, если виден;
   - `raw_text` — дословная цитата или описание ячейки таблицы, откуда взято число;
   - `confidence` — твоя оценка уверенности от 0 до 1;
   - `needs_review` — true, если значение неоднозначно, таблица нечитаема, есть сомнение или нужна проверка сметчицы.

8. Если таблица двумерная, строки × столбцы, сохрани структуру таблицы, не превращай её в одно число.

Это особенно важно для:
- таблиц маршрутов траншей;
- таблиц коммуникаций;
- спецификаций арматуры;
- спецификаций труб;
- таблиц Ж/Б балок.

Используй `extract_groups` из `calculator_targets_compact.json`.

9. Сначала извлекай таблицы как `raw_table_rows`, потом маппь значения в `found`.

Для каждой спецификации или ведомости, из которой ты берёшь хотя бы одно значение, добавь в соответствующий раздел `raw_table_rows`:
- заголовок таблицы;
- строки;
- колонки как они видны в PDF;
- исходный текст ячеек;
- единицы;
- источник.

Только после этого создавай элементы `found`, сопоставляя строки с `target_aliases_ru.yaml`.

10. Если таблица нечитаема, размыта, наложена на чертёж, или ты не уверена в разбиении по строкам, верни `needs_review: true`, а не угадывай структуру.

Лучше честно сказать "не уверена", чем красиво оформить неверные данные.

11. Если есть сомнение между двумя возможными значениями для одного параметра, верни оба как `candidates`, не выбирай молча одно.

Например:
- непонятно, какое число к какому уровню относится;
- есть две похожие площади;
- одно значение может относиться к разным разделам.

12. Если поле по смыслу расчётное, не выдавай его как найденное значение параметра.

Вместо этого извлеки исходные данные, из которых оно должно считаться кодом.

13. Каждая строка `raw_table_rows` с непустым `mapped_target_codes` обязана появиться ровно в одном месте итогового результата: `found`, `needs_review` или `missing`.

Нельзя, чтобы строка была размечена как относящаяся к цели на этапе `raw_table_rows`, а потом бесследно пропала — не попала ни в `found`, ни в `needs_review`, ни в `missing`. Если сомневаешься в единице измерения, разбивке или значении строки — верни её с низкой `confidence` и `needs_review: true`, но не отбрасывай молча.

## Порядок работы с таблицами

1. Найди лист, страницу и заголовок таблицы.

2. Выпиши таблицу в `raw_table_rows` без сокращений:
   - `table_id`;
   - `table_title`;
   - `columns`;
   - `cells`;
   - `raw_text`;
   - `unit`;
   - `normalized_unit`;
   - `source_pdf`;
   - `page_number`;
   - `page_title`.

3. Для каждой строки проверь `target_aliases_ru.yaml`:
   - совпадает ли `section_code`;
   - есть ли русский алиас или близкий русский смысл;
   - совпадает ли единица с ожидаемой;
   - есть ли `required_context`;
   - нет ли слов из `negative_context`.

4. Только после этих проверок добавляй строку в `found`.

Особенно важно не смешивать:

- ЭППС 100 мм торец плиты в м3 и площадь опалубки торца плиты в м2;
- ЭППС 100 мм низ/под плитой в м3 и площадь опалубки под плитой в м2;
- бетон плиты, бетон балок и строку "Итого" по таблице Ж/Б балок;
- площадь опалубки плиты перекрытия 2-го этажа и площадь кровли другого уровня;
- периметр в м/п и площадь в м2;
- объём материала в м3 и площадь работ в м2.

### Правило про площадь гидроизоляции фундаментной плиты

Для раздела `waterproofing` production-калькулятору нужна площадь `waterproofing_area_m2` — площадь
гидроизоляции фундаментной плиты битумной мастикой.

По методике Елены, если в PDF нет отдельной строки "площадь гидроизоляции", эта площадь равна площади
опалубки бортов фундаментной плиты из раздела `foundation_slab`:

```text
waterproofing.waterproofing_area_m2 = foundation_slab.slab_side_formwork_area
```

Поэтому если ты нашла строку PDF "Площадь опалубки бортов фундаментной плиты" / "Опалубка бортов" /
похожую строку в м2 и сопоставила её с `foundation_slab.slab_side_formwork_area`, то также создай
`found` item для `waterproofing.waterproofing_area_m2` с тем же числом, тем же `source_pdf`,
`page_number`, `page_title` и `raw_text`.

Для `waterproofing_area_m2` в этом случае поставь:

- `needs_review: true`;
- `confidence` не выше confidence исходной строки опалубки;
- `notes`: "Площадь гидроизоляции принята равной площади опалубки бортов фундаментной плиты по методике Елены."

Это разрешённое дублирование одного PDF-значения между двумя разделами. Не считай новое число и не
ищи другую площадь, если явной отдельной строки гидроизоляции нет.

## Правило про арматуру

В проектных спецификациях арматура обычно дана в `м/п`, а рядом может быть колонка `Масса ед. шт.` или похожая колонка с массой одного погонного метра.

Не вычисляй общий вес арматуры в кг.

Если строка арматуры содержит:

- `Кол-во` = длина в `м/п`;
- `Масса ед. шт.` = масса одного погонного метра;
- `Примечание` или единица строки = `м/п`;

то запиши исходные данные (длину и массу 1 м), а не готовый вес — общий вес, полученный умножением
длины на массу 1 м, не является найденным значением из PDF, такой вес должен считать код после
extraction.

Если в PDF явно дана строка в `кг`, только тогда можно записать:

- `weight_kg`;
- `unit: "кг"`;
- `normalized_unit: "kg"`.

Названия полей для длины и массы 1 м зависят от конкретной группы (см. `group_value_shapes` в
схеме и `extract_groups[].fields` в `calculator_targets_compact.json` — это ground truth для полей,
не дублируй имена здесь, чтобы не разойтись с ними):

- `foundation_rebar_items` → `source_length_m`, `kg_per_meter`;
- `floor_slab_1_rebar_items` → `spec_length_m`, `kg_per_meter`, `floor: 1`, `component: "floor_slab_1"`;
- `floor_slab_2_rebar_items` → см. `group_value_shapes`;
- `main_wall_rebar_items` → `spec_length_m`, `kg_per_meter`, `component: "load_bearing_walls"`;
- `lintel_rebar_items` → `spec_length_m`, `kg_per_meter`, `component: "lintels"`.

Для раздела `load_bearing_walls_lintels` не используй старую сводную цель
`masonry_rebar_a500_d10_weight` в production extraction. Арматуру кладки несущих стен извлекай
строками в `main_wall_rebar_items`, арматуру перемычек — строками в `lintel_rebar_items`.
Марки/позиции перемычек (`Пм-1`, `Пм-2` и т.п.) — это `lintel_items`, не арматура.

Во всех случаях: `weight_kg: null`, `unit: "м/п"`, `normalized_unit: "linear_m"`, если строка дана в
метрах погонных.

Важно: если PDF даёт арматуру в м/п, извлекай исходные данные (длину в м/п и массу 1 м, если она
есть), а не готовый вес.

## Правило про коммуникации

`communications_length_m` — это итоговая длина коммуникаций для калькулятора земляных работ.

Извлекай `communications_length_m` только если в PDF явно есть готовая итоговая длина коммуникаций:
например строка "Итого", "общая длина", "суммарная длина" или отдельная ведомость с готовым итогом.

Если есть только позиции труб/фитингов, не суммируй их сама и не выдавай сумму как
`communications_length_m`. В этом случае оставь `communications_length_m` missing/needs_review и
извлеки `communications_pipe_items` построчно:

- `code` — стабильный код строки из видимого названия/ГОСТ/назначения;
- название;
- диаметр;
- длина одной штуки, если строка в штуках;
- количество штук;
- итоговая длина строки, только если она явно написана в PDF;
- включается ли строка в длину коммуникаций, если это понятно из таблицы.

Если строка имеет единицу `м/п`, то записывай её как погонную длину:

- `total_length_m`, если это готовая длина строки;
- `unit: "м/п"`;
- `normalized_unit: "linear_m"`.

Не записывай такую строку как "35 штук" и не трактуй её как "одна труба длиной 35 м", если в PDF стоит `м/п`.

Суммарную длину коммуникаций из позиций труб не считай в чате.

## Правило про траншеи

Если в таблице траншей есть готовая строка "Итого" с суммой, извлеки её отдельно как `trench_volume_m3` с `raw_text`.

Но также обязательно извлеки `trench_routes` по каждому маршруту отдельно:

- код маршрута;
- название маршрута;
- длина;
- глубина;
- ширина;
- объём;
- источник;
- raw_text.

Код потом должен иметь возможность пересчитать сумму и сверить с "Итого".

Если по таблице видно, что длина × глубина × ширина не равна указанному объёму, не исправляй значения сам.

В JSON всё равно запиши то, что указано в PDF, а в `notes` и/или `needs_review` отметь сомнение.

Также вынеси такую ситуацию в служебную записку для сметчицы.

## Единицы измерения

Пиши единицу как она написана в PDF в поле `unit`.

Также заполняй `normalized_unit` по таблице из `unit_normalization_guide.json`.

Если единицы нет в таблице нормализации, оставь:

`normalized_unit: null`

и укажи единицу как есть в `unit`.

## Что считать нестыковкой для служебной записки

Во время извлечения ты можешь заметить явные противоречия, сомнения или возможные ошибки проектировщика.

Такие вещи не нужно исправлять самостоятельно, но нужно кратко описать в служебной записке для сметчицы после JSON.

Отмечай только важные случаи, которые могут повлиять на смету.

### 1. Арифметика не сходится

Например:

- длина × ширина × высота не равна объёму;
- длина × глубина × ширина не равна объёму траншеи;
- сумма строк не равна итогу;
- количество × размер не похоже на итоговую площадь или объём.

### 2. Противоречие между листами

Например:

- на одном листе толщина плиты указана одна, на другом другая;
- в спецификации один объём, а в узле или разрезе другой размер;
- одна и та же конструкция имеет разные отметки, толщины, площади или объёмы.

### 3. Похожие строки с разными единицами

Например:

- ЭППС в м3 нельзя путать с площадью утепления в м2;
- опалубку в м2 нельзя путать с объёмом бетона в м3;
- периметр в м/п нельзя подставлять вместо площади.

### 4. Несколько кандидатов

Например:

- есть две площади кровли, но неясно, какая относится к нужному уровню;
- один и тот же газоблок встречается в стенах, парапетах и вентканалах;
- одно значение может относиться к разным разделам.

### 5. Неполные данные

Например:

- есть общий итог, но нет разбивки;
- есть материал, но нет строки работы;
- есть диапазон вместо одного значения;
- есть "ориентировочно", "уточнить", "по месту", "см. лист".

### 6. Возможная ошибка проектировщика

Например:

- объём в таблице не соответствует размерам;
- толщина или высота выглядит несовместимой с объёмом;
- единица измерения выглядит неверной;
- строка явно выбивается из соседних строк.

### 7. Одинаковый материал в разных разделах

Например:

- песок или геотекстиль виден и в земляных, и в фундаменте;
- один и тот же материал может быть исходной строкой для разных работ;
- нужно проверить, это одна и та же строка или разные работы.

### 8. Газоблоки

Если один размер газоблока встречается в разных местах:

- несущие стены;
- перегородки;
- парапеты;
- вентканалы;

не складывай всё случайно в одну строку.

Если неясно, что относится к какому разделу, верни `candidates`, поставь `needs_review: true` и опиши сомнение в служебной записке.

## Служебная записка для сметчицы

Твоя основная задача — извлечь данные из PDF и подготовить корректный JSON по схеме.

Но если по ходу извлечения ты видишь явные нестыковки, противоречия или сомнительные места в проекте, после JSON добавь отдельный человеческий блок:

# Служебная записка для сметчицы

Этот блок не является частью JSON.

Его не нужно вставлять в JSON-файл.

Он нужен только человеку для быстрой проверки проекта.

В служебной записке укажи только важные сомнения, которые могут повлиять на смету.

Пиши понятным языком:

- раздел;
- PDF;
- страницу;
- лист, таблицу или место на странице;
- какие значения в проекте указаны;
- что именно вызывает сомнение;
- что сметчице стоит проверить.

Не исправляй проектные данные сам.

Не подгоняй числа.

Не выбирай за сметчицу.

Не придумывай правильное значение.

Не превращай записку в длинное обсуждение.

Если данные не бьются арифметически, покажи короткую проверку.

Если в разных местах PDF указаны разные значения для одного параметра, перечисли оба места.

Если есть несколько возможных кандидатов, объясни, почему нельзя выбрать уверенно.

Если строка похожа на нужную, но единица измерения другая, укажи это.

Если значение выглядит как ошибка проектировщика, так и напиши: "возможно, ошибка проекта".

Важно:

В JSON всё равно записывай только извлечённые из PDF данные.

Если значение сомнительное, ставь:

- `needs_review: true`;
- пояснение в `notes`;
- при необходимости `candidates`.

Служебная записка — это краткое резюме сомнений для Елены.

Если явных нестыковок нет, после JSON напиши:

"Служебная записка: явных нестыковок не заметил."

## Формат финального ответа

Верни результат в двух частях.

### Часть 1. JSON для Telegram-бота

Это должен быть чистый JSON по схеме из `claude_extraction_output_schema.json`.

Не добавляй внутрь JSON служебную записку.

### Часть 2. Служебная записка для сметчицы

Это обычный текст после JSON или после ссылки на JSON-файл.

Не включай служебную записку в JSON.

Пиши только важные сомнения и нестыковки.

Пример:

# Служебная записка для сметчицы

1. Земляные работы — траншеи

PDF: <имя файла проекта>
Страница: <номер>
Лист: План котлована
Таблица: траншеи

К1: в PDF указано:
длина 40,0 м, глубина 0,5 м, ширина 0,6 м, объём 24,0 м3.

Проверка:
40,0 × 0,5 × 0,6 = 12,0 м3, а не 24,0 м3.

Что проверить:
возможно, ошибка в глубине или в объёме траншеи. Для сметы нужно решение сметчицы или проектировщика.

2. Фундаментная плита — опалубка

PDF: ...
Страница: ...
Таблица: ...

В таблице есть строка "Площадь опалубки 235,8 м2", но не уточнено, это вся опалубка или только борта.

Что проверить:
можно ли использовать это значение для нужного параметра сметы.

Если явных нестыковок нет:

Служебная записка: явных нестыковок не заметил.
