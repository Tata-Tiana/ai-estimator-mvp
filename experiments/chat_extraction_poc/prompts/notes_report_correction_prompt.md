ИСПРАВЛЕНИЕ JSON ПО ТЕХНИЧЕСКОМУ ПРИЛОЖЕНИЮ (код-отчёт)

У тебя есть в этом же чате:

1. исходные PDF-файлы проекта;
2. уже сформированный extraction JSON;
3. техническое приложение — файл `code_notes_report_*.txt`, собранный кодом (не нейронкой) из этого JSON.

Приложение — не служебная записка для сметчика. Это список технических несоответствий, которые программа нашла напрямую в структуре JSON: повторяющиеся/отсутствующие `code` в repeated group, значения, взятые из запрещённого источника, конфликты scalar-полей, и т.п. Каждый пункт помечен статусом (`semantic_error`, `needs_review`, `missing_code`, `raw_table_rows`, `not_required_alt`, `conditional_absent_ok`, `diagnostic_only`, `found`).

ВАЖНО ПО НОВОМУ РАЗДЕЛУ СТЕН И ПЕРЕМЫЧЕК P6

Раздел стен и перемычек сейчас называется `load_bearing_walls_lintels_p6`.

В нём нельзя возвращаться к старым scalar-полям:

- `main_wall_*`;
- `floor_1_lintel_*`;
- `floor_2_lintel_*`;
- `parapet_*_volume`;
- `floors_count`.

Исправляй этот раздел только через repeated groups:

- `wall_zones`;
- `wall_block_items`;
- `wall_chasing_rebar_items`;
- `lintel_items`;
- `lintel_rebar_items`.

Каждая строка блоков, штробления/арматуры и перемычек должна иметь `zone_id`, который точно совпадает с одной строкой `wall_zones[].zone_id`.
`wall_zones[].zone_kind` может быть только:

- `main_walls`;
- `second_light`;
- `parapet`;
- `vent_chimney_cladding`.

Перегородки не включай в production-группы раздела P6. Если в PDF есть строки перегородок, оставь их только в `raw_table_rows`/notes.

Не создавай отдельную `wall_zones` только ради общей строки арматуры, например "подоконное армирование",
"общее армирование", "common rebar" и т.п. `wall_zones` — это физические сметные зоны кладки: несущие
стены этажа, второй свет, парапет, обкладка вентканалов. Перемычки НЕ образуют собственную зону — они
всегда используют `zone_id` той зоны стен, к которой относятся (`lintel_items`/`lintel_rebar_items`),
даже если PDF даёт для них отдельную спецификацию/лист. Подоконное армирование по утверждённому
правилу входит в общую арматуру несущих стен: если PDF не указывает другой физической зоны, привяжи
его к зоне несущих стен 1 этажа (`zone_kind: "main_walls"`) в `wall_chasing_rebar_items`, с отдельным
`item_id`/`source_label` вроде `subwindow`. Оно должно пулироваться с остальной арматурой Ø10 этой
зоны, а не жить отдельной сметной зоной. Перегородочную арматуру при этом по-прежнему не включай.

Арматура стен/парапета/перемычек в P6 визуально будет справочной серой таблицей для Елены, но для расчёта она всё равно важна. Не удаляй её из JSON. Если строка арматуры неверна, исправь привязку к зоне/типу или оставь сомнение, но не переводь её в старые поля.

ЗАДАЧА

Пройди по приложению пункт за пунктом и реши каждый **только по этому JSON и исходным PDF** — не придумывай значения.

Для каждого пункта:

- `semantic_error` — это нарушение уже задокументированного правила (например: несколько строк одной repeated group совпадают по floor/component/steel_class/diameter и не имеют уникального `code`; или значение сопоставлено с target_code, для которого этот источник строки прямо запрещён). Исправь JSON: добавь недостающие `code` (уникальные, по смыслу строки — не порядковый номер), убери запрещённое сопоставление, разведи перепутанные значения. Если для решения не хватает данных из PDF — не исправляй молча, оставь как есть и явно об этом скажи в ответе.
- `needs_review` — прочитай соответствующие страницы PDF заново. Если можешь надёжно снять конфликт/неоднозначность по PDF — сделай это и явно опиши, что изменил. Если нет — оставь needs_review как есть, ничего не выдумывай.
- `missing_code` (список «Не найдено в JSON» в конце каждого раздела) — проверь по PDF, есть ли эти данные вообще. Если данные в PDF реально отсутствуют — не трогай. Если нашёл — добавь как `found` с указанием страницы/источника.
- `raw_table_rows`, `not_required_alt`, `conditional_absent_ok`, `diagnostic_only` — это не задачи на исправление, а объяснение уже принятого решения. Не трогай эти строки, если явно не увидишь в PDF ошибку в самом объяснении.
- `found` — значение уже успешно извлечено с высокой уверенностью, попало в приложение только из-за пояснительной заметки (например «просуммированы только эти две строки», «не путать с другим полем»). Это не задача на исправление — не трогай значение и не пересчитывай его, если явно не увидишь в PDF ошибку в самом значении или в пояснении.

ЧЕГО НЕ ДЕЛАТЬ

- Не переписывай JSON целиком «с нуля» — редактируй только то, что указано в приложении.
- Не меняй поля/секции, которых нет в приложении, даже если кажется, что их можно улучшить.
- Не рассчитывай итоговые значения (сумма зон, объём и т.п.), если в PDF нет явного готового проектного итога — так делать запрещено правилами извлечения.
- Не удаляй `needs_review`/`candidates`, если сомнение реально осталось после повторной проверки PDF.
- Не меняй `load_bearing_walls_lintels_p6` на старый `load_bearing_walls_lintels`: текущая проверка P6 ожидает именно новый section_code.

РЕЗУЛЬТАТ

1. Сохрани исправленный JSON отдельным файлом (не перезаписывай исходный, дай новое имя с суффиксом, например `_corrected`).
2. В чат выведи короткий список: что именно исправлено (пункт из приложения → что сделано), что осталось без изменений и почему.
3. Не публикуй полное содержимое JSON в чат — только ссылку на файл и список изменений.
