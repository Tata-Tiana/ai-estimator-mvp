# Шаг 3 — служебная записка для сметчицы

Используй этот промпт в новом чате без PDF и без справочников.

Загрузи только:

1. `step2_extraction.json`.

Твоя задача — написать понятную служебную записку для Елены/сметчицы по уже
готовому extraction JSON.

Служебная записка — это не краткое summary, а контрольный аудит. Она должна
помочь сметчице быстро понять, какие места в проекте могут повлиять на смету и
что именно надо проверить.

## Что проверить

1. Все `extraction_warnings`.
2. Все `needs_review`.
3. Все `missing`, если они важны для расчёта.
4. Конфликты между `raw_table_rows` и `found`.
5. Scalar targets, оставленные `null`/`missing`, потому что в PDF были только
   компоненты без явного итога.
6. Несовпадение единиц PDF и ожидаемых единиц target.
7. Строки в `raw_table_rows`, для которых нет подходящего target_code.
8. Противоречия спецификации с чертежом, узлом, подписью общего вида или
   пояснительной запиской.
9. Ошибки арифметики: сумма строк, площадь, объём, количество × длина.
10. Рискованные одинаковые материалы в разных разделах: газоблоки, ЭППС,
    гидроизоляция, мембраны, геотекстиль, Schiedel.

## Правило про штампы

Если в JSON есть предупреждения про разные штампы/адреса на листах, описывай это
как ошибку оформления/копирования страниц проектировщиками. Не пиши, что данные
с этих листов нельзя использовать, если в JSON нет отдельного содержательного
сомнения.

## Что обязательно объяснять

Для каждого важного сомнения пиши:

- что именно указано в PDF;
- почему это значение нельзя принять автоматически;
- что записано в JSON: `found`, `needs_review`, `missing`, `candidates` или
  только `raw_table_rows`;
- какой `target_code` затронут, если он есть;
- какое решение должна принять сметчица.

Не ограничивайся фразой "нужно проверить". Объясняй причину:

- не совпала единица измерения;
- нет общего итога;
- есть несколько уровней, зон, марок, типов кровли, типов плит или типов стен;
- значение относится к другой конструкции;
- таблица повторяется;
- строка может быть не той работой;
- арифметика не сходится;
- PDF содержит похожие строки с разным смыслом;
- нет `legend_ref` там, где смысл зависит от штриховки/цвета/маркера.

Если итоговое scalar-поле оставлено `missing`/`null`, прямо напиши почему:
нет явного итога, несколько компонентов, не совпадает единица, неясный контекст
или другое.

Если в JSON есть конструкции "вне списка целей", вынеси их отдельным пунктом:
они могут быть не учтены в 8 разделах калькуляторов.

## Формат записки

Пиши на русском.

Для каждого важного пункта используй стабильный формат:

```text
<N>. <Раздел> — <краткая проблема>

PDF: <source_pdf>, страница <page_number>, лист "<page_title>"
В PDF указано: <значения/строки>
Сомнение: <почему нельзя принять автоматически>
Что записано в JSON: <found / needs_review / missing / candidates / raw_table_rows, target_code>
Что проверить: <конкретное решение для Елены>
```

Не включай мелкие технические предупреждения, которые не влияют на смету.
Лучше 10-15 точных пунктов с причинами, чем 30 шумных.

В конце дай короткий итог:

- какие разделы выглядят пригодными;
- какие разделы требуют решения;
- какие ошибки схемы/словаря/парсинга видны по этому проекту.

Если явных нестыковок нет, напиши:

```text
Служебная записка: явных нестыковок не заметил.
```
