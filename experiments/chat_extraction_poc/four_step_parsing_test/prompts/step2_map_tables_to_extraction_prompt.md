# Шаг 2 — разложить сырые таблицы по сметным target_code

Используй этот промпт в новом чате без PDF.

Загрузи:

1. `step1_below.json`;
2. `step1_above.json`;
3. `data/calculator_targets_compact.json`;
4. `data/target_aliases_ru.yaml`;
5. `data/section_guide.json`;
6. `data/unit_normalization_guide.json`;
7. `schemas/claude_extraction_output_schema.json`.

PDF на этом шаге не загружается. Все числа, страницы, листы, таблицы, легенды и
цитаты нужно брать только из `step1_below.json` и `step1_above.json`.

Верни только JSON по `claude_extraction_output_schema.json`. Не добавляй
служебную записку в этот ответ: записка делается на шаге 3.

## Главный принцип

Каждый `found` item обязан ссылаться на одну или несколько строк шага 1 через
`source_row_ids` в `notes` или отдельном поле, если схема/чат позволяет.

Если нет подходящей строки в step1-файлах, значит значения нет. Не вспоминай PDF
и не придумывай значение.

Сначала сохрани нужные исходные строки в `raw_table_rows`, потом маппь их в
`found`, `needs_review` или `missing`.

## Как выбирать target_code

Используй только:

- `calculator_targets_compact.json`;
- `target_aliases_ru.yaml`;
- `section_guide.json`;
- `unit_normalization_guide.json`;
- строки из step1-файлов.

Нельзя выбирать `target_code` только по английскому или техническому имени вроде
`main_formwork_area`, `eps100_edge_volume`, `main_wall_rebar_items`.

Для каждой строки проверь:

- русский текст строки;
- `table_title`;
- `page_title`;
- `legend_ref`;
- единицу и `expected_unit`;
- `required_context`;
- `negative_context`;
- соседние ячейки и примечания.

Никогда не изобретай новый `target_code` и не меняй регистр/написание
существующего. Если важная конструкция есть в проекте, но target для неё нет,
сохрани её в `raw_table_rows` / `notes` как "вне списка целей" и добавь
предупреждение для шага 3.

## Жёсткие правила маппинга

1. Не считай смету. Твоя задача — extraction JSON.
2. Не придумывай значения. Если числа нет в step1 — не пиши его.
3. Если значение не видно явно — верни `null` и добавь код в `missing`.
4. Если таблица двумерная, строки × столбцы, сохрани структуру таблицы.
5. Если есть сомнение между значениями, верни candidates/needs_review, не
   выбирай молча одно.
6. Если поле по смыслу расчётное, не выдавай его как найденное значение, а
   сохрани исходные данные.
7. Каждая строка `raw_table_rows`, которую ты считаешь относящейся к цели,
   должна появиться в `found`, `needs_review` или объяснять `missing`.
8. Несовпадение единиц измерения — стоп-сигнал для уверенного маппинга.
9. Арифметика нужна только для проверки, а не для подмены проектных данных.
10. Если разные места проекта противоречат друг другу, сохрани источники
    отдельно, поставь `needs_review` и добавь предупреждение.

## Repeated groups вместо скаляров

Если один scalar `target_code` ожидает одно итоговое значение, а step1 даёт
несколько отдельных значений по зонам, маркам, уровням, типам, конструкциям или
таблицам, не выбирай и не суммируй их молча.

Если в `calculator_targets_compact.json` для таких данных есть repeated group
(`extract_groups`, например `*_items`, `*_rows`, `*_segments`, `*_routes`,
`roof_zones`, `schiedel_channel_items`, `wall_block_items`, `slab_zones`,
`thermal_insert_items`, `beam_items`), заполняй repeated group построчно.

Scalar заполняй уверенно только если в step1 есть явный итог именно для нужной
сущности:

- "Итого";
- "Всего";
- "Общая площадь";
- "Общий объём";
- "Суммарная длина";
- другая явно подписанная итоговая строка.

Если явного итога нет:

- не вычисляй итог как extraction-значение;
- не подставляй первое/самое большое/самое похожее значение;
- оставь scalar в `missing` или `value: null`;
- сохрани компоненты в `raw_table_rows` и/или repeated group;
- поставь `needs_review: true`;
- объясни ситуацию в `notes` / `extraction_warnings`.

Если источник даёт меньше детализации, чем ждёт target, например одна смешанная
цифра для торца плиты и торца балки вместе, не дели её искусственно. Верни как
агрегированное значение с `needs_review: true` и явным объяснением.

## Приоритет источников

Если спецификация/ведомость материалов противоречит чертежу, разрезу, узлу,
подписи общего вида или пояснительной записке, в JSON-поле фиксируй значение из
таблицы спецификации и ставь `needs_review: true`.

В `notes` укажи оба значения и оба источника. Это касается всех разделов:
площади, объёмы, длины, толщины, марки, типы материалов.

Исключение — штампы/титульные данные. Для адреса, объекта и шифра проекта
приоритет у титульного листа; расхождение штампа записывай как ошибку оформления,
но не снижай confidence и не ставь `needs_review` только по этой причине.

Толщину плиты перекрытия и аналогичных монолитных конструкций определяй по
сечению/разрезу, а не по пояснительной записке. Если после этого остаются два
кандидата на итоговый объём бетона, фиксируй большее значение и ставь
`needs_review: true`. Не уменьшай проектные данные вычислением.

## Специальные правила

### Гидроизоляция фундаментной плиты

`waterproofing.waterproofing_area_m2` — площадь гидроизоляции фундаментной плиты
битумной мастикой.

Если в step1 нет отдельной строки "площадь гидроизоляции", но есть строка
"Площадь опалубки бортов фундаментной плиты" / "Опалубка бортов" в м2,
сопоставленная с `foundation_slab.slab_side_formwork_area`, создай также
`found` item для `waterproofing.waterproofing_area_m2` с тем же числом и тем же
источником.

Для этого item поставь:

- `needs_review: true`;
- `confidence` не выше confidence исходной строки опалубки;
- `notes`: "Площадь гидроизоляции принята равной площади опалубки бортов фундаментной плиты по методике Елены."

Это разрешённое дублирование одного PDF-значения между двумя разделами. Не считай
новое число.

### Отсечная гидроизоляция

Отсечная гидроизоляция под первый ряд блоков/стен относится к разделу
`load_bearing_walls_lintels`, target:

```text
cutoff_waterproofing_load_bearing_walls_area
```

Не маппь отсечную гидроизоляцию в:

```text
waterproofing.waterproofing_area_m2
```

Если строка отсечной гидроизоляции различается штриховкой/цветом/маркером, а
`legend_ref` отсутствует, не принимай её уверенно. Оставь target в
`missing`/`needs_review` и объясни, что не хватает связи с легендой.

Если спецификация даёт отдельные строки для наружных и внутренних несущих стен
без общего итога, а target ждёт площадь под несущими стенами, можно суммировать
только эти load-bearing строки, если это прямо разрешено в notes target. Строки
перегородок не включай.

### Арматура

Если в спецификации арматура дана в `м/п`, извлекай исходную длину и массу 1 м,
если она есть. Не вычисляй общий вес в кг.

Используй поля из `group_value_shapes` / `extract_groups`:

- `foundation_rebar_items`;
- `floor_slab_1_rebar_items`;
- `floor_slab_2_rebar_items`;
- `main_wall_rebar_items`;
- `lintel_rebar_items`.

`rod_length_m` — обычно каталожная длина прутка, а не значение из PDF. Извлекай
её только если step1 явно содержит таблицу длин прутков; иначе оставь `null`.

### Коммуникации и траншеи

`communications_length_m` извлекай только если в step1 есть явная готовая общая
длина коммуникаций. Если есть только позиции труб/фитингов, не суммируй их сама:
заполни `communications_pipe_items`.

Для траншей всегда сохраняй `trench_routes` по каждому маршруту. Если есть явная
строка "Итого" по объёму траншей, её можно записать в `trench_volume_m3`, но
также сохрани построчные маршруты.

Если таблица даёт готовый `volume_m3`, записывай готовый объём из таблицы, даже
если он расходится с length × depth × width. Расхождение вынеси в notes.

### Кровля

Если кровля разбита больше чем на две зоны/типа/этажа или есть отдельная кровля
лестницы, не втискивай всё в `roof_area_level_1/2`. Используй `roof_zones`, если
она есть в `extract_groups`.

Обозначения зоны кровли бери только из спецификации/плана самой кровли. Не
переноси сюда обозначения плит ПМ1/ПМ2 с кладочного плана или плана перекрытий.

`operability` ставь `exploitable` только если лист явно пишет "эксплуатируемая".
Во всех остальных случаях ставь `non_exploitable` и `needs_review`, если есть
сомнение.

### Schiedel

Для вентканалов Schiedel важны строки товаров/модулей из спецификации, а не
количество шахт/узлов на плане. Используй `schiedel_channel_items`, если она есть
в `extract_groups`.

`quantity_pcs` — количество модулей/элементов из спецификации в штуках. Не
считай количество шахт и не подменяй им количество товара.

Если PDF даёт только линейные размеры или неясный формат без готового количества
в `шт`, оставь группу пустой/needs_review и не вычисляй количество сама.

## Формат `found`

У каждого found item должны быть:

- `target_code`;
- `group_code`, если это repeated group;
- `item_name`, если это строка repeated group;
- `value`;
- `unit`;
- `normalized_unit`;
- `source_pdf`;
- `page_number`;
- `page_title`;
- `raw_text`;
- `confidence`;
- `needs_review`;
- `notes`.

Если значение собрано из нескольких строк, перечисли все `source_row_ids` и
коротко объясни логику в `notes`.

## Что передать шагу 3

Все важные сомнения, которые должны попасть в служебную записку, сохрани в:

- `needs_review`;
- `missing`;
- `notes`;
- `extraction_warnings`;
- `raw_table_rows` для out-of-scope строк.

Шаг 3 не будет видеть PDF, поэтому не оставляй важную мысль только "в голове".

## Запреты

- Не бери значения не из step1-файлов.
- Не выбирай `target_code` по английскому имени.
- Не суммируй компоненты в scalar, если нет явного итога или явного разрешения в notes target.
- Не маппь строки с несовпадающей единицей уверенно.
- Не теряй значимые unmapped строки: сохраняй их в `raw_table_rows` / `notes`.
- Не добавляй служебную записку в JSON.
