# Арматура — округление прутков пулом на группу (этаж+компонент+зона+сталь+диаметр), не по строкам

Добавлено 2026-08-09 (см. `reports/trc_vs_original_comparison/05_floor_slab_1.md`, находка про
округление арматуры — тот же баг, что уже чинили в разделе стен/перемычек, отчёт 04).

Реальные числа ТРЦ: основная зона — 12 отдельных именованных строк Ø10 A500C (P1_D10 ... BG_D10,
включая балочную арматуру B4_D10/B5_D10, физически часть основной зоны), кухня — 3 строки Ø10.
До фикса калькулятор округлял КАЖДУЮ строку до целого прутка (11.7м) НЕЗАВИСИМО — теряя лишний
пруток почти на каждом округлении. После фикса — сумма метров группы считается один раз, округление
один раз на группу:

- main: 4286.375м база × 1.05 = 4500.69 → 385 прутков = **4504.5м** (её реальное число, было 4551.3)
- kitchen: 811.15м база × 1.05 = 851.71 → 73 прутка = **854.1м** (её реальное число, было 865.8)

Важно: зоны пулятся ОТДЕЛЬНО через `zone_context` (сумма main+kitchen БЕЗ разделения по зонам дала
бы 458 прутков = 5359.8м — не совпадает с её реальными 4504.5+854.1=5358.6м). Она округляет по зоне
отдельно, тот же паттерн «по зоне, потом сложить», что уже подтверждён на доставке опалубки и
материале бетона.

`zone_context` — опциональное поле per rebar_items[] строка. Текущее реальное извлечение ТРЦ его
ещё не даёт (все её позиции сейчас различаются только кодом с префиксом "K_" у кухни, не отдельным
полем) — фикс уже пулит арматуру БЕЗ разделения по зонам на текущих данных (частичное улучшение:
пул один на весь раздел, а не по строкам), полное совпадение появится после того, как zone_context
попадёт в извлечение. Не стала опираться на текстовый признак ("K_" в коде / "Кухня:" в названии) —
это ровно тот текстовый хак, которого мы избегаем везде в проекте (см. fact_of_data_vs_text_signal_
principle), нужен настоящий отдельный столбец.

`legacy_weight_parts` (второй calc_method) НЕ тронут — пулинг применяется только к
`spec_length_items`, где есть реальные доказательства бага; для weight-based строк отдельного
подтверждения нет.
