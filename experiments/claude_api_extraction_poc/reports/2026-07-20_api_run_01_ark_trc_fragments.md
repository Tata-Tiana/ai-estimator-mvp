# Отчет по первому API-прогону Claude

Дата: 20 июля 2026  
Эксперимент: `experiments/claude_api_extraction_poc`  
Статус: первый технический прогон небольших фрагментов ARK и TRC через Claude API  
Стоимость прогона по факту: 1,54 $

## 1. Зачем делали прогон

Цель была проверить, можно ли заменить ручной чатовый парсинг PDF более управляемым API-процессом.

Важно: ARK, TRC и USV не являются источником универсальных правил. Это только тестовые проекты. Мы проверяем не “подгонку под проект”, а будущий универсальный парсер: любой проектный JSON/набор PDF должен пройти одинаковый путь.

Проверяли два результата:

- `extraction_output.json` — структурированный JSON для дальнейшей проверки и Google-таблицы;
- `service_memo.txt` — служебная записка для сметчицы, где понятным языком написано, что найдено, где сомнения и что нужно проверить.

## 2. Что использовали

Модель API:

- `claude-sonnet-4-6`

Почему именно она:

- первый запуск с прежним именем модели `claude-sonnet-4-20250514` не прошел: Anthropic API вернул `model not found`;
- после этого дефолт в API-эксперименте был заменен на актуальный `claude-sonnet-4-6`.

Библиотеки:

- PyMuPDF (`fitz`) — открыть PDF, вытащить текстовый слой страниц и отрендерить страницы в PNG;
- `requests` — отправить запрос в Anthropic API;
- локальный validator `validate_claude_extraction.py` — проверить форму JSON после ответа модели.

Что важно: на этом шаге библиотеки еще не парсили таблицы как полноценный табличный extractor. Они были использованы как подготовительный слой:

1. PDF открывается программно.
2. Каждая страница сохраняется как текст.
3. Каждая страница сохраняется как картинка PNG.
4. В Claude API отправляются выбранные страницы: текст + картинка + prompt-pack.
5. Claude делает JSON и служебную записку.

То есть это был не “чисто библиотечный парсер таблиц”, а гибрид: библиотека готовит материал, модель читает и маппит.

## 4. Как прошел запуск технически

Было три API-вызова, которые важны для истории эксперимента.

### ARK, первая попытка

Модель: `claude-sonnet-4-6`  
Вход: 69 702 input tokens  
Выход: 20 000 output tokens  
Stop reason: `max_tokens`

Результат: ответ оборвался на середине JSON. Полезный текст был получен, но итоговый JSON не был валиден.

Вывод: даже маленький фрагмент на 3 страницы становится тяжелым, если передавать полный prompt-pack и разрешать модели подробно расписывать все отсутствующие цели. API-режим должен быть компактнее, чем ручной чатовый prompt.

После этого в секционный API-prompt добавлено правило:

- не создавать `found`/`extracted_values` с `value: null` для каждого отсутствующего target;
- отсутствующие targets перечислять в `missing`;
- в `found` класть найденные значения и спорные найденные кандидаты;
- служебную записку писать только по выбранным страницам.

## 5. Что получилось хорошо

### 5.1. API-процесс технически работает

Удалось получить оба итоговых файла:

- JSON;
- служебную записку.

JSON проходит локальную проверку формы. Это значит, что API-процесс уже можно использовать для маленьких контролируемых фрагментов.

### 5.2. Модель хорошо пишет служебную записку, если видит конфликт

В ARK модель заметила, что на страницах кровли есть не одна простая площадь, а несколько типов/уровней:

- кровля Тип А, отм. +3,730 — 224,3 м2;
- кровля Тип Б, отм. +3,730 — 54,8 м2;
- кровля Тип А, отм. +5,160 — 84,9 м2.

Служебная записка правильно объяснила риск: калькулятор ждет более простые поля `roof_area_level_1` и `roof_area_level_2`, а в проекте фактически три компонента.

Это хорошо: модель не стала молча складывать все в одно число.

### 5.3. ARK: модель правильно увидела, что это не Schiedel

В ARK на странице 25 нет системы Schiedel. Там газоблочные шахты вентканалов.

Служебная записка написала это очень полезно:

> В проекте НЕТ системы Schiedel; это газоблочные шахты.

Это сильное место API-прогона. Для сметчицы такая фраза важнее, чем просто “missing”.

### 5.4. TRC: модель правильно нашла общую высоту вентканалов

В TRC на странице 40 есть явная строка:

- `4,9 п.м + 4,9 п.м = 9,8 п.м`

API-прогон записал:

- `schiedel_masonry_total_length_m = 9,8 п.м.`

Это совпадает со старым chat-прогоном.

## 6. Что получилось плохо или опасно

### 6.1. Модель пока слабая в сметном смысле

Главная проблема: модель видит таблицу, но не всегда понимает, что именно нужно калькулятору.

Самый показательный пример — TRC, Schiedel.

В PDF есть строки:

- `Вентиляционный канал 1х,20/25 см Schiedel — 21 шт`;
- `Вентиляционный канал 2х,36/25 см Schiedel — 15 шт`.

API-прогон записал:

- `schiedel_vent_channel_2x_count = 21 шт`, needs_review;
- `vent_channel_2_count = 15 шт`, needs_review.

Проблема: 21 шт и 15 шт — это похоже на количество элементов/блоков Schiedel в спецификации, а не количество шахт на плане. В старом chat-прогоне это было лучше: `vent_channel_2_count` был записан как 1 шт с проверкой.

Вывод: для Schiedel нужно отдельное универсальное правило:

- `шт` в спецификации элементов Schiedel — это элементы/блоки;
- количество шахт/каналов брать только из плана или явной строки про количество шахт;
- не переносить количество элементов в `vent_channel_*_count` без `needs_review` и объяснения.

### 6.2. Полный prompt-pack слишком тяжелый для маленького фрагмента

Даже 2-3 страницы дали 66-70k input tokens, потому что вместе с ними передается полный prompt, schema, targets, aliases и guides.

Это дорого и медленно. Для полного ARK/TRC так идти нельзя.

Нужен подготовительный слой:

- сначала библиотека собирает `page_inventory.json`;
- затем по alias/section guide выбираются только нужные страницы и строки;
- в Claude отправляется не весь огромный prompt-pack, а короткий секционный task + нужные targets/aliases конкретного раздела.

### 6.3. Библиотеки пока не помогают модели понять таблицу

Сейчас PyMuPDF только подготовил:

- текст страницы;
- PNG страницы.

Но он не выделил заранее таблицы, строки, колонки и координаты. Поэтому Claude все равно делал сложную работу сам.

Следующий слой должен дать модели более жесткую заготовку:

- найденные текстовые блоки;
- возможные таблицы;
- строки-кандидаты;
- совпадения по русским aliases;
- координаты/страницы;
- предупреждения, где текстовый слой плохой и надо смотреть картинку.

## 7. Сравнение с ручными чатами GPT/Claude

### По ARK

API-прогон сильнее в диагностике по выбранным страницам:

- хорошо увидел три площади кровли;
- хорошо описал конфликт 224,3 м2 / 226,1 м2;
- хорошо написал, что вентканалы в ARK не Schiedel, а газоблочные шахты;
- хорошо вынес спорные места в служебную записку.

Но JSON стал осторожнее:

- `project_spec_roof_area` оставлен `null`;
- `roof_area_level_1` оставлен `null`;
- `roof_internal_drains_count` оставлен `null`.

Это не обязательно плохо: для спорного проекта осторожность лучше, чем подстановка неверного итога. Но для автоматического слоя дальше нужно уметь хранить компоненты, а не только scalar.

### По TRC

Ручной chat-прогон был лучше именно по смыслу количества вентканалов:

- старый результат: `vent_channel_2_count = 1 шт` с проверкой;
- API-прогон: `vent_channel_2_count = 15 шт` с проверкой.

API-прогон при этом хорошо написал служебную записку и сам предупредил, что 15 шт — возможно элементы, а не шахты. Но он все равно положил это число в target, что опасно.

Вывод: API-модель может быть полезной как внимательный читатель и автор записки, но ей нужен более жесткий подготовленный вход и правила маппинга.

## 8. Вывод для руководства

Первый API-прогон считать технически успешным, но не готовым к production.

Что подтвердилось:

- Claude API может принимать подготовленные страницы PDF как текст + картинки;
- по небольшим фрагментам можно получить JSON и служебную записку;
- служебная записка может быть полезной и понятной для сметчицы;
- validator подтверждает формальную валидность JSON.

Что не подтвердилось:

- нельзя просто дать API полный prompt-pack и ждать стабильного production-парсинга;
- модель без дополнительного слоя путает инженерный смысл некоторых количеств;
- полный запуск по всем страницам ARK/TRC в текущем виде будет дорогим, медленным и рискованным.

Главный следующий шаг:

сделать слой подготовки данных перед Claude:

1. `page_inventory.json` по каждому PDF;
2. список таблиц/строк/кандидатов по страницам;
3. поиск по русским aliases;
4. секционный selection: какие страницы и строки отправлять в модель;
5. только после этого — Claude API как mapper + автор служебной записки.
