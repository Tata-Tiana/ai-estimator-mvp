# Floor Slab Unification Plan — от "8 разделов" к N плитам на проект

Дата создания: 2026-08-09.

**Если контекст сессии прервался — читай этот файл первым**, до того как трогать `floor_slab_1`,
`floor_slab_2`, `SECTION_ORDER` в `export_calculator_results_to_estimate_workbook.py`, или
`section_contract.yaml` любой из этих двух секций. Источник: построчный анализ
`reports/trc_vs_original_comparison/05_floor_slab_1.md` (сессия 2026-08-09) + прямое построчное
сравнение 8 реальных плит перекрытия из 3 проектов (ТРЦ×4, АРК×2, ЮСВ×2), см. раздел "Что подтвердил
анализ" ниже. Этот файл — ПЕРВЫЙ шаг (только план), никакого кода ещё не менялось.

## Зачем этот файл

Вся система сейчас построена на правиле **"8 фиксированных калькуляторов = 8 фиксированных
разделов сметы"** (`SECTION_ORDER` в билдере финальной сметы, `HANDOFF.md`'s "Step 4 — Section
Order"). Для `floor_slab_1`/`floor_slab_2` это правило — искусственное упрощение: в реальности
проект содержит не "плиту 1 этажа" и "плиту 2 этажа", а **произвольное число физически отдельных
плит перекрытия** — у ТРЦ их 4 (основная 1 этажа, кухня/столовая 1 этажа, 2 этаж, плита лестницы),
каждая со своим разделом сметы, своим "Итого по разделу", своими накладными. Название раздела не
подчиняется схеме "этаж N" — есть "второй свет", "плита кухни", "плита лестницы" и т.п.

Сейчас это временно обходится через `slab_zones[]` ВНУТРИ `floor_slab_1` (main+kitchen слиты в один
расчёт с одним итогом) — рабочий, но принципиально ограниченный костыль: не масштабируется на 3+
плиты, не даёт отдельного "Итого по разделу" на каждую (важно для сверки со сметчиком построчно),
и не обобщается на `floor_slab_2`/будущие проекты с другой разбивкой.

## Что подтвердил анализ (2026-08-09, до этого плана)

Построчно сравнены ВСЕ 8 доступных реальных плит перекрытия (не только floor_slab_1's 2 зоны):
ТРЦ main/кухня/2эт/лестница, АРК +3.550/+4.980, ЮСВ 1эт(180мм)/2эт(200мм). Результат — **это один
шаблон**, ~20 строк идентичны по составу и порядку во всех 8 без исключений (монтаж опалубки,
комплект опалубки, доставка манипулятором, подача арматуры/опалубки автокраном, расходники опалубки,
монтаж опалубки доски, фанера, пиломатериал, каркас арматуры, арматура по диаметрам, бетонирование
плиты, бетон материал, доставка бетона, бетононасос, утепление торца, ЭППС материал, клей-пена,
6-строчный overhead-блок логистика/расходники/технадзор/заготовительно-складские/накладные/прибыль).

Расхождения между плитами делятся на 3 категории, ни одна не требует разных калькуляторов:

1. **Управляется фактом данных** (уже умеет `floor_slab_1_calculator.py` через опциональные поля):
   есть балки → есть строки бетонирования балок; открытый низ плиты → есть утепление низа; способ
   доставки арматуры (отдельным рейсом или вместе с опалубкой).
2. **Две настоящие методические развилки между ПРОЕКТАМИ** (не между плитами одного проекта) —
   нужны как calc_method-флаги:
   - Демонтаж опалубки: control-строка (0₽) у ТРЦ, реальные деньги у АРК и ЮСВ.
   - Деление бетонирования балок по высоте (≤250мм/>250мм, 2 ставки): есть у ТРЦ и АРК, у ЮСВ —
     одна строка «Бетонирование балки» по объёму, высота не делится вообще.
3. **Один настоящий разовый случай** — закладные детали ЗД-1 + лист 16мм у АРК зона1 (уникальная
   деталь конкретного проекта) — это ad-hoc `manual_lines`, не повод для нового структурного поля.

Полная таблица — в чате сессии 2026-08-09 (не сохранена отдельным файлом, при необходимости
перестроить: pull имя+ед.изм+кол-во столбцов B/C/D для каждого раздела напрямую из трёх исходных
xlsx на Рабочем столе, как это было сделано здесь).

## Базовые правила (унаследованы из UNIVERSALIZATION_PLAN.md, повторены для этого потока)

- Не придумывать числа/поля — только то, что подтверждено реальными PDF/xlsx минимум 2 проектов.
- Каждый шаг ниже — аддитивный, где возможно: старое поведение (`floor_slab_1`/`floor_slab_2` как
  сейчас) должно продолжать работать байт-в-байт, пока новый механизм явно не включён данными.
- **Явная авторизация пользователя перед КАЖДЫМ из шагов P1-P4** — это не одна правка, а
  последовательность независимо авторизуемых решений. Не начинать следующую фазу без отдельного
  "давай" на неё, даже если план в целом одобрен.
- Промпт извлечения (`calculator_targets_compact.json`/`target_aliases_ru.yaml`) — трогаем
  последним (P4), после того как схема+калькулятор+оркестрация проверены на уже извлечённых
  реальных данных (тот же порядок, что во всех P1-находках `UNIVERSALIZATION_PLAN.md`).
- Никогда не дописывать реальные данные проекта (ТРЦ/АРК/ЮСВ) вручную ради проверки нового
  механизма — только синтетические тест-кейсы с реальными числами (уже устоявшийся паттерн сессии
  2026-08-09, см. `test_slab_zones_additional_concrete_items`, `test_rebar_pooled_per_zone`).
