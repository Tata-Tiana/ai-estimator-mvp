# P6. Новый production contract для стен, перемычек и парапета

Дата: 2026-08-13. По аналогии с P5 (`P5_SLAB_DATA_CONTRACT.md`) — тот же принцип: зона вместо
фиксированного этажа. Основание — реальные чертежи КР2 всех 3 проектов (ТРЦ/АРК/ЮСВ), см. ниже.

## Подтверждение на реальных документах (сделано перед этим планом, не гипотеза)

Проверила листы КР2 (второй структурный комплект — стены/кладка, отдельно от КР1 — фундамент/плиты)
на всех 3 проектах:

- **ТРЦ** (КР2, лист 8): «Спецификация стенового блока» — одна таблица, но каждая строка с явной
  меткой зоны: `1эт`, `2эт`, `вентканалы`, `парапеты1эт`, `парапеты2эт` (парапет разделён по этажу!).
  Рядом — «Спецификация расхода арм-ры на армирование стен», та же разбивка по зоне+толщине блока.
- **АРК** (КР2): отдельные ЛИСТЫ чертежа под каждую зону («Кладочный план парапета кровли»,
  «Кладочный план стен 2 этажа и парапетов...»), в каждом — своя таблица блока и арматуры, явно
  подписанная («Стены надстройки» / «Парапет» отдельными группами строк).
- **ЮСВ** (КР2, лист 15): «Спецификация по газобетонным блокам» — 4 отдельные подтаблицы:
  «...несущих стен 1-го этажа», «...перегородок 1-го этажа», «...несущих стен 2-го этажа»,
  «...парапетов кровли», каждая со своим объёмом блока и длиной арматуры.

Вывод: источник данных **уже зонирован** на всех 3 проектах — ровно так же, как плиты перекрытия
были зонированы по маркам до P5. Значит парсер может и должен извлекать стены так же, как теперь
извлекает плиты — по зонам, а не по фиксированному «1 этаж / 2 этаж».

## Важное отличие от плит: две вложенные сущности, не одна

У плиты зона самодостаточна (бетон+опалубка+утепление+балки+арматура одной плиты). У стен внутри
каждой зоны кладки есть ещё **перемычки** (над проёмами) — отдельная подсущность со своей
геометрией/арматурой/бетоном/опалубкой/утеплением, которая физически находится внутри той же зоны
кладки, но считается отдельно (U-блок перемычки vs монолитные — разные материалы и работы). Схема
должна отражать это как вложенный список, а не приравнивать зону кладки к зоне перемычек.

## Уточнение 2026-08-13: что общее на весь раздел, а что повторяется по зонам

Раздел стен — не «один раздел на зону», как у плит, а **одна секция с общей головой/хвостом +
список зон внутри**. Прошла построчно по ТРЦ и АРК, потом (после того как нашла у ЮСВ неправильный
лист — реальная полная смета лежит на листе `АЛ 06.04 КР1,КР2 (ЕЧ)(ЮВ)КровТН`, не на `РС 29.04.26`,
у которой нет серых колонок вообще) перепроверила и на ЮСВ тоже. Все 3 совпадают:

**Section-wide, один раз на весь раздел (НЕ внутри зон):**
- Леса, подмостья + пиломатериал для лесов — одна строка перед первой зоной.
- Расходные материалы (%), вывоз мусора, технадзор, 3 нулевые markup-строки — один блок после
  последней зоны.

**Повторяется в каждой зоне (обычные zone-scoped поля):**
- Кладка (объём работы), блоки по плотности, клей, штробление+арматура по диаметру,
  доставка/разгрузка/кран.

**Опциональные zone-scoped поля — есть не у каждой зоны, и это нормально, не ошибка:**
- Перемычки (`lintel_items[]`) — у ТРЦ есть у КАЖДОЙ зоны кладки (льёт поэтажно). У АРК и ЮСВ —
  только у ОДНОЙ зоны (обычно первой/нижней), весь дом перемычками поэтажно не делится. Значит
  `lintel_items[]` пристёгнут к конкретному `zone_id` как обычное поле зоны — просто на практике
  у 2 из 3 проектов он будет заполнен только у одной зоны, у остальных пусто. Никакой специальной
  логики «перемычки относятся ко всему разделу» вводить не нужно — обычное опциональное поле зоны.
- Гидроизоляция под первый ряд блоков — сначала подумала, что это «на самом деле про всё здание»
  и предлагала отдельное section-wide поле. Пересмотрела: это гидроизоляция именно нижнего ряда
  блоков, значит нужна только той зоне, что реально стоит на плите/земле. У всех 3 проектов
  «второй свет»/«кухня-гостиная»/парапет — надстройки НА стенах, плиты не касаются, им это не
  нужно физически, не по случайности чертежа. Значит это тоже обычное опциональное поле зоны, а
  не section-wide — просто заполняется только у зоны, которая касается плиты (везде это первая
  зона, но это следствие физики, не жёсткое правило "всегда первая").
- Обкладка дымохода/вентканалов — есть только у `zone_kind: parapet` (там вентканалы выходят на
  крышу), у остальных зон нет.

**Вывод для схемы:** `wall_zones[]` — все специфичные под-блоки (`lintels`, гидроизоляция первого
ряда, обкладка дымохода) должны быть НЕОБЯЗАТЕЛЬНЫМИ полями зоны, без required-проверки «у каждой
зоны должно быть». Section-wide голова/хвост (леса, расходники/вывоз мусора/технадзор) — отдельные
поля на уровне всей секции, не внутри `wall_zones[]` вообще.

## Что уже работает правильно — НЕ переделывать

Проверила калькулятор перед тем, как писать план — часть инфраструктуры уже зонированная и
корректная:

- **`main_wall_rebar_items[]`** уже несёт `floor` (int) и `component` на каждой строке, и
  `rebar_from_spec_length_items_pooled()` уже пулит строго по `(floor, component, steel_class,
  diameter_mm)` — это подтверждено собственным docstring-ом функции на реальных ТРЦ/АРК/ЮСВ данных
  (2026-08-09): суммарная длина по каждой (этаж, диаметр) группе, округлённая ОДИН раз до целых
  прутков, точно совпадает с её реальными числами на всех трёх проектах. Менять эту логику не
  нужно — она уже зонирована правильно.
- **`wall_block_items[]`** уже частично динамический — каждая строка несёт `wall_role`, калькулятор
  уже умеет читать per-role объёмы независимо (main_walls/floor_2/parapet каждый по-своему, с
  fallback на старые scalar-поля, если конкретной роли в списке нет).

## Что сломано прямо сейчас — можно почистить отдельно, без этого плана

Экспортный Stage 2 rebar-pooling (`_pool_rebar_lines()`, `export_calculator_results_to_estimate_
workbook.py`, добавлен 12.08 для фундаментной плиты/плит перекрытия — секции с ОДНОЙ зоной) группирует
только по `price_code` (класс+диаметр), без floor/zone. Раздел стен — единственный, где секция
содержит НЕСКОЛЬКО зон внутри себя, и этот пулинг склеивает арматуру 1-го и 2-го этажа обратно в
одну строку на экспорте — хотя калькулятор отдаёт её раздельно (см. выше). Это баг ЭКСПОРТА, не
калькулятора. Чинится точечно: добавить floor/zone в ключ пулинга для этой конкретной секции, не
трогая остальные 7 (у них зона всегда одна, добавление ключа — no-op).

## Новая структура extraction JSON (по аналогии с `floor_slabs.slab_zones[]`)

```yaml
sections:
  load_bearing_walls_lintels:
    wall_zones:
      - zone_id: string        # "floor_1", "floor_2", "parapet_floor_1", "parapet_floor_2",
                                # "partitions_floor_1", "vent_chimney_cladding", ...
        display_name: string   # "Кладка стен 1-го этажа", "Парапет кровли над 1 этажом"
        zone_kind: main_walls | second_light | parapet | partitions | vent_chimney_cladding | other
        source_level: string | null
        include_in_estimate: true
        status: found | needs_review | missing
        source_refs: []
        masonry:
          block_items: []        # {block_density, thickness_mm, volume_m3, source_ref} — как в спецификации
          chasing_rebar_items: [] # штробление/порядовое армирование, по диаметру — та же схема,
                                   # что main_wall_rebar_items сейчас, просто zone_id вместо floor:int
        lintels:
          - lintel_id:
            lintel_kind: u_block | monolithic
            total_length_m:
            concrete_volume_m3:
            rebar_items: []
            formwork: {}
            insulation: {}
            groove_length_m:      # для partitions-зон
        manual_inputs:
          crane_shifts:
          delivery_trucks:
```

Правило `zone_id`, как в P5: если в проекте есть явная метка (ТРЦ: «парапеты1эт»/«парапеты2эт»;
АРК: «ПМ1»/«ПМ2») — использовать её как основу; если метки нет — нейтральный контекст (`floor_2`,
`vent_chimney_cladding`). НЕ вводить отдельное поле "номер этажа" как int нигде в схеме — весь смысл
"это не 1-й этаж, а что-то ещё" передаётся через `zone_id`/`zone_kind`, без привязки к числу.

## Уточнение 2026-08-13: парапет — ОДНА билинговая зона, несмотря на несколько зон в чертеже

Проверила реальные сметы всех 3 проектов напрямую (не только чертежи КР2) — важная поправка к
разделу выше. Хотя чертёж КР2 у ТРЦ даёт парапет ДВУМЯ отдельными зонами (парапеты1эт 5.94 м³ +
парапеты2эт 13.21 м³ = 19.15 м³), в реальной смете — **только одна секция «Парапет»**, и её объём
кладки (19.15 м³) — это ровно сумма обеих чертёжных зон. То же самое у АРК (две отдельные страницы
кладочного плана парапета в КР2, но одна секция «Парапеты» в смете) и у ЮСВ (там даже в чертеже
парапет не делится на этажи).

Значит: `zone_kind: parapet` — это **не отдельная зона на каждый этаж**, а ВСЕГДА одна билинговая
зона на весь проект, даже если внутри неё несколько физических подзон с разным объёмом. Схема
`wall_zones[]` должна это отражать так же, как P5 сделала со slab_zones — одна billing-зона
`parapet` с массивом `masonry.block_items[]` внутри (несколько строк объёма по подзонам/этажам,
как позволяет реальная спецификация), а не `parapet_floor_1`/`parapet_floor_2` как две отдельные
записи в `wall_zones[]`. Детализация по подзонам нужна только для проверки парсера (Stage 1,
zoo-строки) — то же двухэтапное разделение, что уже сделано для арматуры по диаметрам и сейчас для
ЭППС50+100 в гидроизоляции: Stage 1 = полная детализация для сверки с PDF, Stage 2 (сама смета) =
объединённые billing-строки.

Это касается только `zone_kind: parapet`. Для 1-го/2-го этажа основной кладки — наоборот, каждый
этаж остаётся своей отдельной billing-зоной (Елена держит их раздельными секциями во всех 3
сметах) — там дробление по этажам реальное и билинговое, не только чертёжное.

## Уточнение 2026-08-13: балки, перемычки и перегородки — что нашла на всех 3 проектах

Смотрела и чертежи (КР2 — отдельные листы «План перемычек 1/2 этажа» с собственной спецификацией
именно под перемычки), и реальные сметы всех троих.

### «Балки» — это не отдельная сущность для этого раздела

На чертеже АРК (лист 11, легенда) есть буквально 4 обозначения: красная толстая линия — «ж/б балка
**в теле плиты ПМ1**» (это балка ВНУТРИ плиты перекрытия, её место — `floor_slab_beam_items`,
уже есть, к стенам отношения не имеет вообще); зелёная — «ж/б балка **перемычка** ПБ» (буквально
одно и то же слово через дефис — это и есть монолитная перемычка, просто над широким проёмом её
называют то «балка», то «перемычка», не разделяя). В самой смете ТРЦ то же самое видно с другой
стороны: 1-й этаж называет эту строку «...армирования **перемычек**», 2-й этаж — «...армирования
**балок**» — то же самое действие, просто другое слово в тексте, не другая категория. **Вывод:
отдельная сущность «балки» в разделе стен не нужна — то, что иногда называют балкой, это и есть
монолитная перемычка (`lintel_kind: monolithic`) над широким проёмом.** Настоящие балки (внутри
плит перекрытия) уже покрыты `floor_slab_beam_items` в другом разделе — переделывать не нужно.

### Перемычки — типы задаются (толщина стены × способ), не просто "U-блок vs монолит"

На «Плане перемычек» у АРК/ТРЦ каждый проём промаркирован своим типом (ПР-1/ПР-2/ПР-3, ПБ-1/ПБ-2 у
АРК; ПР-1/ПР-2 у ТРЦ), и у каждого типа — своя спецификация арматуры/бетона/опалубки. По сути тип
= (толщина стены, в которой проём) × (способ: U-блок фабричный vs монолит по месту). У ТРЦ, кроме
того, есть третий вариант — просто пруток арматуры в штробе без бетонирования вообще (на плане
подписан отдельным цветом, без своей спецификации бетона) — по объёму денег незначимый (это просто
кусок арматуры, не отдельная работа), но для полноты картины в extraction стоит не терять эту
метку, а не пытаться классифицировать её как «U-блок» с нулевым бетоном.

**Практический вывод:** уровень детализации `lintel_kind: u_block | monolithic` (уже есть в этом
плане) — правильный для СМЕТЫ (Елена сама не делает разницы между ПР-1/ПР-2/ПР-3 в смете, там всё
уже свёрнуто до «перемычки в U-блоке» одной строкой + «монолитные перемычки» отдельной строкой).
Деление по промаркированным типам (ПР1/ПР2/ПР3/ПБ1/ПБ2) нужно только на Stage 1 (зоопарк для сверки
с PDF), не в самой смете — тот же принцип двух этапов, что уже применили к арматуре по диаметрам.
Перемычки остаются per-floor зоной (как в текущем плане) — оба проекта держат отдельные листы «План
перемычек 1/2 этажа», это реальное, не выдуманное деление.

### Перегородки — ОТДЕЛЬНЫЙ раздел сметы, вне скоупа этого плана (решение 2026-08-13)

Перегородки — своя секция сметы у всех проектов («КЛАДКА ПЕРЕГОРОДОК, ПЕРЕМЫЧКИ НАД ПРОЕМАМИ»), не
подраздел стен. Своего калькулятора под неё пока нет — делать её сейчас не будем, весь план выше
(`wall_zones[]`, `lintel_items[]`) — только про `load_bearing_walls_lintels` (несущие стены,
1эт/2эт/парапет), перегородки туда не входят.

Парсер уже умеет находить объём/арматуру перегородок отдельно (`wall_block_items` с
`wall_role=partitions`) — это нормально, пусть находит, пригодится для будущего калькулятора. Но
`load_bearing_walls_lintels_calculator.py` уже проверила напрямую — он защищён от смешивания:
арматура с `component="partitions"` вызывает жёсткую ошибку («must be calculated in partitions
calculator, not in load_bearing_walls_lintels_calculator», строка 583), а объём блоков перегородок
захватывается (`partitions_captured_volume_m3`) но сознательно НЕ оценивается в деньгах (решение от
2026-07-20). То есть даже если парсер найдёт перегородки, в сумму раздела несущих стен они не
попадут — путаницы нет, можно не бояться при переделке P6.

### Открытый вопрос по ЮСВ (не блокирует, для истории)

У ТРЦ и АРК «КЛАДКА ПЕРЕГОРОДОК, ПЕРЕМЫЧКИ НАД ПРОЕМАМИ» — отдельный раздел сметы (не подраздел
стен), со своими особенностями: кладка меряется в **м²**, не м³ (толщина 100/150мм даётся отдельным
множителем в описании работы, не как параметр объёма) — другая единица измерения, чем у несущих
стен. Перемычки над проёмами В ПЕРЕГОРОДКАХ — только штробление+арматура (уже зафиксировано ранее
как [[lintel_groove_partitions_and_insulation_note]]), никогда не льются как U-блок или монолит —
для перегородки это не нужно конструктивно (лёгкая ненесущая стена).

У ЮСВ — при этом её КР2-чертёж ДАЁТ отдельную «Спецификацию перегородок 1-го этажа» (16.81 м³,
189 п.м арматуры), но в её собственной смете (лист «РС 29.04.26») я не нашла ни одной строки,
явно упоминающей перегородки — либо они спрятаны внутри общей формулировки «внешних, внутренних
стен» без отдельного упоминания, либо реально не выставлены отдельной строкой в этой версии сметы.
Это не повод копировать её пробел — если у нас будет реальный объём перегородок из проекта, его
нужно считать, независимо от того, показала ли Елена это отдельной строкой у себя. Стоит уточнить
у неё при случае, но не блокирует план — перегородки остаются своей зоной (`zone_kind: partitions`)
по образцу ТРЦ/АРК, с площадью (не объёмом) как первичной величиной кладки.

## Роли — из фиксированного enum в открытый список

`WALL_BLOCK_ITEM_ROLES = {main_walls, floor_2, parapet, partitions}` — заменить на открытый список
зон. Обоснование не гипотетическое: у ТРЦ уже сейчас нужно 2 парапета (1эт/2эт раздельно, разные
объёмы — 5.94 м³ и 13.21 м³), а не 1 роль `parapet` на всё; и нужна отдельная роль под «обкладка
вентканалов» (ТРЦ КР2 л.8: D500 150мм, 0.66 м³, своя строка в спецификации) — этот объём калькулятор
сейчас вообще не читает, это реальный пробел, не запасной случай на будущее.

## Перемычки — та же унификация

Сейчас: `floor_1_lintel_*` / `floor_2_lintel_*` — 12+ отдельных scalar-полей, дублирующих друг друга
по имени один в один под каждый этаж (`floor_1_lintel_monolithic_concrete_volume_m3` /
`floor_2_lintel_monolithic_concrete_volume_m3` и так далее). Перевести на `lintel_items[]` с
`zone_id` (ссылка на `wall_zones`) + `lintel_kind` — одна схема полей для любой зоны, без
дублирования имени поля под каждый этаж. Заодно закрывает найденную в отчёте v2 несостыковку
(1-й этаж — одна строка бетонирования U-блок+монолит вместе, 2-й этаж — две строки у самой Елены):
с явным `lintel_kind` на каждой позиции это будет видно из данных, а не угадываться кодом.

## Ручные поля (кран/доставка) — per-zone, а не смесь формулы и исключения

Сейчас `parapet_crane_shifts` — отдельное ручное поле только для парапета, а кран для этажей
считается формулой (`delivery_trucks_threshold`). По аналогии с решением по плитам (per-pour manual
costs, 2026-08-10 — кран/насос/доставка металла/технадзор всегда per-pour, не общий пул) — кран и
доставка для стен тоже должны быть per-zone полем в одном списке, единообразно для любой зоны, а не
формула для одних зон и ручное поле для других по историческим причинам.

## Почему делать в 2 этапа, а не всё сразу

В отличие от плит (где P5 полностью и сразу заменила `floor_slab_1`/`floor_slab_2` одним движком),
здесь реалистичнее так:

1. **Быстрый фикс экспортного pooling** (per-zone ключ) — закрывает конкретно ту находку, из-за
   которой начался этот разговор (арматура 1+2 этажа слипается в смете). Маленький, безопасный,
   не трогает extraction/adapter, делается отдельно от всего плана ниже хоть сегодня.
2. **Полная P6-переделка** (открытый список зон на extraction + `lintel_items[]` + ручные поля
   per-zone) — объём работы сопоставим с P5 (раздел уже назван «12 calc_methods, самый сложный» из
   8), с отдельным adapter-этапом и полным regression-прогоном (30+ существующих кейсов
   `load_bearing_walls_lintels_calculator`). Делать отдельным большим заходом.

## Первый практический шаг

1. Фикс экспортного pooling (шаг 1 выше) — можно сделать прямо сейчас, независимо от остального.
2. Затем (отдельный заход): новая секция `wall_zones` в extraction schema/prompt — сначала находим
   все физические зоны кладки (как они реально поданы в спецификации КР2 — по меткам, не по номеру
   этажа), потом раскладываем блоки/арматуру/перемычки по каждой найденной зоне.
3. Только после этого — adapter/калькулятор, как в P5.
