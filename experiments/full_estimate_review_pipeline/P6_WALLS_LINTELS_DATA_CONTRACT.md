# P6. Новый production contract для стен, перемычек и парапета

Дата: 2026-08-13. По аналогии с P5 (`P5_SLAB_DATA_CONTRACT.md`) — тот же принцип: зона вместо
фиксированного этажа. Основание — реальные чертежи КР2 всех 3 проектов (ТРЦ/АРК/ЮСВ), см. ниже.

**Важно по ЮСВ:** при любых проверках сметы ЮСВ использовать только лист
`АЛ 06.04 КР1,КР2 (ЕЧ)(ЮВ)КровТН`. Старые/черновые листы, включая `РС 29.04.26`, не являются
источником для P6-решений.

## Подтверждение на реальных документах (сделано перед этим планом, не гипотеза)

Проверила листы КР2 (второй структурный комплект — стены/кладка, отдельно от КР1 — фундамент/плиты)
на всех 3 проектах:

- **ТРЦ** (КР2, лист 8): «Спецификация стенового блока» — одна таблица, но каждая строка с явной
  меткой зоны: `1эт`, `2эт`, `вентканалы`, `парапеты1эт`, `парапеты2эт` (парапет разделён по этажу!).
  Рядом — «Спецификация расхода арм-ры на армирование стен», та же разбивка по зоне+толщине блока.
- **АРК** (КР2): отдельные ЛИСТЫ чертежа под каждую зону («Кладочный план парапета кровли»,
  «Кладочный план стен 2 этажа и парапетов...»), в каждом — своя таблица блока и арматуры, явно
  подписанная («Стены надстройки» / «Парапет» отдельными группами строк).
- **ЮСВ** (КР2, лист 15): «Спецификация по газобетонным блокам» — 4 отдельные подтаблицы:
  «...несущих стен 1-го этажа», «...перегородок 1-го этажа», «...несущих стен 2-го этажа»,
  «...парапетов кровли», каждая со своим объёмом блока и длиной арматуры.

Вывод: источник данных **уже зонирован** на всех 3 проектах — ровно так же, как плиты перекрытия
были зонированы по маркам до P5. Значит парсер может и должен извлекать стены так же, как теперь
извлекает плиты — по зонам, а не по фиксированному «1 этаж / 2 этаж».

## Важное отличие от плит: две вложенные сущности, не одна

У плиты зона самодостаточна (бетон+опалубка+утепление+балки+арматура одной плиты). У стен внутри
каждой зоны кладки есть ещё **перемычки** (над проёмами) — отдельная подсущность со своей
геометрией/арматурой/бетоном/опалубкой/утеплением, которая физически находится внутри той же зоны
кладки, но считается отдельно (U-блок перемычки vs монолитные — разные материалы и работы). Схема
должна отражать это как вложенный список, а не приравнивать зону кладки к зоне перемычек.

## Уточнение 2026-08-13: что общее на весь раздел, а что повторяется по зонам

Раздел стен — не «один раздел на зону», как у плит, а **одна секция с общей головой/хвостом +
список зон внутри**. Прошла построчно по ТРЦ и АРК, потом (после того как нашла у ЮСВ неправильный
лист — реальная полная смета лежит на листе `АЛ 06.04 КР1,КР2 (ЕЧ)(ЮВ)КровТН`, не на `РС 29.04.26`,
у которой нет серых колонок вообще) перепроверила и на ЮСВ тоже. Все 3 совпадают:

**Section-wide, один раз на весь раздел (НЕ внутри зон):**
- Леса, подмостья + пиломатериал для лесов — одна строка перед первой зоной.
- Расходные материалы (%), вывоз мусора, технадзор, 3 нулевые markup-строки — один блок после
  последней зоны.

**Повторяется в каждой зоне (обычные zone-scoped поля):**
- Кладка (объём работы), блоки по плотности, клей, штробление+арматура по диаметру,
  перемычки, если они относятся к этой зоне.

Организационные строки вроде доставки блоков, разгрузки и крана **не являются данными зоны из PDF**:
они создаются калькулятором позже по закупочному объёму/партиям поставки и не должны попадать в
parser targets.

**Опциональные zone-scoped поля — есть не у каждой зоны, и это нормально, не ошибка:**
- Перемычки (`lintel_items[]`) — у ТРЦ есть у КАЖДОЙ зоны кладки (льёт поэтажно). У АРК и ЮСВ —
  только у ОДНОЙ зоны (обычно первой/нижней), весь дом перемычками поэтажно не делится. Значит
  `lintel_items[]` пристёгнут к конкретному `zone_id` как обычное поле зоны — просто на практике
  у 2 из 3 проектов он будет заполнен только у одной зоны, у остальных пусто. Никакой специальной
  логики «перемычки относятся ко всему разделу» вводить не нужно — обычное опциональное поле зоны.
- Гидроизоляция под первый ряд блоков — сначала подумала, что это «на самом деле про всё здание»
  и предлагала отдельное section-wide поле. Пересмотрела: это гидроизоляция именно нижнего ряда
  блоков, значит нужна только той зоне, что реально стоит на плите/земле. У всех 3 проектов
  «второй свет»/«кухня-гостиная»/парапет — надстройки НА стенах, плиты не касаются, им это не
  нужно физически, не по случайности чертежа. Значит это тоже обычное опциональное поле зоны, а
  не section-wide — просто заполняется только у зоны, которая касается плиты (везде это первая
  зона, но это следствие физики, не жёсткое правило "всегда первая").
- Обкладка дымохода/вентканалов — есть только у `zone_kind: parapet` (там вентканалы выходят на
  крышу), у остальных зон нет.

**Вывод для схемы:** `wall_zones[]` — все специфичные под-блоки (`lintels`, гидроизоляция первого
ряда, обкладка дымохода) должны быть НЕОБЯЗАТЕЛЬНЫМИ полями зоны, без required-проверки «у каждой
зоны должно быть». Section-wide голова/хвост (леса, расходники/вывоз мусора/технадзор) — отдельные
поля на уровне всей секции, не внутри `wall_zones[]` вообще.

## Важно: без переходного режима и старых scalar-полей

P6 делается как новый production-контракт с чистого листа, а не как слой совместимости поверх
старого калькулятора. Нельзя оставлять в production два параллельных адреса для одних и тех же
данных (`main_wall_*` scalar + `wall_block_items[]`, `floor_1_lintel_*` + новые `lintel_items[]` и
т.п.). Именно такое смешивание уже дало тихий ноль по кладке стен в ТРЦ.

При этом «с чистого листа» означает **чистую модель данных**, а не переписывание проверенной
сметной математики заново. Отчёт
`reports/trc_vs_original_comparison/04_load_bearing_walls_lintels.md` показал, что после точечных
исправлений старый калькулятор уже почти повторил раздел стен ТРЦ:

- реальная себестоимость ТРЦ: 2 990 808 ₽;
- наша сборка после правок 2026-08-09: 3 015 189 ₽;
- расхождение: +24 381 ₽ / +0.82%;
- до исправлений расхождение было +308 307 ₽.

Значит главная проблема старого production-пути была не в формулах, а в смешанной форме входных
данных и маршрутизации: часть данных жила в старых scalar-полях, часть в repeated items, и
калькулятор мог молча выбрать не ту ветку. Самый опасный пример — ТРЦ, где `wall_block_items[]` был
не пустой из-за перегородок/парапета/верхних зон, а основные стены 1-го этажа остались только в
scalar-полях; старая логика «items есть -> scalar игнорируем полностью» дала тихий ноль по кладке
несущих стен.

**Правило для P6:** переписываем адреса данных и структуру раздела, но сохраняем проверенные
расчётные ядра старого калькулятора. Новый калькулятор должен быть новым по входной модели
(`wall_zones[]`, `block_items[]`, `lintel_items[]`, grouped rebar), но в формулах запасов,
округлений, закупки и коэффициентов он должен повторять уже проверенную сметную логику, кроме
мест, где ниже явно записано новое решение Елены или новая production-логика.

Проверенные ядра, которые надо перенести/переиспользовать:

1. Закупка газоблоков: проектный объём * 1.05, затем округление вверх до паллеты по типу блока.
2. Доставка блоков/смеси: по закупочному объёму партии, ориентир 32 м3 на машину; разгрузка равна
   числу машин.
3. Клей для блоков: считать от объёма кладки с тем же запасом/округлением, что уже совпадало с
   ТРЦ/АРК/ЮСВ.
4. Пескобетон/ЦПС под первый ряд: сохранить текущую методику, которая была исправлена и совпала с
   ТРЦ.
5. Штробление под арматуру стен/парапета: количество показывать, но работа в себестоимости = 0,
   потому что в эталонных сметах она включена в кладку или стоит нулевой строкой.
6. Арматура стен/перемычек/парапета: pooling по зоне, назначению, классу стали и диаметру; закупочное
   округление до хлыстов/прутков, как уже проверено на ТРЦ.
7. Бетон перемычек: материал считать в м3 с заказом/округлением, доставка бетона и ручной
   перенос/подъём создаются калькулятором рядом с бетонным блоком перемычек.
8. Бетонирование перемычек как работа: U-блоки и монолитные перемычки считать в м.п. по текущему
   прайсу; решение после ответа Елены — не возвращаться к старой м3-ставке для монолитных
   перемычек.
9. Опалубка монолитных перемычек: пиломатериал считать от фактической площади опалубки и толщины
   доски, а не подгонять под круглые старые числа смет.
10. Утепление монолитных перемычек: если проект даёт длину утепляемой части, считать работу по м.п.,
    материал ЭППС и клей-пену по текущей формуле/упаковке.
11. Леса/подмости, вывоз мусора, технадзор и коэффициентные хвостовые строки: сохранить как
    section-wide строки, с текущими подтверждёнными price_code/defaults.

Что запрещено переносить из старой реализации:

- `main_wall_*`, `floor_2_*`, `floor_1_lintel_*`, `floor_2_lintel_*` как production-входы;
- любые проверки вида «если вообще есть хоть один item, полностью игнорируем scalar-путь»;
- смешивание перегородок с несущими стенами;
- автоматическое деление парапета на несколько сметных зон только потому, что чертёж дал несколько
  подзон;
- старые цены из тестовых смет, если текущий прайс Елены уже даёт другое значение;
- старые выводы по ЮСВ из неправильных листов.

Порядок работ:

1. Новый калькулятор/новая внутренняя модель раздела.
2. Новый `section_contract.yaml`.
3. Новый adapter из review workbook в calculator input.
4. Новый вывод на лист 01 Google-таблицы.
5. Новые parser targets/schema/aliases/prompt.
6. Новый zip-пак и новый extraction-прогон.

Старые поля можно держать только в архивных тестах/diagnostic notes, но не как production fallback.

## Новая структура extraction JSON (по аналогии с `floor_slabs.slab_zones[]`)

```yaml
sections:
  load_bearing_walls_lintels:
    wall_zones:
      - zone_id: string        # "floor_1", "floor_2", "second_light", "parapet",
                                # "vent_chimney_cladding", ...
        display_name: string   # "Кладка стен 1-го этажа", "Парапет"
        zone_kind: main_walls | second_light | parapet | partitions | vent_chimney_cladding | other
        source_level: string | null
        include_in_estimate: true
        status: found | needs_review | missing
        source_refs: []
        masonry:
          block_items: []        # {block_density, thickness_mm, volume_m3, source_ref} — как в спецификации
          chasing_rebar_items: [] # штробление/порядовое армирование, по диаметру — та же схема,
                                   # что main_wall_rebar_items сейчас, просто zone_id вместо floor:int
        lintels:
          - lintel_id:
            lintel_kind: u_block | monolithic
            total_length_m:
            concrete_volume_m3:
            rebar_items: []
            formwork: {}
            insulation: {}
            groove_length_m:      # для partitions-зон
```

Правило `zone_id`, как в P5: если в проекте есть явная метка (ТРЦ: «парапеты1эт»/«парапеты2эт»;
АРК: «ПМ1»/«ПМ2») — использовать её как основу; если метки нет — нейтральный контекст (`floor_2`,
`vent_chimney_cladding`). НЕ вводить отдельное поле "номер этажа" как int нигде в схеме — весь смысл
"это не 1-й этаж, а что-то ещё" передаётся через `zone_id`/`zone_kind`, без привязки к числу.

## Уточнение 2026-08-13: парапет — ОДНА билинговая зона, несмотря на несколько зон в чертеже

Проверила реальные сметы всех 3 проектов напрямую (не только чертежи КР2) — важная поправка к
разделу выше. Хотя чертёж КР2 у ТРЦ даёт парапет ДВУМЯ отдельными зонами (парапеты1эт 5.94 м³ +
парапеты2эт 13.21 м³ = 19.15 м³), в реальной смете — **только одна секция «Парапет»**, и её объём
кладки (19.15 м³) — это ровно сумма обеих чертёжных зон. То же самое у АРК (две отдельные страницы
кладочного плана парапета в КР2, но одна секция «Парапеты» в смете) и у ЮСВ (там даже в чертеже
парапет не делится на этажи).

Значит: `zone_kind: parapet` — это **не отдельная зона на каждый этаж**, а ВСЕГДА одна билинговая
зона на весь проект, даже если внутри неё несколько физических подзон с разным объёмом. Схема
`wall_zones[]` должна это отражать так же, как P5 сделала со slab_zones — одна billing-зона
`parapet` с массивом `masonry.block_items[]` внутри (несколько строк объёма по подзонам/этажам,
как позволяет реальная спецификация), а не `parapet_floor_1`/`parapet_floor_2` как две отдельные
записи в `wall_zones[]`. Детализация по подзонам нужна только для проверки парсера (Stage 1,
zoo-строки) — то же двухэтапное разделение, что уже сделано для арматуры по диаметрам и сейчас для
ЭППС50+100 в гидроизоляции: Stage 1 = полная детализация для сверки с PDF, Stage 2 (сама смета) =
объединённые billing-строки.

Это касается только `zone_kind: parapet`. Для 1-го/2-го этажа основной кладки — наоборот, каждый
этаж остаётся своей отдельной billing-зоной (Елена держит их раздельными секциями во всех 3
сметах) — там дробление по этажам реальное и билинговое, не только чертёжное.

## Уточнение 2026-08-13: арматура в смете агрегируется по зоне и диаметру

Проверила реальные сметы ТРЦ, АРК и ЮСВ по разделу стен/перемычек. Во всех трех сметах арматура
показана не сырыми строками из PDF, а уже агрегированными сметными строками внутри своей зоны:

- для кладки зоны: одна нулевая строка штробления/армирования + одна строка материала A500/A500C
  Ø10;
- для перемычек зоны: одна нулевая строка «изготовление и монтаж каркаса...» + строки материала по
  диаметрам, например A500 Ø12, A500 Ø16, A240 Ø6;
- для парапета: отдельная нулевая строка штробления парапета + отдельная строка A500 Ø10 парапета.

То есть production-логика должна быть как у плит:

1. В Google-таблице показываем **все проектные строки арматуры справочно** в конце соответствующей
   зоны/раздела, серым цветом. Елена сверяет их с PDF, но не правит руками — если ошибка в арматуре,
   правку должен вносить проектировщик.
2. Для расчета внутри каждой зоны арматура агрегируется по `(zone_id, назначение, класс стали,
   диаметр)`, с закупочным округлением до хлыстов/прутков по тем же правилам, что уже применяются в
   калькуляторах плит.
3. В конце раздела можно показывать общий справочный итог арматуры по диаметрам/классам для
   контроля поставочного веса и доставки металла, но не дублировать эти строки как отдельные
   расчетные позиции, если они уже учтены в зонах.
4. Нельзя смешивать назначение арматуры: арматура кладки, арматура перемычек и арматура парапета
   агрегируются отдельно, даже если класс и диаметр совпадают.
5. Арматура перегородок не попадает в этот раздел вообще: она может быть сохранена как найденная
   справочная строка для будущего калькулятора перегородок, но не участвует в расчете несущих стен.

Это важная поправка к новой модели `wall_zones[]`: repeated-строки арматуры нужны для проверки и
для корректного pooling, но видимая сметная строка должна быть агрегированной, а не «одна строка PDF
= одна строка сметы».

### «Балки» — это не отдельная сущность для этого раздела

На чертеже АРК (лист 11, легенда) есть буквально 4 обозначения: красная толстая линия — «ж/б балка
**в теле плиты ПМ1**» (это балка ВНУТРИ плиты перекрытия, её место — `floor_slab_beam_items`,
уже есть, к стенам отношения не имеет вообще); зелёная — «ж/б балка **перемычка** ПБ» (буквально
одно и то же слово через дефис — это и есть монолитная перемычка, просто над широким проёмом её
называют то «балка», то «перемычка», не разделяя). В самой смете ТРЦ то же самое видно с другой
стороны: 1-й этаж называет эту строку «...армирования **перемычек**», 2-й этаж — «...армирования
**балок**» — то же самое действие, просто другое слово в тексте, не другая категория. **Вывод:
отдельная сущность «балки» в разделе стен не нужна — то, что иногда называют балкой, это и есть
монолитная перемычка (`lintel_kind: monolithic`) над широким проёмом.** Настоящие балки (внутри
плит перекрытия) уже покрыты `floor_slab_beam_items` в другом разделе — переделывать не нужно.

### Перемычки — типы задаются (толщина стены × способ), не просто "U-блок vs монолит"

На «Плане перемычек» у АРК/ТРЦ каждый проём промаркирован своим типом (ПР-1/ПР-2/ПР-3, ПБ-1/ПБ-2 у
АРК; ПР-1/ПР-2 у ТРЦ), и у каждого типа — своя спецификация арматуры/бетона/опалубки. По сути тип
= (толщина стены, в которой проём) × (способ: U-блок фабричный vs монолит по месту). У ТРЦ, кроме
того, есть третий вариант — просто пруток арматуры в штробе без бетонирования вообще (на плане
подписан отдельным цветом, без своей спецификации бетона) — по объёму денег незначимый (это просто
кусок арматуры, не отдельная работа), но для полноты картины в extraction стоит не терять эту
метку, а не пытаться классифицировать её как «U-блок» с нулевым бетоном.

**Практический вывод:** уровень детализации `lintel_kind: u_block | monolithic` (уже есть в этом
плане) — правильный для СМЕТЫ (Елена сама не делает разницы между ПР-1/ПР-2/ПР-3 в смете, там всё
уже свёрнуто до «перемычки в U-блоке» одной строкой + «монолитные перемычки» отдельной строкой).
Деление по промаркированным типам (ПР1/ПР2/ПР3/ПБ1/ПБ2) нужно только на Stage 1 (зоопарк для сверки
с PDF), не в самой смете — тот же принцип двух этапов, что уже применили к арматуре по диаметрам.
Перемычки остаются per-floor зоной (как в текущем плане) — оба проекта держат отдельные листы «План
перемычек 1/2 этажа», это реальное, не выдуманное деление.

### Перегородки — ОТДЕЛЬНЫЙ раздел сметы, вне скоупа этого плана (решение 2026-08-13)

Перегородки — своя секция сметы у всех проектов («КЛАДКА ПЕРЕГОРОДОК, ПЕРЕМЫЧКИ НАД ПРОЕМАМИ»), не
подраздел стен. Своего калькулятора под неё пока нет — делать её сейчас не будем, весь план выше
(`wall_zones[]`, `lintel_items[]`) — только про `load_bearing_walls_lintels` (несущие стены,
1эт/2эт/парапет), перегородки туда не входят.

Парсер уже умеет находить объём/арматуру перегородок отдельно (`wall_block_items` с
`wall_role=partitions`) — это нормально, пусть находит, пригодится для будущего калькулятора. Но
`load_bearing_walls_lintels_calculator.py` уже проверила напрямую — он защищён от смешивания:
арматура с `component="partitions"` вызывает жёсткую ошибку («must be calculated in partitions
calculator, not in load_bearing_walls_lintels_calculator», строка 583), а объём блоков перегородок
захватывается (`partitions_captured_volume_m3`) но сознательно НЕ оценивается в деньгах (решение от
2026-07-20). То есть даже если парсер найдёт перегородки, в сумму раздела несущих стен они не
попадут — путаницы нет, можно не бояться при переделке P6.

### Уточнение по ЮСВ и перегородкам (не блокирует P6)

У ТРЦ и АРК «КЛАДКА ПЕРЕГОРОДОК, ПЕРЕМЫЧКИ НАД ПРОЕМАМИ» — отдельный раздел сметы (не подраздел
стен), со своими особенностями: кладка меряется в **м²**, не м³ (толщина 100/150мм даётся отдельным
множителем в описании работы, не как параметр объёма) — другая единица измерения, чем у несущих
стен. Перемычки над проёмами В ПЕРЕГОРОДКАХ — только штробление+арматура (уже зафиксировано ранее
как [[lintel_groove_partitions_and_insulation_note]]), никогда не льются как U-блок или монолит —
для перегородки это не нужно конструктивно (лёгкая ненесущая стена).

Для ЮСВ любые проверки сметы выполнять только по листу `АЛ 06.04 КР1,КР2 (ЕЧ)(ЮВ)КровТН`. Старый
лист `РС 29.04.26` не использовать как источник для P6-решений. На уровне P6 вывод всё равно тот же:
перегородки не входят в раздел несущих стен/перемычек и должны уйти в отдельный будущий калькулятор
перегородок. Если parser находит перегородки в проекте, он сохраняет их как отдельную сущность для
будущего раздела, но P6-калькулятор несущих стен не должен оценивать их деньгами и не должен мешать
их с несущими стенами.

## Роли — из фиксированного enum в открытый список

`WALL_BLOCK_ITEM_ROLES = {main_walls, floor_2, parapet, partitions}` — заменить на открытый список
зон/сущностей. Обоснование не гипотетическое: в проектах встречаются не только `main_walls` и
`floor_2`, но и парапет, обкладка вентканалов/дымохода, перегородки для будущего отдельного раздела
и другие подписи спецификаций. При этом `parapet` для сметы — одна billing-зона, даже если PDF
даёт несколько физических подзон; эти подзоны должны жить как строки внутри `parapet`, а не как
несколько отдельных сметных зон. Обкладка вентканалов/дымохода может иметь собственный блок/толщину
(ТРЦ КР2 л.8: D500 150мм, 0.66 м³, своя строка в спецификации) — этот объём старый калькулятор
сейчас вообще не читает, это реальный пробел, не запасной случай на будущее.

## Перемычки — та же унификация

Сейчас: `floor_1_lintel_*` / `floor_2_lintel_*` — 12+ отдельных scalar-полей, дублирующих друг друга
по имени один в один под каждый этаж (`floor_1_lintel_monolithic_concrete_volume_m3` /
`floor_2_lintel_monolithic_concrete_volume_m3` и так далее). Перевести на `lintel_items[]` с
`zone_id` (ссылка на `wall_zones`) + `lintel_kind` — одна схема полей для любой зоны, без
дублирования имени поля под каждый этаж. Заодно закрывает найденную в отчёте v2 несостыковку
(1-й этаж — одна строка бетонирования U-блок+монолит вместе, 2-й этаж — две строки у самой Елены):
с явным `lintel_kind` на каждой позиции это будет видно из данных, а не угадываться кодом.

## Организационные строки: не parser targets и не лист 01-1

Ранний вариант плана предполагал сделать кран/доставку per-zone manual fields. Это отменено. Для
стен/перемычек такие строки не приходят из проекта как расчетные параметры и не должны попадать на
лист 01 или 01-1.

Production-решение:

- кран блоков/смеси, доставка блоков/смеси и разгрузка манипулятором создаются калькулятором по
  закупочному объёму блоков/клея;
- доставка бетона до объекта и ручной перенос/подъём бетона создаются калькулятором при наличии
  бетона перемычек;
- если Елена хочет поправить организацию работ, она правит уже готовую смету, а не extraction
  workbook;
- parser/prompt/contract не должны требовать эти строки как найденные в PDF.

## Google workbook (лист 01) после переделки

Цель листа 01 — не показать внутреннюю модель калькулятора, а дать Елене нормальную человеческую
проверку извлечённых из проекта данных. После переделки плит мы уже поймали антипример: структура
данных стала правильнее, но лист 01 на время превратился в кашу из зон, технических названий и
сводных строк вроде «Высота: ...; Бетон: ...». Для P6 это нельзя повторять.

Эталон интерфейса — текущий хороший вид листа 01 после финальной правки плит:

- один проверяемый параметр = одна строка;
- колонка A: понятное русское название того, что проверяем;
- колонка B: одно значение, которое модель нашла в проекте;
- колонка C: единица измерения;
- дальше статус, уверенность, что нужно сделать, источник, фрагмент проекта, комментарий Елены;
- технические колонки справа не считаются интерфейсом для Елены и не должны быть нужны для проверки
  глазами;
- никаких строк, где в одной ячейке смешаны несколько чисел (`длина; ширина; высота; бетон; опалубка`);
- если объект имеет несколько параметров, он разворачивается построчно:
  `перемычка/балка/зона — длина`, `... — бетон`, `... — опалубка`, `... — утепление`, и т.д.;
- если параметр можно исправить в review workbook, исправление относится именно к этой строке и
  именно к этому числу, а не к JSON-объекту целиком;
- серой делаем только арматуру и полностью диагностические/нерасчётные блоки;
- арматура всегда справочная и серая: Елена её не правит руками, при ошибке сообщает проектировщику;
- балки, перемычки, зоны, вентканалы и другие проектные параметры, которые влияют на расчёт, не
  серые: они остаются зелёными/оранжевыми/красными и должны позволять править конкретное число;
- если диагностическая/справочная таблица пустая, её не показываем вообще;
- расчётные project values окрашиваются зелёный/оранжевый/красный;
- строки `Не требуется / условно отсутствует`, `diagnostic/reference-only`, `show_to_user: false`
  скрываются, если это не заполненная справочная таблица.

Практическое правило для миграции P6: перед тем как переписывать вывод стен, сохранить старый
понятный вид раздела стен как образец. Новый вариант лучше делать рядом/отдельным режимом до тех
пор, пока он не станет таким же читаемым:

- не ломать старый production-вывод стен одним большим переписыванием;
- сначала собрать новый P6-лист 01 рядом и сравнить визуально со старым: порядок зон, названия,
  цвет, количество строк, отсутствие технических заголовков;
- только после проверки на ТРЦ/АРК/ЮСВ подключать новый вывод вместо старого;
- если новый `wall_zones[]` удобен коду, это не означает, что его надо показывать Елене как
  технический JSON. На листе 01 зоны должны выглядеть как обычные сметные подблоки:
  «Кладка стен 1-го этажа», «Кладка стен 2-го этажа», «Парапет», «Обкладка вентканалов».

```text
Кладка и перемычки

    блоки/объём (по плотности)
    штробление + арматура (арматура справочно, серым, по строкам PDF; расчет агрегирует по диаметру)
    перемычки (U-блок / монолит), каждая со своими полями
  Кладка стен 2-го этажа
```

Цвета — как в P5: расчётные project values зелёный/оранжевый/красный. Серой делаем арматуру,

## Уточнение 2026-08-13: кран/доставка блоков — расчет калькулятора, не parser/manual sheet

Проверка смет ТРЦ, АРК и ЮСВ показала устойчивое правило для перемещения блоков/смеси автокраном:

- ТРЦ: 1-й этаж — 3 машины доставки блоков -> 1 смена крана; 2-й этаж — 3 машины -> 1 смена;
  парапет -> 1 смена.
- АРК: 1-й этаж — 4 машины -> 2 смены; надстройка 2 света — 2 машины -> 1 смена; парапеты ->
  1 смена.
- ЮСВ: 1-й этаж — 5 машин -> 2 смены; парапет -> 1 смена.

Вывод для P6:

1. Кран блоков/смеси **не является parser target**: проект обычно не даёт организацию работ по
   сменам крана.
2. Кран **не должен появляться на листе 01**: лист 01 показывает данные из проекта/парсера, а не
   сметные организационные default-строки.
3. Кран **не должен жить в заранее созданном manual values листе 01-1**, потому что зоны кладки
   динамические и заранее неизвестно, сколько их будет.
4. Кран создаётся калькулятором уже при сборке готовой сметы:
   - для обычной зоны кладки: `ceil(block_delivery_trucks / 3)`, минимум 1 при положительном объёме
     блоков/смеси;
   - для парапета: 1 смена при наличии кладки парапета или обкладки вентканалов, потому что доставка
     парапета часто включена в соседнюю доставочную строку, а кран в сметах стоит отдельной строкой;
   - если в зоне нет блоков/смеси — 0.
5. Если Елене нужно поправить кран, она правит уже **готовую смету**, не лист 01 и не 01-1.

Доставка блоков/смеси и разгрузка манипулятором тоже не должны быть parser target, если в проекте
нет таких строк. Они рассчитываются калькулятором по закупочному объёму блоков/клея. Разгрузка по
трем сметам равна количеству машин доставки блоков. Доставка может покрывать несколько соседних зон
одной строкой (например, «в т.ч. парапеты»), поэтому P6 не должен требовать отдельную доставку на
каждую физическую подзону.

Закупка газоблоков по всем трем сметам считается одинаково:

```text
расчетное_количество_паллет = проектный_объем_блока_м3 * 1.05 / объем_паллеты_м3
закупочный_объем_блока_м3 = ceil(расчетное_количество_паллет) * объем_паллеты_м3
```

Проверенные паллетные объемы из смет:

- D400 600x400x250: примерно 2.15-2.16 м3/паллета;
- D500 600x250x250: 1.8 м3/паллета;
- D500 600x150x250: 1.8 м3/паллета.

Доставка блоков/смеси считается партиями поставки (`block_delivery_batches[]`), а не строго по
каждой кладочной зоне:

```text
машины_доставки_партии = ceil(сумма_закупочного_объема_блоков_партии_м3 / 32)
разгрузка_партии = машины_доставки_партии
```

`32 м3` — расчетная вместимость машины по трем сметам. Это видно прямо в формулах:

- ТРЦ, 1 этаж: `(58.05 + 28.8) / 32 = 2.71` -> 3 машины.
- АРК, 1 этаж: `(79.92 + 37.8) / 32 = 3.68` -> 4 машины.
- ЮСВ: одна партия на блоки раздела `(83.85 + 32.4 + 15.05 + 23.65 + 3.6) / 32 = 4.95`
  -> 5 машин.

Production default для группировки партий:

1. Основная нижняя кладка (`main_walls` нижнего уровня) — отдельная партия.
2. Верхняя/надстроечная кладка + парапет + обкладка вентканалов — одна общая партия, если они
   фактически идут рядом в сметной секции. В названии сметной строки можно оставить человеческую
   пометку «в том числе для парапета», как у Елены.
3. Если проект/сметная структура явно показывает одну общую поставку на весь раздел, калькулятор
   может объединить все закупочные объемы в одну партию.

Это именно calculator default для готовой сметы. На лист 01 такие партии не попадают как parser
values: в проекте их обычно нет, и Елена проверяет/правит организацию поставки уже в готовой смете.

## Уточнение 2026-08-13: доставка бетона внутри блока перемычек

Не писать в смете строку «доставка бетона для перемычек» — у Елены такой строки нет. В реальных
сметах ТРЦ, АРК и ЮСВ строка называется просто:

```text
Доставка бетона до объекта
```

Но по расположению и смыслу она стоит внутри бетонного блока перемычек: рядом со строками
«Бетон марки В22,5 (М300)» и «Перенос, подъем бетона вручную».

Правило P6:

- если в зоне есть бетон для перемычек в U-блоке и/или монолитных перемычек, калькулятор выводит
  рядом три строки:
  - «Бетон марки В22,5 (М300)»;
  - «Доставка бетона до объекта»;
  - «Перенос, подъем бетона вручную»;
- название строки доставки остается дословно как у Елены: «Доставка бетона до объекта»;
- это не parser target, если такой организационной строки нет в проекте; калькулятор создает её
  по наличию положительного заказа бетона в перемычках;
- если бетона перемычек в зоне нет, этот бетонный блок не выводится.
