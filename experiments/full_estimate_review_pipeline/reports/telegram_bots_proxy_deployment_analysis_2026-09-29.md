# Отчёт по Telegram-ботам, прокси и миграции транспорта

Дата проверки: 29.09.2026.

## 1. Краткий вывод

На клиентском сервере работают три разных Telegram-бота, но их Telegram-слой
реализован не одинаково:

- `snab_bot` и `photo_bot` используют `python-telegram-bot`, `HTTPX` и нативный
  `HTTPXRequest` с SOCKS5;
- ИИ-сметчик `calc` переведён с `pyTelegramBotAPI` на тот же стек:
  `python-telegram-bot 22.7`, `HTTPX 0.28.1`, `socksio 1.0.0`;
- миграция выполнена в commit `d24d3e2`, 19 локальных тестов проходят;
- новый PTB-код установлен на сервер и запущен через рабочий HTTP-прокси:
  `calc.service` имеет `active`, `NRestarts=0`, журнал содержит
  `Application started`;
- через SOCKS5 новый PTB-клиент получает `socksio ProtocolError: Malformed reply`
  уже во время SOCKS-аутентификации, до запроса Telegram;
- проблема ограничена транспортным Telegram-слоем ИИ-сметчика. Парсеры, расчётные
  модули, Google Sheets, Google Drive и сборка Excel от неё не зависят.

Текущий рабочий production-вариант ИИ-сметчика временно оставлен на HTTP-прокси.
Требуемая директором кодовая миграция на PTB выполнена; для окончательного перехода
на SOCKS5 нужен отдельный доступный endpoint либо подтверждение и снятие ограничения
текущего прокси.

После технической проверки получена дополнительная позиция техподдержки поставщика
прокси: **«Не используйте протокол SOCKS5 для работы с Телеграм из РФ»**. Поэтому
до уточнения физической площадки сервера и требований директора переходить на
SOCKS5 не следует, даже несмотря на работу через него двух существующих ботов.

### 2.1. Предварительная проверка местонахождения сервера

Публичный IP сервера `201.24.123.138` проверен 29.09.2026 по нескольким сетевым
источникам:

- IPWhois определяет страну как Российскую Федерацию, город как Москву и сеть как
  `AS9123 JSC TIMEWEB`;
- IPinfo также определяет Россию, Москву и `AS9123 JSC TIMEWEB`;
- DB-IP определяет Россию и Москву;
- RIPEstat показывает, что маршрут `201.24.123.0/24` объявляется автономной системой
  `AS9123`;
- PeeringDB подтверждает принадлежность `AS9123` компании JSC TimeWeb и наличие у
  неё площадок как в России, так и за рубежом.

Совпадение GeoIP-баз и маршрута даёт высокую вероятность, что для сетевых ограничений
сервер следует считать российским. Однако GeoIP и ASN не доказывают физический адрес
оборудования: провайдер может маршрутизировать адрес через другую площадку или
использовать зарубежный дата-центр.

Физическая площадка сервера на момент составления отчёта **уточняется директором по
договору с хостинг-провайдером**. До получения ответа рабочее допущение для Telegram:
сервер находится в РФ, следовательно, рекомендация техподдержки прокси относится к
этому деплою.

## 3. Как написаны работающие боты

### 3.1. Общая схема

Оба существующих бота используют одинаковый сетевой стек:

```text
python-telegram-bot 22.7
    -> HTTPXRequest
        -> HTTPX 0.28.1
            -> socksio
                -> SOCKS5-прокси
                    -> Telegram Bot API
```

Прокси передаётся средствами самой библиотеки `python-telegram-bot` отдельно для
обычных запросов и для получения обновлений. То есть и отправка сообщений, и
долгий запрос `getUpdates` работают через один предусмотренный библиотекой
SOCKS-транспорт.

Оба бота используют один и тот же SOCKS5 endpoint и одинаковые реквизиты доступа.
На момент проверки оба сервиса были `active`, а их процессы имели установленные
TCP-соединения с прокси.

### 3.2. Особенность конфигурации

В существующих ботах адрес и реквизиты прокси зашиты непосредственно в исходный
код. Такая схема работоспособна, но для ИИ-сметчика копировать её буквально не
следует: секреты должны оставаться в закрытом environment-файле с правами `600`,
а не попадать в Git и production-архив.

Для ИИ-сметчика повторён **сетевой механизм** работающих ботов, но сохранён более
безопасный способ хранения реквизитов.

## 4. Как написан ИИ-сметчик

### 4.1. Происхождение текущей библиотеки

`pyTelegramBotAPI` появилась в самом первом Telegram-коммите от 22.06.2026:

```text
1c64260 feat(bot): add Telegram polling bot for earthworks MVP (Шаг 8)
```

Первоначальная версия создавалась как быстрый MVP одного раздела, занимала 371
строку и выполняла несколько простых действий: принимала PDF, запускала внутренние
скрипты и отвечала на команды. В требованиях того этапа не было клиентского
сервера, обязательного SOCKS5 и совместимости с уже работающими ботами.

Для такого прототипа `pyTelegramBotAPI` была удобна простым синхронным API и
декораторами обработчиков. Затем MVP вырос, но библиотека осталась прежней.

### 4.2. Устройство до миграции

Сейчас Telegram-файл ИИ-сметчика содержит 2898 строк и 21 обработчик сообщений и
команд. В нём реализованы:

- приём документов и extraction JSON;
- пользовательские сессии и job;
- публикация промежуточной таблицы в Google;
- запуск сборки итогового Excel;
- отправка файлов пользователю;
- проверка прав пользователя и администратора;
- административные команды, события и выгрузка логов;
- восстановление сессий и повторный запуск polling после сетевых ошибок.

Сетевой стек до commit `d24d3e2` выглядел так:

```text
pyTelegramBotAPI 4.36.0
    -> requests 2.34.2
        -> PySocks 1.7.1
            -> HTTP- или SOCKS5-прокси
                -> Telegram Bot API
```

Параметры прокси читаются из закрытого `calc.env`. Код валидирует схему, адрес,
порт и полноту реквизитов, URL-кодирует логин и пароль и не выводит их в обычные
логи.

### 4.3. Устройство после миграции

Production-стек ИИ-сметчика теперь совпадает с двумя известными ботами:

```text
python-telegram-bot 22.7
    -> HTTPXRequest
        -> HTTPX 0.28.1
            -> socksio 1.0.0
                -> HTTP- или SOCKS5-прокси
                    -> Telegram Bot API
```

Существующие 21 синхронный обработчик сохранены. PTB принимает обновления в своём
asyncio event loop, а длительные операции ИИ-сметчика выполняются в рабочих потоках,
чтобы subprocess, Google API и сборка Excel не блокировали polling. Отправка ответов,
скачивание документов и отправка Excel возвращаются в event loop PTB.

Для обычных запросов и `getUpdates` создаются отдельные штатные `HTTPXRequest`.
Успешные HTTPX request-логи подавлены, а токен и полный proxy URL фильтруются из
корневых журналов. Реквизиты по-прежнему находятся только в закрытом `calc.env`.

### 4.4. Почему это не ошибка расчётной системы

Telegram-слой только принимает файлы и команды, затем запускает уже существующие
скрипты. Он не содержит формул калькуляторов и не определяет содержание сметы.

Переход на другую Telegram-библиотеку не требует переписывать:

- парсинг проектной документации;
- семь готовых расчётных разделов;
- интеграцию Google Sheets и Google Drive;
- генерацию итогового Excel;
- правила формирования левой и правой частей сметы.

## 5. Что именно проверили с SOCKS5

### 5.1. Проверка штатного транспорта `pyTelegramBotAPI`

При подключении ИИ-сметчика к SOCKS5 через штатную связку `requests/PySocks`
Telegram-запрос завершился ошибкой о некорректных данных от SOCKS5-сервера.

Это не доказывает, что сам прокси неисправен: через него одновременно продолжали
работать два других бота с другим сетевым клиентом.

### 5.2. Проверка временного HTTPX-транспорта

Для `calc` временно был подготовлен HTTPX/SOCKS-транспорт, приближенный к механизму
работающих ботов.

Результат состоял из двух разных этапов:

1. Изолированный короткий запрос `getMe` прошёл: Telegram вернул HTTP 200 и
   `ok=true`.
2. После включения постоянного polling стартовый запрос получил
   `socksio ProtocolError: Malformed reply`.

Первый результат подтверждает, что сервер может дойти до Telegram через этот
SOCKS5. Второй показывает, что временная прослойка между `pyTelegramBotAPI` и
`HTTPX` не обеспечивает надёжную работу продолжительных запросов.

После ошибки эксперимент был полностью отменён:

- исходный Telegram-транспорт восстановлен из резервной копии;
- экспериментальные зависимости удалены из `.venv`;
- конфигурация `calc` возвращена на HTTP-прокси;
- перезапущен только `calc.service`;
- `snab_bot` и `photo_bot` остались активными и не изменялись.

### 5.3. Результат полноценной миграции на PTB

После решения директора использовать SOCKS5 выполнена полноценная замена Telegram-
транспорта, а не временная HTTPX-прослойка:

- `pyTelegramBotAPI` и `PySocks` исключены из production requirements;
- добавлен `python-telegram-bot[socks]==22.7`;
- версии PTB, HTTPX и socksio совпадают с действующими ботами;
- SOCKS URL `snab_bot`, `photo_bot` и `calc` сравнен побайтно через SHA-256 без
  вывода реквизитов: все три значения совпадают;
- отдельный серверный PTB `getMe` через текущий SOCKS5 всё равно получил
  `ProtocolError('Malformed reply')` на этапе SOCKS-аутентификации;
- тот же PTB-код через HTTP успешно выполнил `getMe` и запустил постоянный polling.

Во время диагностики обнаружены три уже установленных TCP-соединения к SOCKS5:

1. `photo_bot.service`, PID 560;
2. `snab_bot.service`, PID 1517376;
3. отдельный процесс `python3 bot.py`, PID 578, рабочая папка `/root/photobot`,
   cgroup `cron.service`.

Третий процесс не относится к `photo_bot.service`, но использует тот же SOCKS5.
Он не останавливался и не изменялся. Наличие трёх занятых соединений и отказ нового
на аутентификации делает лимит одновременных SOCKS-сессий наиболее вероятной причиной,
но это остаётся гипотезой до подтверждения поставщиком прокси или директором.

### 5.4. Повторное побайтовое исследование SOCKS5

После сообщения поставщика об отсутствии лимита выполнена отдельная проверка без
Telegram-библиотеки и без Telegram-токена. С сервера был открыт обычный TCP-сокет
к proxy endpoint, после чего отправлено стандартное приветствие SOCKS5:

```text
05 01 02
```

Это означает: SOCKS версии 5, один предложенный метод, авторизация по логину и
паролю. TCP-соединение установилось, пакет был отправлен, но прокси не вернул ни
одного байта. Через 10 секунд клиент получил `TimeoutError`. Следовательно:

- проверка логина и пароля ещё не начиналась;
- команда соединения с `api.telegram.org` ещё не отправлялась;
- Telegram-токен и код обработчиков не участвовали;
- ошибка возникла между сервером и SOCKS endpoint на первом шаге протокола.

Стандартный `curl` подтвердил тот же результат: SOCKS5-подключение завершилось
с кодом `28` (`Connection timed out after 10001 milliseconds`). При этом тот же
адрес, порт и реквизиты в режиме HTTP proxy успешно вернули HTTP `302` от
`api.telegram.org` примерно за две секунды.

Ранее `HTTPX/socksio` также выдавал `ProtocolError('Malformed reply')`. Эти ошибки
не противоречат друг другу: в разных попытках SOCKS endpoint либо не ответил совсем,
либо вернул данные, которые не соответствовали ожидаемому сообщению SOCKS5. Обе
ошибки произошли до TLS и до Telegram Bot API.

Возраст работающих процессов на момент проверки:

- `photo_bot.service` и отдельный cron-процесс `/root/photobot/bot.py` работают с
  10.07.2026 без перезапуска;
- `snab_bot.service` запущен 29.09.2026 в 00:05 UTC;
- все три держат установленные TCP-соединения к одному endpoint;
- новое SOCKS5-приветствие вечером 29.09.2026 осталось без ответа.

## 6. В чём техническая проблема

Проблема не сводится к неверно введённому адресу или порту. Один и тот же endpoint
ведёт себя по-разному в зависимости от сетевого клиента и характера запроса.

Различие библиотек после миграции устранено:

| Параметр | `snab_bot` / `photo_bot` | `calc` |
|---|---|---|
| Telegram-библиотека | `python-telegram-bot 22.7` | `python-telegram-bot 22.7` |
| HTTP-клиент | `HTTPX 0.28.1` | `HTTPX 0.28.1` |
| SOCKS-реализация | `socksio 1.0.0` | `socksio 1.0.0` |
| Поддержка прокси | нативный `HTTPXRequest` | нативный `HTTPXRequest` |
| Постоянный SOCKS5 polling | работает | не подтверждён |

Повторное сравнение исходного кода выявило одно отличие транспортной схемы:

- оба работающих бота создают один объект `HTTPXRequest` и передают один и тот же
  объект в `.request(...)` и `.get_updates_request(...)`;
- первая версия миграции `calc` создавала два объекта `HTTPXRequest`, то есть два
  отдельных пула соединений;
- `calc` приведён к схеме работающих ботов: теперь Bot API и `getUpdates` используют
  один объект `HTTPXRequest`; добавлен автоматический тест этого условия.

Оставшиеся различия не влияют на начальное SOCKS5-приветствие: синхронный адаптер
обработчиков `calc`, набор `allowed_updates`, значения HTTP-таймаутов, хранение
секретов в environment вместо исходного кода и использование отдельного venv.
Версии Python, PTB, HTTPX и socksio у `calc` и `snab_bot` совпадают.

Временная попытка встроить HTTPX под `pyTelegramBotAPI` решила один короткий
запрос, но добавила нестандартный слой совместимости. Этот слой должен был
правильно воспроизвести поведение `requests.Session` для всех методов Telegram,
загрузки и скачивания файлов, таймаутов и long polling. Ошибка постоянного polling
показывает, что такой адаптер нельзя считать production-решением.

После устранения различия с HTTPX-клиентами низкоуровневая проверка всё равно не
получает ответ на приветствие SOCKS5. Точная серверная причина не доказана. Нельзя
утверждать, что это лимит соединений: поставщик его отрицает. Но можно уверенно
утверждать, что текущий отказ происходит до запуска кода Telegram и должен
диагностироваться поставщиком по логам endpoint.

### 6.1. Текст для техподдержки прокси

```text
Здравствуйте. Проверяем SOCKS5 endpoint с сервера 201.24.123.138.

TCP-соединение с endpoint устанавливается. Затем клиент отправляет стандартное
приветствие SOCKS5 в hex: 05 01 02 (SOCKS5, username/password authentication),
но endpoint не возвращает ни одного байта. Через 10 секунд получаем TimeoutError.

Проверка стандартным curl:
curl --socks5-hostname <host>:<port> --proxy-user <login>:<password> https://api.telegram.org/
завершается с curl exit code 28: Connection timed out after 10001 milliseconds.

При этом тот же host, port и credentials как HTTP proxy работают: запрос к
https://api.telegram.org/ завершается успешно, HTTP 302 примерно за 2 секунды.

До проверки credentials и до команды CONNECT к Telegram SOCKS-обмен не доходит.
На этом же endpoint сохраняются три ранее установленных SOCKS5-соединения от
работающих процессов. Новые соединения TCP принимаются, но на SOCKS5 greeting
ответа нет.

Пожалуйста, проверьте серверные логи endpoint для source IP 201.24.123.138 и
подтвердите:
1. почему нет ответа 05 02 на greeting 05 01 02;
2. разрешены ли новые SOCKS5-сессии с этого source IP;
3. не переведён ли endpoint фактически в режим HTTP-only;
4. нет ли ограничения на число одновременно установленных соединений или сессий;
5. какой точный SOCKS5 host/port следует использовать для нового подключения.
```

## 7. Варианты решения

Порядок вариантов ниже следует рассматривать с учётом официального ответа
техподдержки прокси. Техническая возможность подключения через SOCKS5 сама по себе
не означает, что поставщик гарантирует его устойчивую работу с Telegram из РФ.

### Вариант 1. Перевести Telegram-оболочку на `python-telegram-bot`

**Выполнено в commit `d24d3e2` и установлено на сервер.**

Что меняется:

- создание Telegram application;
- регистрация 21 обработчика;
- получение и скачивание документов;
- отправка сообщений и файлов;
- запуск и остановка polling;
- вызовы Telegram API внутри обработчиков;
- подключение прокси через штатный `HTTPXRequest` и `get_updates_request`.

Что сохраняется:

- вся бизнес-логика job и сессий;
- каталоги и форматы файлов состояния;
- права пользователей и администраторов;
- внутренние subprocess-команды;
- Google и Excel;
- systemd-сервис и пользователь `calc`;
- реквизиты прокси в закрытом `calc.env`.

Плюсы:

- тот же проверенный стек, что уже работает на сервере;
- штатная поддержка SOCKS5 без самописного сетевого адаптера;
- меньше скрытых рисков в long polling, таймаутах и передаче файлов.

Минусы:

- это миграция Telegram-оболочки, а не изменение одной настройки;
- `python-telegram-bot` версии 22 использует асинхронную модель, поэтому каждый
  обработчик нужно адаптировать и проверить;
- перед production необходим полный регрессионный тест команд и файлового потока.

### Вариант 2. Дорабатывать собственный HTTPX-адаптер для `pyTelegramBotAPI`

Этот вариант позволяет оставить текущие декораторы и большую часть Telegram-файла,
но требует самостоятельно поддерживать совместимость двух библиотек.

Потребуется отдельно решить и проверить:

- long polling и разные виды таймаутов;
- повторное использование и закрытие соединений;
- загрузку PDF/JSON в Telegram;
- скачивание присланных документов;
- отправку итогового Excel и диагностических выгрузок;
- retries и обработку ошибок SOCKS-протокола;
- отсутствие токенов и реквизитов прокси в HTTPX-логах.

Этот путь выглядит меньше по объёму исходного изменения, но имеет больше скрытых
сетевых рисков. После уже полученной ошибки polling он не рекомендуется как
основной production-вариант и после миграции больше не нужен.

### Вариант 3. Оставить рабочий HTTP-прокси

Новый PTB-код `calc.service` сейчас работает через HTTP endpoint. Это временно
сохраняет доступность до выдачи отдельного SOCKS endpoint, увеличения лимита сессий
или решения директора по обнаруженному процессу PID 578.

## 8. Статус плана миграции

Шаги 1-6 и 9 выполнены. Шаг 7 остановлен внешним SOCKS-ответом, шаг 8 требует
пользовательского теста в Telegram.

1. Не менять работающий production-сервис до готовности новой реализации.
2. Отделить Telegram-вызовы от бизнес-логики небольшим интерфейсным слоем.
3. Подключить `python-telegram-bot` и штатный `HTTPXRequest` с SOCKS5 из environment.
4. Перенести 21 обработчик, сохранив тексты команд, права и форматы состояния.
5. Добавить автоматические тесты входящих команд, документов и исходящих файлов.
6. Локально проверить старый PDF-flow, новый JSON-flow и администраторские команды.
7. На сервере выполнить изолированные `getMe`, `sendMessage`, загрузку и скачивание
   файла, затем устойчивый polling.
8. Провести полный пользовательский маршрут:
   `/start` → JSON → Google Sheet → исправление → `/build` → итоговый `.xlsx`.
9. Сделать резервную копию текущего `calc`, переключить только `calc.service` и
   наблюдать журнал.
10. При любой регрессии вернуть текущую HTTP-версию; другие два бота не трогать.

## 9. Критерии готовности

Миграцию можно считать завершённой только при одновременном выполнении условий:

- `calc.service` работает через SOCKS5 и не входит в цикл перезапусков;
- polling устойчиво работает продолжительное время, а не только один `getMe`;
- `/start`, пользовательские и администраторские команды отвечают;
- JSON и документы принимаются и скачиваются;
- Google Sheet создаётся в папке проекта;
- `/build` собирает и отправляет итоговый Excel;
- восстановление сессий после перезапуска сохранено;
- в логах нет токена Telegram и реквизитов прокси;
- `snab_bot` и `photo_bot` не изменялись и продолжают работать.

## 10. Текущее безопасное состояние

На момент завершения исследования:

- `calc.service` — `active`, `enabled`, без цикла перезапусков;
- ИИ-сметчик использует рабочий HTTP-прокси;
- production использует новый PTB/HTTPX-транспорт из commit `d24d3e2`;
- два существующих бота работают через SOCKS5 и не были изменены;
- отдельно обнаружена старая cron-копия `/root/photobot/bot.py`, также занимающая
  SOCKS5-соединение; она не изменялась и не останавливалась;
- техподдержка прокси не рекомендует SOCKS5 для Telegram из РФ;
- сетевые базы указывают на Россию и Москву, а физическая площадка уточняется по
  договору с хостинг-провайдером;
- полный пользовательский production-маршрут ИИ-сметчика всё ещё необходимо
  проверить отдельно.
