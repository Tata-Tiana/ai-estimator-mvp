## 1. Баги сборщика — найдены и уже исправлены в исправленном JSON

### 1a. wall_block_items: два блока парапета схлопывались в один

`repeated_item_sheet_id()` (`populate_review_workbook_from_extraction.py`, ~строка 1339) строит
идентификатор строки для внутренней проверки листа 01 из фиксированного набора полей
(`zone_id`, `block_density`, `steel_class`, `diameter_mm` и т.п.) — **не включает `item_id` и
`volume_m3`**. Когда два реальных разных блока парапета (14,8 м³ со стр.20 КР2 и 8,2 м³ со стр.22,
«ПМ2») были записаны с одним и тем же `zone_id: "parapet"`, их идентификаторы совпали, и на лист 01
попало 4 строки вместо 5 → сборщик падал с `RuntimeError: Сборщик остановлен: лист 01 неполный`.

**Не код-фикс, а фикс JSON**: пользователь развела парапет на две зоны `parapet_pm1`/`parapet_pm2`
в исправленном JSON. Сборка прошла (`returncode 0`, `found: 94, needs_review: 8`). Сам код
(`repeated_item_sheet_id`) остаётся потенциально уязвимым для ЛЮБОГО будущего проекта с двумя
позициями `wall_block_items`, у которых совпадают zone_id+density+size, но разные item_id/объём —
это не исправлено на уровне кода, только обойдено на уровне данных этого проекта.

### 1b. schiedel_channel_items: строка ручного ввода терялась из-за `group_code: null`

Строка-заглушка «Модули Schiedel — ручной ввод количества» (нужна, потому что в PDF нет штук,
только метры) была помечена `needs_review: true`, но с `group_code: null` — сборщик не мог привязать
её ни к одной группе, и она физически не попадала в таблицу. Исправлено в JSON (`group_code:
"schiedel_channel_items"`) — теперь строка видна на листе 01 (строка 446 таблицы, «Проверьте
(needs_review)», пусто, ждёт ручного ввода).

Изначально показалось, что не хватает только арматуры Ø16/Ø14/Ø8 ростверка. При проверке контракта

Это решение принято раньше (2026-07-20/29), не новый баг — но по факту означает: **весь раздел
Елены «УСТРОЙСТВО РОСТВЕРКОВОГО ФУНДАМЕНТА»** (бетон, опалубка, мембрана Planter, арматура 6

## 10. Разбор инструкции ChatGPT по листу 01 (ручные поля) — 2026-08-28

Пользователь скачала пустую Google-таблицу и попросила ChatGPT (в том же чате, где парсили АРК)
разобрать лист 01 целиком и написать, что реально нужно заполнить вручную. Ниже — что из его ответа
подтвердилось при проверке кода/контрактов, что нет, и что с этим делать.

### 10.1. PLANTER (320 м²) и внутренние воронки (5 шт) — подтверждено, реальная архитектурная дыра

`membrane_area_m2` (`foundation_slab/section_contract.yaml`) и `internal_roof_drains_count`
(`flat_roof/section_contract.yaml`) — оба одиночные обязательные scalar-поля, разбивки по зонам у
них в схеме вообще нет. ПДФ даёт компоненты отдельно (ФП1=256+ФП2=64; Тип А=3+Тип Б=2 воронки) без
печатной строки «Итого» — по правилу «не выдумывать сумму, если проект её не печатает» извлечение
корректно оставило оба поля пустыми.

При этом у нас уже есть готовый прецедент для ровно такой ситуации — группа `slab_zones`
(`concrete_volume_m3` по зонам ФП1/ФП2, с автосуммированием вместо одиночного scalar). Идею ГПТ
(«показывать компоненты + одну сумму-подтверждение для калькулятора») стоит реализовать по этому же
образцу для membrane_area_m2 и internal_roof_drains_count — универсально, не только для АРК.

**Что делать:** для этого проекта — принять правки ГПТ (320 и 5) как есть, они верные. Отдельной
задачей на будущее — завести аналог `slab_zones` для PLANTER и для воронок (не только для этого
проекта, универсально).

### 10.2. Бетононасос 1 смена — подтверждено, не выдумка ГПТ

В коде (`populate_review_workbook_from_extraction.py`) уже зашита подсказка: «⚠️ОБЯЗАТЕЛЬНО
заполнить. Формулы нет, но на всех проверенных плитах (ТРЦ/АРК/ЮСВ, 8 из 8) — ровно 1 смена».
ГПТ просто процитировал уже существующую рекомендацию. **Что делать:** принять как есть.

### 10.3. ПБ1/ПБ2 «Опалубка» — реальная находка, но не денежный баг

ПДФ (КР2 стр.11) даёт ОДНУ площадь опалубки на перемычку (ПБ1: 2,10 м², ПБ2: 1,83 м²), без деления
на горизонтальную/вертикальную. Схема `lintel_items` требует оба поля отдельно
(`formwork_horizontal_area_m2` + `formwork_vertical_area_m2`).

Проверила калькулятор (`load_bearing_walls_lintels_p6_calculator.py`, ~строка 502) — эти два поля
просто **складываются** при расчёте стоимости, оба по умолчанию 0.0. ГПТ положил всю площадь в
горизонтальную, вертикальную оставил пустой — **итоговая сумма для расчёта уже верна** (2,10 м²,
как в PDF), деньги не теряются. Проверила `build_input.py` — там нет никакой обязательной проверки
на этот случай (пустое поле просто отбрасывается `_drop_blank_values`, сборка не падает).

Единственная реальная проблема — `formwork_vertical_area_m2` не в списке полей, которые разрешено
оставлять пустыми без пометки (`FIELD_NEVER_MONEY_RELEVANT_WHEN_EMPTY`), поэтому лист 01 покажет
пустую вертикальную опалубку как «требует внимания» (needs_review-подобная пометка), хотя по факту
там нечего вписывать — Елена может решить, что чего-то не хватает, хотя всё уже верно.

**Что делать:** для этого проекта — ничего страшного, можно спокойно собирать смету, сумма верна.
На будущее — либо добавить `formwork_total_area_m2` как альтернативное поле для перемычек с одной
общей площадью опалубки, либо добавить `("lintel_items", "formwork_vertical_area_m2")` в список
`FIELD_NEVER_MONEY_RELEVANT_WHEN_EMPTY`, когда горизонтальная уже заполнена — не срочно, не блокер.

### 10.4. ЭППС 50мм кровли (2,7 м³) — ГПТ ОШИБСЯ, это не баг

ГПТ назвал это «реальной недоработкой связки таблицы с JSON» — не так. Поле
`eps50_supplier_required_volume_m3` сознательно исключено из извлечения решением от 2026-08-05:
*«не универсальный слой кровли (есть не на всех проектах), и даже там, где есть, реальное число
сметчицы смешивает площадную часть с добавленными вручную константами — нельзя чисто извлечь из
PDF»* — та же категория, что и SLOPE-плиты (только по КП поставщика, никогда из архитектурного PDF).

То, что 2,7 м³ лежит рядом в `roof_raw_material_spec_rows` — это архитекторская спецификация, а не
то число, которое реально нужно калькулятору (оно может отличаться от факта монтажа по КП).

**Что делать:** НЕ использовать правку ГПТ «2,7» для этого поля — вписать туда можно только реальное
число из КП поставщика. Если КП сейчас нет под рукой, оставить поле пустым/уточнить у Елены, а не
подставлять архитекторскую цифру под видом «нашли».

### 10.5. Остальные ручные поля — подтверждено, ничего нового

Schiedel в штуках) — все это уже известные «только по КП поставщика» поля, ничего не упущено, ничего
