# Шаг 28 — план доведения JSON/записки до production review workbook

Дата: 2026-08-02

Статус: план работ после свежего прогона ТРЦ.

Важно: текущий рабочий сценарий парсинга — **один chat prompt** из `experiments/chat_extraction_poc`.
Эксперимент `four_step_parsing_test` закрыт и в этом шаге не трогается.

## Зачем нужен этот шаг

После свежего прогона ТРЦ стало понятно: chat extraction уже неплохо читает проект и честно
показывает сомнения, но наш production pipeline еще не умеет нормально превращать такой JSON
в удобную Google review table и надежную служебную записку.

Human audit:

```text
experiments/chat_extraction_poc/reports/trc_json_and_memo_human_audit_2026-08-02.md
```

Проверочные отчеты:

```text
experiments/chat_extraction_poc/reports/trc_validation_report_2026-08-02.md
experiments/chat_extraction_poc/coverage_audit/trc_coverage_report_2026-08-02.md
experiments/chat_extraction_poc/coverage_audit/trc_service_memo_report_2026-08-02.md
```

Главная мысль: проблема уже не только в prompt. Prompt стал достаточно осторожным, чтобы находить
и подсвечивать противоречия. Теперь надо подтянуть schema, validator, review workbook и служебную
записку так, чтобы они умели принимать реальные проектные структуры.

## Что считаем успехом

- Google review workbook по реальному JSON показывает не только найденные значения, но и все сомнения.
- Лист `01_Проверка проекта` не содержит пустых бесполезных колонок и показывает confidence.
- Служебная записка или отдельный автоматически собранный отчет выводит все `needs_review` и важные `notes`.
- Сложные строки проекта не теряются: зоны плит, балки, траншеи, кровельные зоны, компоненты сумм.
- Код не подгоняется под ARK/TRC/USV и не содержит проектных чисел как business logic.
- Четко видно, что можно отправлять в калькулятор, а что должно остановиться на проверке.

## Строгое правило универсальности

На каждом шаге проверять:

- [ ] нет новых правил вида "если проект ТРЦ/АРК/ЮСВ";
- [ ] нет захардкоженных объемов, площадей, длин или цен конкретного проекта;
- [ ] проектные числа могут быть только в test fixture, output/report или примере, но не в универсальном коде;
- [ ] если добавляется автосумма, она описана как универсальное правило по структуре данных, а не по названию дома;
- [ ] если поле не найдено, код не подставляет значение из старой сметы.

## Шаг 28.5. Разобраться с `mixed` для сложных строк

Валидатор дал много предупреждений по `normalized_unit: mixed`. Это возникает в строках, где
одна repeated row содержит несколько разных чисел: длину, ширину, объем, количество.

Примеры:

- траншеи;
- beam_items;
- roof_zones;
- raw rows с несколькими колонками.

Что сделать:

- [ ] Решить формат для complex rows:
  - либо разрешить `normalized_unit: mixed` только для repeated groups;
  - либо заменить на `normalized_unit: null/table`;
  - либо проверять единицы только внутри `value`.
- [ ] Обновить `unit_normalization_guide.json`, schema и validator согласованно.
- [ ] В prompt объяснить модели, как заполнять единицу для строк-таблиц.

Проверка:

- [ ] Валидатор не ругается на корректные detail rows.
- [ ] Валидатор продолжает ловить реальные ошибки единиц в scalar-полях.
- [ ] Нельзя под видом `mixed` спрятать scalar, который должен быть `m2`/`m3`/`linear_m`.

## Шаг 28.7. Ввести явную логику candidates и автосумм

Проблема:

Проекты часто дают несколько компонентов вместо одного итога. Иногда это можно безопасно сложить,
иногда нельзя.

Типовые случаи:

- можно суммировать:
  - воронки одного типа в штуках;
  - компоненты одной мембраны по зонам, если это один target и одна сущность;
  - однотипные компоненты материала, если нет конфликтующего итога;
- нельзя молча суммировать:
  - бетон плиты и бетон балок;
  - строки, где есть явный конфликт между итогом и компонентами;
  - маршруты коммуникаций, трубы и фитинги как одну длину;
  - разные кровельные материалы, если у них разные типы/слои.

Что сделать:

- [ ] Описать в коде список разрешенных автосумм по target_code/group.
- [ ] Для разрешенной автосуммы сохранять:
  - итог;
  - список компонентов;
  - note "автосумма из компонентов";
  - статус `needs_review` или `found` по правилу риска.
- [ ] Для запрещенной суммы оставлять candidates и выводить вопрос.

Проверка:

- [ ] Мембрана/воронки суммируются только универсальным правилом, без проектных чисел.
- [ ] Бетон плиты и балки не складываются в один объем.
- [ ] В Google workbook видно, что значение получено автосуммой.

## Шаг 28.11. Решить границу между prompt и кодом

Правило:

Prompt читает проект и сохраняет факты.

Код принимает production-решения:

- автосуммы;
- блокировки расчета;
- обязательность поля;
- отображение в workbook;
- подготовка данных для калькулятора.

Что не надо делать:

- [ ] Не заставлять модель считать бизнес-логику вместо кода.
- [ ] Не добавлять в prompt правила под конкретный проект.
- [ ] Не чинить missing тем, что модель "вспомнит" значение из контекста.

Что надо делать:

- [ ] Код должен решать, какие компоненты можно превратить в итог.
- [ ] Сметчица должна видеть все места, где автоматике нельзя доверять.
