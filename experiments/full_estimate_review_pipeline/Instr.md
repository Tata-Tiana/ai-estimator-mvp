Что из PDF должно прийти по фундаментной плите
В contract сейчас заложены такие проектные параметры:
membrane_area_m2 — площадь мембраны PLANTER под плитой;
slab_side_formwork_area_m2 — площадь опалубки бортов фундаментной плиты;
eps50_under_slab_volume_m3 — ЭППС 50 мм под плитой, объем;
concrete_project_volume_m3 — проектный объем бетона фундаментной плиты;
thermal_insert_50_length_m — длина термовставок 50 мм;
thermal_insert_100_length_m — длина термовставок 100 мм;
thermal_insert_50_material_spec_qty — материал термовставок 50 мм по спецификации;
thermal_insert_100_material_spec_qty — материал термовставок 100 мм по спецификации;
foundation_rebar_items — арматура по строкам спецификации: класс стали, диаметр, длина в м.п., масса 1 м.
Ключевое: арматура теперь не “итоговым весом”, а строками из проекта, потому что PDF обычно дает м.п. и массу метра. Калькулятор потом сам досчитает закупку/вес/стоимость.
Что важно не путать
Мы зафиксировали прям отдельными правилами:
бетон фундаментной плиты не смешивать с бетоном перекрытий, балок, перемычек;
ЭППС 50 мм под плитой — это м3, а площадь укладки считается потом;
опалубка бортов — это м2, ее нельзя путать с ЭППС 100 мм торца;
eps_100_edge_volume парсер может найти, но в калькулятор фундаментной плиты он сейчас не идет как production input;
термовставка “длина” и термовставка “материал объем” — разные вещи.
Что считается автоматически
В contract есть блок auto_calculated. Там описано, например:
площадь укладки ЭППС 50 мм = eps50_under_slab_volume_m3 / eps50_thickness_m;
количество фанеры = площадь опалубки с запасом / площадь листа;
заказной объем бетона = проектный бетон с коэффициентом запаса и округлением;
арматура считается по строкам спецификации, с запасом и длиной хлыста.
То есть мы не просим GPT угадывать формулы. GPT должен дать проектные строки, а формулы остаются в нашем слое.
Что идет в цены
В этом же contract перечислены price keys: работы по мембране, материал PLANTER, опалубка, фанера, пиломатериал, ЭППС, термовставки, арматура, бетон, доставка бетона, бетононасос, демонтаж опалубки, кран, доставка металла, технадзор.
Это потом должно лечь на лист 02_Цены себестоимости.
Что остается ручным
Есть supplier_inputs:
смены крана для подачи арматуры;
машины доставки арматуры/металла;
общий вес металла коробки для контроля доставки;
смены бетононасоса;
логистика и снабжение;
расходники/амортизация инструмента.
То есть мы честно не притворяемся, что это можно достать из PDF, если калькулятор все равно ждет ручное решение.

Там нашли и частично уже исправили важные вещи:

Куда мы двигаемся
Сейчас архитектура такая:
GPT/PDF extraction
→ target_aliases_ru.yaml помогает понять русские строки проекта
→ section_contract.yaml говорит, какие значения нужны калькулятору
→ Google review workbook показывает это Елене на проверку
→ после правок workbook скачивается обратно
→ reader делает normalized review JSON
→ adapter собирает input калькулятора
→ калькулятор считает
→ финальная смета получает строки и формулы.
Фундаментная плита сейчас уже прошла важный этап: мы поняли ее contract и сверили с реальными extraction-проходами. Это уже не совсем темный лес. Но до “света” еще есть два больших куска:
Сделать общий reader: Google workbook → normalized review JSON.
Сделать adapter: normalized review JSON → input конкретного калькулятора фундаментной плиты.
