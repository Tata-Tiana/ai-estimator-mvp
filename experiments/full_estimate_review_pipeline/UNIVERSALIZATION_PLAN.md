# Universalization Plan — making the 8 section contracts project-agnostic

Дата создания: 2026-07-18.

**Если контекст сессии прервался — читай этот файл первым**, до того как редактировать любой
`section_contract.yaml` или калькулятор. Источник: `reports/step_20_ark_third_project_stress_test.md`,
`reports/step_21_ark_real_extraction_crosscheck.md`, `reports/step_22_trc_real_extraction_audit.md`,
плюс уже сделанные ТРЦ-правки 2026-07-13..15 (см. `git log --oneline --all -i --grep=ТРЦ`, память
`lintel_floor_split_and_monolithic.md` и `floor_2_walls_incomplete_and_floors_count_risk.md`).
**ТРЦ ещё не готов "идеально проходить" через пайплайн** — есть отдельное, не чинящееся кодом условие
(несовпадающие штампы объекта на части листов КР2, см. раздел "ТРЦ real-extraction audit" ниже).

## Зачем этот файл

Заказчик прямо попросил: проверить калькуляторы/парсер ещё на нескольких проектах и сделать всю
систему сметы коробки универсальной под разные архитектурные и конструктивные решения, а не
подогнанной под один дом.

ЮСВ в одиночку сформировал все 8 контрактов под себя. ТРЦ заставил вырасти `load_bearing_walls_lintels`
и `waterproofing` (перемычки по этажам, монолитные перемычки, опциональный D500 парапет, опциональный
слой ЭППС-50 в гидроизоляции). Третий реальный проект (АРК, отчёт `step_20`) показывает ту же
жёсткость ещё в пяти местах — и один случай, где правило, выведенное на ТРЦ, оказалось не
универсальным (D400/D500 по ширине блока). Этот файл — приоритизированный чек-лист правок,
закрывающих найденные пробелы.

## Базовые правила (унаследованы из Instr.md/HANDOFF.md, повторены здесь для этого потока работы)

- Не придумывать числа: каждое поле здесь — это правка *формы* (новая repeated-группа, новое
  значение `context`, новое опциональное поле), подтверждённая по реальному PDF/калькулятору, а не
  догадка.
- Никаких проектных чисел ни в этом файле, ни в `section_contract.yaml` — только имена полей,
  source_class, контексты.
- Код калькулятора трогаем по минимуму; где возможно — чиним на уровне контракта (тот же принцип,
  что и Naming Alignment Rule). Явно помечать, где правка `calculator.py` неизбежна, чтобы
  пользователь мог её авторизовать заранее (как исключения 2026-07-10 для flat_roof/floor_slab_1).
- Перед тем как доверять любому имени поля, выведенному из ручного чтения PDF — прогнать реальный
  chat-extraction (`claude_estimate_extraction_prompt.md`) по проекту и свериться, как это уже
  сделано для ЮСВ в step_13/15/16/17.

## Закрытый вопрос архитектуры (был открытым в step_21, решён 2026-07-19 после чтения кода калькулятора)

- Раньше здесь был вопрос: не перевести ли `floor_slab_1_beams_concrete_volume` (и аналоги) из
  `AUTO_PROJECT` в `AUTO_CALCULATED`, раз это поле всегда можно получить суммой `beam_items[]`.
  **Решено: не трогать.** Чтение `floor_slab_1_calculator.py` показало, что поле уже устроено
  правильно — калькулятор всегда сам суммирует `beam_items[]`, а печатный итог из PDF (если есть)
  используется как перепроверка: при расхождении с суммой больше 0.01 м³ калькулятор останавливается
  с ошибкой. Это рабочий, уже приносящий пользу защитный механизм (та же категория, что расхождения
  бренда мембраны кровли и длины вентканалов), специально добавленный под то, что и у ЮСВ, и у ТРЦ
  печатается настоящий общий итог по балкам. Перевод в `AUTO_CALCULATED` убрал бы эту защиту именно
  там, где она сейчас работает.
  **Реальная проблема — в промпте извлечения, не в контракте/калькуляторе**: на АРК спецификация
  балок floor_slab_1 не даёт общего итога, только отдельные строки по маркам — а список алиасов цели
  ("бетон балок", "объём бетона балок") недостаточно строгий и, похоже, матчится и на отдельные марки
  тоже. Нужно ужесточить правило: это поле заполняется ТОЛЬКО из строки, явно обозначенной как общий
  итог по всем маркам сразу (например, рядом со словом "Итого"), никогда — из значения отдельной
  марки; для отдельных марок уже есть корректное место, `beam_items[]`, без всякой дополнительной
  цели.
