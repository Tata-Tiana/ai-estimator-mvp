# Продакшн-репетиция: бот принимает JSON, гоняет коррекцию, собирает review workbook

Дата: 2026-08-25. Цель — превратить ручной цикл, который сейчас выполняется руками через Claude
Code, в цикл через Telegram-бота: загрузка extraction JSON → авто-отчёт работы над ошибками →
загрузка исправленного JSON → сборка Google review workbook → (после заполнения сметчицей) сборка
финальной сметы.

Светофор (pre/post-calculation readiness gate из `HANDOFF.md`) в этот заход **не входит** —
отдельная будущая задача.

## Фазы

### Фаза 0 — реанимация бота (инфраструктура, без новой логики)

1. Новый launchd-plist с текущим путём репозитория (`/Users/tatanamedzidova/Desktop/ai_estimator/ai_estimator_mvp`).
2. `TELEGRAM_BOT_TOKEN` в `.env` (сейчас отсутствует в `.env.example` — добавить туда тоже, без
   самого токена).
3. Запустить, убедиться, что бот отвечает на `/start` без падений — до любой новой функциональности.

### Фаза 1 — приём JSON вместо PDF

1. Новая команда/режим приёма файла: `.json` (а не только `.pdf`, как сейчас) — определяем по
   расширению, как уже сделано для PDF в `handle_document`.
2. Файл кладётся в `experiments/chat_extraction_poc/outputs/<project>/`, с понятным именем (не
   переписывая предыдущие версии — та же логика, что у файлов вида `extraction_output(N).json`,
   которые сейчас качаются вручную из ChatGPT).
3. Бот подтверждает приём и просит следующий шаг (либо ждёт `/done`, либо срабатывает сразу — решить
   при реализации).

### Фаза 2 — авто-отчёт работы над ошибками

1. После приёма JSON бот сам запускает `build_extraction_notes_report.py --input <json> --output <report>`.
2. Отдаёт готовый `.txt`-отчёт обратно в чат — тот же файл, что сейчас руками отправляется в
   ChatGPT вместе с `notes_report_correction_prompt.md`.
3. Бот НЕ отправляет ничего в ChatGPT сам — это по-прежнему делает человек (вставляет в тот же чат).
   Автоматизация чата с ChatGPT — вне scope этой репетиции.

### Фаза 3 — приём исправленного JSON

1. Тот же приёмник, что в фазе 1, но с пометкой «это уже вторая, исправленная версия» — либо
   отдельная команда (`/upload_corrected`), либо бот сам определяет по количеству файлов проекта.
2. Как только исправленный JSON получен — переходим к фазе 4.

### Фаза 4 — сборка review workbook + публикация в Google

1. `populate_review_workbook_from_extraction.py` на исправленном JSON.
2. Публикация в Google Sheets — нужно сначала проверить состояние `google_sheet_publisher.py`
   (он есть, но нигде не подключён — до этой фазы отдельно посмотреть, рабочий ли он вообще, или
   нужно чинить).
3. Бот присылает ссылку на Google-таблицу сметчице.

### Фаза 5 — сборка финальной сметы

1. Команда `/build <job_id>` (переиспользуем из старого бота, но без хардкода `--section-number 2` —
   должна собирать все 7 разделов через `build_all_section_results.py` + экспорт).
2. Бот скачивает заполненную Google-таблицу, гоняет калькуляторы, отдаёт финальный Excel.

### Команды бота для сметчицы и админов

Добавлено 2026-08-27 после первого рабочего JSON-flow в Telegram: пользовательский интерфейс нельзя
смешивать со старым PDF-flow, иначе сметчица не понимает, с какого файла начинается работа.

Обычная сметчица должна видеть только текущий production-путь:

1. `/start` — короткая инструкция: первый JSON, отчёт замечаний, исправленный JSON, Google-таблица,
   затем `/build <job_id>`.
2. `/help` — подробная инструкция по тому же JSON-пути без упоминания прямой PDF-загрузки.
3. `/new_project` — явно начать новый JSON-прогон, если бот ещё помнит предыдущий job.
4. `/update_json <job_id>` — загрузить новый исправленный JSON в уже существующий job, если сметчица
   позже попросила ChatGPT поправить JSON словами. Следующий присланный JSON не создаёт новый проект,
   а сохраняется в старую папку job и сразу пересобирает Google-таблицу.
5. `/recreate <job_id>` — пересобрать Google-таблицу из последнего JSON без нового extraction.
6. `/build <job_id>` — скачать проверенную Google-таблицу, посчитать разделы и собрать итоговую смету.

Команды `/done`, `/cancel`, `/rerun`, `/confirm_rerun` относятся к старому PDF-flow. Они могут
оставаться в коде как legacy/admin-инструменты, но не должны показываться в обычном `/help` и не должны
быть основным сценарием для Елены. Если позже понадобится отмена именно JSON-прогона, нужно сделать
отдельное поведение `/cancel` для JSON-session или новую понятную команду, а не возвращать PDF-логику
в пользовательскую инструкцию.

Админский `/admin_help` должен явно помечать старые PDF-команды как legacy, а диагностические команды
оставить отдельно: `/admin_status`, `/sessions`, `/logs`, `/tail_errors`, `/job_status <job_id>`,
`/export_logs ...`, `/reset_session <chat_id>`, `/recover_sessions`.

### Фаза 6 — нормальные логи

Отдельный пункт, не «потом» — входит в эту репетицию.

Что нашли по старому боту: логи в принципе есть (`telegram_logs/`, `admin_exports/`,
восстановление сессий), но реальный `err.log` разросся до **1.87 ГБ** и молча копил цикл падений
несколько недель никем не замеченный — то есть логи писались, но были нечитаемы и никто не видел,
что бот вообще упал.

Нужно:

1. **Ротация/ограничение размера** лог-файлов — не дать повториться истории с 1.87 ГБ.
2. **Разделение по уровням**: отдельно падения/ошибки (коротко, по одному инциденту, не полный
   traceback-дамп на каждую попытку реконнекта), отдельно обычный ход работы (какой JSON пришёл,
   какой отчёт отдан, какая таблица собрана).
3. **Явный сигнал живости** — при старте бот должен один раз явно залогировать текущий путь
   репозитория и версию/коммит, чтобы path-баги (как в этот раз) были видны сразу в первой строке
   лога, а не через раскопки внутри многогигабайтного файла.
4. **Простая проверка статуса** — переиспользовать `/admin_status` из старого бота (уже есть),
   убедиться, что он реально отражает: жив ли процесс, когда был последний успешный джейсон/сборка.

## Что осознанно НЕ входит в эту репетицию

- Светофор (pre/post-calculation readiness gate) — отдельная будущая задача.
- Автоматизация самого ChatGPT-чата (отправка промпта/файлов туда ботом) — человек по-прежнему
  сам переносит отчёт в чат и получает исправленный JSON обратно, бот его только принимает.
- Проверка/починка `google_sheet_publisher.py`, если окажется, что он реально не работает — это
  найдём в фазе 4, но чинить будем отдельным шагом, не блокируя всю репетицию.

## Порядок работы

Фаза 0 → 1 → 2 → 3 → 4 → 5, логи (фаза 6) — не в конце, а внедряются с фазы 0 (проще сразу писать
нормально, чем переделывать после). Каждую фазу проверяем перед следующей — реальным файлом, не
только "код написан".
