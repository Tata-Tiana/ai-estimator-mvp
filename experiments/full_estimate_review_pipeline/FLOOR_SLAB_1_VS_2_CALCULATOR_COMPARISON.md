# floor_slab_1_calculator.py vs floor_slab_2_calculator.py — построчное сравнение кода

Дата: 2026-08-09. Часть P1.1 `FLOOR_SLAB_UNIFICATION_PLAN.md` — обязательный шаг перед слиянием
калькуляторов. Оба файла прочитаны целиком (не по памяти о более ранних правках в этой сессии):
`experiments/floor_slab_1_calculator/floor_slab_1_calculator.py` (1601 строка),
`experiments/floor_slab_2_calculator/calculator.py` (1120 строк).

**Вывод по каждому пункту ниже — не "молча перенести", а явное решение, что берём за основу.**
floor_slab_1 в целом более зрелый (это уже было ясно), но ниже есть исключения, где floor_slab_2
делает что-то, чего в floor_slab_1 нет вообще, и это не второстепенно.

## 1. Арматура — самое большое расхождение

| | floor_slab_1 | floor_slab_2 |
|---|---|---|
| `rebar_calc_method` значения | `legacy_weight_parts` / `spec_length_items` | `legacy_weight_kg` / `spec_length_items` (**другие имена!**) |
| `waste_coeff` | обязателен на каждой строке (`item["waste_coeff"]` без fallback) | опционален, `item.get("waste_coeff", default_waste_coeff)` — есть общий дефолт |
| Валидация `component`/`floor` | жёстко требует `component=="floor_slab_1"` и `floor==1` для `spec_length_items` | нет такой проверки вообще |
| `price_code` | НЕ хранится на item, строится на месте вызова `estimate_line()`: `f"rebar_{steel_class.lower()}_d{diameter}_m"` | хранится прямо на item (`item.get("price_code", ...)`) |
| Пул округления по группе | **есть** (`calculate_rebar_items_pooled()`, добавлено 2026-08-09, только для `spec_length_items`) | **нет вообще** — каждая строка округляется независимо, всегда (тот же баг, что чинили в floor_slab_1 Находкой 4, сюда не перенесён) |

**Решение:** брать floor_slab_1 за основу целиком (более новая логика, пул уже проверен на реальных
данных). Порт пула на floor_slab_2 — часть слияния, не отдельная задача "когда-нибудь". Имена
calc_method нормализовать на floor_slab_1's (`legacy_weight_parts`/`spec_length_items`) — в
floor_slab_2's `legacy_weight_kg` нет смысловой разницы, просто другое слово.

## 2. Балки

| | floor_slab_1 | floor_slab_2 |
|---|---|---|
| Функция | inline в `calculate_floor_slab_1()` | отдельная `calculate_beam_items()` |
| Бетонирование балок | **разделено по высоте** (≤250мм — мп, >250мм — м³, 2 разные строки/ставки, `beam_concrete_placing_work_m`/`_m3`) | **одна строка**, всегда по длине (мп), одна ставка `beam_concrete_placing_work_m`, независимо от высоты |
| `eps_material_area_m2` на балку | считается отдельно, позже, внутри `calculate_insulation_context()` | считается сразу в `calculate_beam_items()`, лежит на самом item |
| Валидация length/height >= 0 | **отсутствует** (проверяется только `count < D0`) | есть явная проверка `length_m/width_m/height_m/count >= 0` вместе |

**Решение:** высотное разделение — реальная методическая развилка между проектами (подтверждено и на
уровне сметы ТРЦ/АРК vs ЮСВ, и на уровне кода floor_slab_1 vs floor_slab_2) → `calc_method`-флаг
`beam_concreting_calc_method` (`height_split`/`single_rate`), дефолт для floor_slab_2-совместимости
— `single_rate`. Валидацию length/height >= 0 добавить в объединённую версию (сейчас дыра именно в
floor_slab_1, не в floor_slab_2 — мелкая, но реальная).

## 3. Площадь опалубки/геометрия — САМОЕ СЕРЬЁЗНОЕ расхождение

floor_slab_1's Находка 3 (площадь опалубки = объём бетона плиты / толщина, не "горизонтальная
опалубка" из спецификации — подтверждено день-в-день на ТРЦ/АРК, отчёт 05) **НЕ перенесена на
floor_slab_2 вообще**. У floor_slab_2:

- Метод `formwork_area_calc_method` (не `formwork_area**S**_calc_method`, другое имя) ∈
  {`legacy_dimensions`, `spec_formwork_area`} — тоже другие имена, чем у floor_slab_1
  (`legacy_calculated_from_geometry`/`spec_formwork_areas`).
- `legacy_dimensions` считает площадь как `slab_length_m × slab_width_m` — **этого режима у
  floor_slab_1 вообще нет**, у него нет понятия "длина×ширина плиты" как источника площади.
- `spec_formwork_area` берёт `main_formwork_area_m2` **напрямую как готовый вход**, без всякого
  сопоставления с объёмом бетона/толщиной — то есть если Находку 3 подтвердить и на floor_slab_2
  (весьма вероятно, метод универсальный по своей природе), у floor_slab_2 сейчас та же цена
  недосчёта, что была у floor_slab_1 до фикса 2026-08-09, просто ещё не найденная/не исправленная.

**Решение: это не входит в слияние молча.** Нужно отдельно решить и подтвердить на floor_slab_2 (на
реальных данных, минимум ТРЦ), прежде чем объединённый калькулятор станет "истиной" для обеих
секций — иначе слияние тихо экспортирует уже известный, ранее исправленный баг обратно в
floor_slab_2. Кандидат на отдельный "давай" внутри P1, не тянуть в P0/автоматически.

## 4. Доставка опалубки манипулятором

| | floor_slab_1 | floor_slab_2 |
|---|---|---|
| Порог (180 м²) | хардкод `d(180)` внутри функции | берётся из входа, `input_data.get("formwork_delivery_threshold_m2", 180)` — настраиваемый |
| По зонам (2026-08-09) | **есть** (`zone_under_slab_areas_m2`, применяет порог к каждой зоне отдельно, суммирует) | **нет** (нет slab_zones — некуда применять) |
| Имя поля с итогом | `formwork_delivery_trucks` | `formwork_delivery_trips` (другое слово) |
| Где считаются деньги | снаружи, на месте `estimate_line()` | внутри самой context-функции (`formwork_delivery_total_raw` уже посчитан) |

**Решение:** брать floor_slab_1 за основу (по-зонная логика уже нужна для унификации). Порог сделать
настраиваемым полем (floor_slab_2's подход лучше — не хардкодить магическое число), но
дефолт = 180 сохранить.

## 5. Ставка на опалубку (комплект/рента)

floor_slab_1 — `calculate_formwork_rate_context()`, два calc_method
(`legacy_supplier_quote_context` — среднее по смете квоте на floor_slab_1+2 вместе,
`direct_section_rate` — прямая ставка). floor_slab_2 — нет отдельной context-функции, ставка ВСЕГДА
берётся как готовый вход `formwork_rental_used_rate_per_m2`, `raw_supplier_rate` считается только
для диагностики (не влияет на деньги). **Решение:** унифицировать под floor_slab_1's два режима,
`direct_section_rate` как дефолт для floor_slab_2-совместимости (у неё сейчас фактически всегда
прямая ставка).

## 6. Бетон — объём/округление/рейсы

| | floor_slab_1 | floor_slab_2 |
|---|---|---|
| Источник объёма | из `total_concrete_volume_from_spec_m3` ИЛИ суммы `slab_zones[]` | прямой вход `concrete_placing_volume_m3` (уже готовое число, "manual/project quantity", даже с явным комментарием "not derived from slab_area × thickness") |
| По зонам (2026-08-09) | **есть** (`calculate_concrete_order_context`, по зоне при наличии `additional_concrete_items`) | **нет** |
| Округление заказа | всегда до целого м³ вверх (`ceil_decimal`) | до произвольного шага (`ceil_to_step(..., concrete_round_step_m3)`) — **другое правило округления** |
| База для рейсов доставки | объём С ОТХОДАМИ, до округления заказа | объём ПОСЛЕ округления заказа (`concrete_order_volume / mixer_volume`) — **другая база**, численно может отличаться |

**Решение:** брать floor_slab_1's по-зонную логику за основу. Округление до шага (floor_slab_2)
интереснее, чем жёсткий ceil до целого — стоит сохранить как настраиваемый `concrete_round_step_m3`
(дефолт "1" = то же самое, что ceil_decimal). База для рейсов доставки — выбрать ОДНУ осознанно
(вероятно floor_slab_1's "с отходами, до округления заказа" — точнее физически), не тащить обе
молча.

## 7. Утепление

| | floor_slab_1 | floor_slab_2 |
|---|---|---|
| Функция | отдельная `calculate_insulation_context()`, 2 calc_method | inline, без calc_method вообще, всегда один способ |
| Cross-check (расчётный объём ЭППС vs объём по спецификации) | есть (`eps_volume_delta`, warning при расхождении) | нет вообще |
| Минимум баллонов клея-пены | нет | **есть** (`foam_min_cans`, `max(min_cans, ceil(raw))`) |
| Хардкод в коде | `d("84.8")` — только для legacy-режима, явно помечен как исторический fallback | **`edge_insulation_height_m` жёстко читается как вход, но КОММЕНТАРИЙ В КОДЕ хардкодит вывод**: `"edge_insulation_height_m = 0.18 m is confirmed by specification; 200 mm in the section title is considered a naming error."` — это ТРЦ-специфичный текст, зашитый в общий калькулятор (см. пункт 9) |

**Решение:** floor_slab_1 за основу (calc_method + cross-check ценнее). `foam_min_cans` — сохранить
как опциональный параметр (полезная защита, ничего не портит при дефолте 0). Хардкодную ТРЦ-строку
из floor_slab_2 — убрать при слиянии, не переносить.

## 8. Металл — доставка арматуры

floor_slab_1 — `calculate_metal_delivery_context()`, два режима (`legacy_slab1_slab2_context` —
общий 10-тонный порог на floor_slab_1+floor_slab_2 вместе, `section_output_only` — с уровня
box-калькулятора). floor_slab_2 — **нет функции вообще**, просто читает готовые
`rebar_metal_delivery_trucks`/`rebar_metal_delivery_unit_price` как вход (всегда как бы
`section_output_only`). **Решение:** унифицировать под floor_slab_1, `section_output_only` как
дефолт (это уже единственный режим, которым сейчас реально пользуется production, `legacy_slab1_
slab2_context` — исторический, см. его же note в коде floor_slab_1).

## 9. Две реальные независимые НАХОДКИ (не про унификацию — баги сами по себе)

- **`floor_slab_2_calculator.py`, строка `section_title`**: `return {..., "section_title": "Ж/Б
  МОНОЛИТНАЯ ПЛИТА ПЕРЕКРЫТИЯ 2-го этажа на отм. +4.680 (200мм)", ...}` — это **буквально
  захардкоженная строка с числами конкретно ТРЦ** (отметка +4.680, 200мм) в "универсальном"
  калькуляторе. Если считать этой функцией любой другой проект (АРК, ЮСВ), заголовок раздела в
  результате всё равно будет говорить "+4.680 (200мм)", независимо от реальных чисел проекта. Тот
  же класс бага, что уже чинили в floor_slab_1 (литерал 51.9 вместо `display_decimal(...)`,
  Находка 5 отчёта 05) — тестовые/проектные данные утекли в "общий" код. `floor_slab_1_calculator.py`
  не возвращает `section_title` вообще (нет этого поля на этом уровне).
- **Комментарий-хардкод про 0.18м** (пункт 7 выше) — того же происхождения, тот же класс проблемы.

Обе находки — реальные, но НЕ блокируют P1: при слиянии эти литералы просто не переносятся (не
нужно отдельного "давай" на их удаление, это не изменение поведения по деньгам — `section_title`
никогда не участвовал в подсчёте суммы, только в тексте заголовка).

## 10. Прочее по мелочи

- floor_slab_1 не эмитит control-строки "Заготовительно-складские"/"Накладные"/"Сметная прибыль" в
  `estimate_lines` вообще; floor_slab_2 эмитит все три как нулевые `zero_excel_structure_line`
  строки. Не про деньги (обе они 0 в обоих калькуляторах), но влияет на то, сколько строк увидит
  человек в результате — стоит унифицировать в объединённой версии для консистентности отображения.
- `price_code` почти everywhere СОВПАДАЕТ между двумя калькуляторами (комплект опалубки, доставка,
  кран, металл, расходники, фанера, брус, бетон, доставка бетона, насос, утепление торца/низа, ЭППС,
  клей-пена — все одинаковые строки) — регистр цен уже фактически унифицирован, разъезжаются только
  КОДЫ САМИХ estimate_line (человеко-читаемые id) и логика количеств, не цены. Единственный реальный
  пробел в price_code — у floor_slab_2 нет пути к `beam_concrete_placing_work_m3` (высокие балки),
  потому что нет самого высотного разделения (см. пункт 2).
- База для расчёта логистики/расходников (% от суммы раздела): floor_slab_1 суммирует ВСЕ
  `estimate_lines` неявно (control-строки дают 0, поэтому не мешают) — если когда-нибудь у
  control-строки появится ненулевая сумма по ошибке, это тихо утечёт в базу. floor_slab_2 считает
  базу явным списком нужных величин (`direct_cost_base_before_addons_raw = formwork_rental_total_raw
  + ... + foam_total_raw`), защищённее. Стоит взять floor_slab_2's явный подход при слиянии, а не
  floor_slab_1's неявный.

## Итоговый список calc_method-флагов для объединённого калькулятора (было 2 в исходном плане, реально 6)

1. `beam_concreting_calc_method`: `height_split` (floor_slab_1) / `single_rate` (floor_slab_2).
2. `formwork_dismantling_calc_method`: `priced` / `zero_control` — из сравнения смет (АРК/ЮСВ vs ТРЦ), не из кода калькуляторов (оба калькулятора сейчас всегда `zero_control`/control-line).
3. `formwork_area_source_calc_method`: `from_concrete_volume` (floor_slab_1's Находка 3) / `from_spec_direct` (floor_slab_2 текущее) / `from_dimensions` (floor_slab_2's legacy_dimensions) — **нужно решение пользователя**, не просто перенос: Находку 3 стоит ли распространять на floor_slab_2 по умолчанию или только опционально.
4. `formwork_rate_calc_method`: `legacy_supplier_quote_context` / `direct_section_rate` (уже есть в floor_slab_1, floor_slab_2 фактически всегда direct).
5. `concrete_order_rounding`: `ceil_to_whole_m3` (floor_slab_1) / `ceil_to_step` (floor_slab_2, с настраиваемым шагом).
6. `metal_delivery_calc_method`: `legacy_slab1_slab2_context` / `section_output_only` (уже есть в floor_slab_1, floor_slab_2 фактически всегда section_output_only).

Плюс параметры (не calc_method, просто числа с дефолтами): `foam_min_cans` (дефолт 0 = floor_slab_1
поведение), `formwork_delivery_threshold_m2` (дефолт 180 у обоих).
