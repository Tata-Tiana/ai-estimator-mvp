## 1. Фундамент

### 1.1. Стены фундамента как отдельная конструкция
**Находка (пользователь):** КР1 стр.10 — бетон 33,0 м3 (стены) + 1,6 м3 (подколонники), верт.
опалубка 163,0/6,9 м2, гидроизоляция 134,3/11,9 м2.
**Проверка:** подтверждено в реальном JSON АРК. **Уже реализовано** — `foundation_wall_items[]` и
`column_footing_items[]` в контракте `foundation_slab`, шипнуто 20 июля 2026. Ничего менять в
архитектуре не нужно.
**Остаётся сделать:** доставить данные до листа 01 (известный баг №1/№2, см.
`SECTION_WITHIN_SECTION_AND_CAPTURE_STATUS_PLAN.md`) и добавить туда арматуру (см. ниже, п.1.1a).

### 1.1a. Арматура стен фундамента/подколонников — не имеет пути захвата
**Проверка:** подтверждено (найдено этой сессией на свежем прогоне АРК). `foundation_wall_items`/
`column_footing_items` имеют поля: `concrete_volume_m3`, `vertical_formwork_area_m2`,
`planter_membrane_area_m2`, `waterproofing_coating_area_m2`, `waterproofing_extent` — **арматуры нет**.
Реальная ведомость армирования ПК1 (сетка Ø12, П-хомуты Ø10, вертикальные Ø16, хомуты Ø6, выпуски,
точные длины, плотность 107,83 кг/м3) сохраняется только текстом.
**MVP:** нужно добавить вложенную арматурную группу или отдельные `foundation_wall_rebar_items`/
`column_footing_rebar_items`.

### 1.2. Две отдельные плиты ФП1/ФП2 вместо одной
**Находка (пользователь):** ФП1 — бетон 49,5 м3, обмазочная гидроизоляция ТОЛЬКО по торцу 7,2 м2,
PLANTER 256,0 м2. ФП2 — бетон 10,5 м3, обмазочная гидроизоляция по торцу **и по верху** 39,3 м2,

**Проверка:** `slab_zones[]` **уже реализован** в контракте `foundation_slab` (20 июля), покрывает
случай "несколько зон плиты без общего итога" (тот же паттерн, что и у ТРЦ — см. раздел "Сравнение"
ниже). НО текущие колонки `slab_zones[]` — только `context` + `concrete_volume_m3`. Поля
`waterproofing_extent` там нет, хотя оно уже есть в соседних `foundation_wall_items`/
`column_footing_items` (тот же паттерн, просто не применён к `slab_zones`).
**MVP:** точечно добавить `waterproofing_extent` (и, возможно, отдельные площади PLANTER/обмазочной
гидроизоляции на зону, если сейчас они общие скаляры, не по зонам — проверить перед правкой) в
`slab_zones[]`.

### 1.3. Термовставка Т1 — нестандартная геометрия
**Находка (пользователь):** у АРК термовставка 100×400×160 (не 50/100мм раздельно, как у ЮСВ/ТРЦ),
арматура ф12+ф6.
**Проверка:** подтверждено. `thermal_insert_50_length_m`/`thermal_insert_100_length_m` в контракте

действительно стандартные 50/100мм, это **специфика только АРК**, не общая проблема (см. сравнение).
**MVP:** нужен generic-список термовставок произвольного типоразмера — но приоритет ниже, чем казалось
изначально, т.к. только один из трёх проектов от этого страдает.

### 1.4. Земляные работы — приямки подпятников, типы песка, точка отсчёта глубины
**Находка (пользователь):** площадь котлована 413,8 м2, приямков 15,7 м2, выемка 185,0+27,5 м3, песок
засыпки пазух+траншей 236,0 м3 отдельно от песка подпятников 1,2 м3. Глубина траншей на схеме сетей

## 3. Стены — новые контексты газоблока

### 3.1. Стены второго света и парапет — РАЗНЫЕ уровни, не просто "2-й этаж" — СДЕЛАНО, см. раздел 21
**Находка (пользователь):** "Стены надстройки" (h=1250мм, между +3,730 и +4,980) = 13,0 м3, арматура
114,8 м.пог. "Парапет" на уровне ПМ1 (+3,730…+4,230) = 14,8 м3, арматура 153,8 м.пог. Ещё парапет на
уровне ПМ2 (+5,160…+5,660) = 8,2 м3, арматура 85,2 м.пог, отдельный лист 22.
**MVP-предложение (пользователь):** заменить `parapet_masonry_volume_m3` (один скаляр) на
`wall_block_items[]` с контекстами `floor_1_external`, `floor_1_internal`, `floor_1_partitions`,
`second_light_walls`, `parapet_level_1`, `parapet_level_2`, `vent_cladding`.
**Проверка, уточнено 2026-07-23 — решение дешевле, чем казалось изначально.** `wall_block_items[]`
уже существует (шипнут 20 июля), роли — `WALL_BLOCK_ITEM_ROLES = {"main_walls", "floor_2", "parapet",
"partitions"}`. Проверила `wall_block_items_totals()` в коде калькулятора: она **уже суммирует
несколько строк с одинаковой ролью** (`parapet`, `floor_2`) в один общий объём для расценки — именно
то, что нужно для многоуровневого парапета. **Новые роли `parapet_level_1`/`parapet_level_2` НЕ
нужны** (беру назад более раннюю версию этого пункта) — механизм суммирования одной роли по нескольким
строкам уже реализован и протестирован.
**Подтверждено системно, не специфика АРК:** у ТРЦ та же болезнь — `parapet_masonry_volume`/
`floor_2_masonry_volume` оба `value: null, needs_review: true`, модель нашла парапет 1 этажа (5,94 м3,
арматура 47,36 м.пог) и парапет 2 этажа (13,21 м3, арматура 105,68 м.пог), не смогла выбрать одно
число для скаляра. У АРК — три отдельных зоны (стены надстройки 13,0 м3, парапет ПМ1 14,8 м3, парапет
ПМ2 8,2 м3). **ЮСВ проверено 2026-07-23, чисто**: `parapet_masonry_volume` = 22,74 м3, одно значение,
`needs_review: false`, источник — одна спецификация ("Спецификация парапетов кровли", лист 15), без
разбивки по уровням. Подтверждено дословным совпадением с реальной сданной сметой (`Сметный расчет
_ЮСВ_28.04.2026.xlsx`, лист "РС 29.04.26", строка 51: "Кладка... м3 22,74"). Значит правка промпта под
`wall_block_items[]` не должна задеть ЮСВ — он и так проходит по простому скалярному пути, регрессия
по нему должна остаться чистой.
**Реальный корень проблемы — не калькулятор, а промпт извлечения.** Модель до сих пор пытается
заполнить старое скалярное поле `parapet_masonry_volume_m3`/`floor_2_masonry_volume_m3` и корректно
сдаётся (value: null + candidates), вместо того чтобы направить данные в уже готовый
`wall_block_items[]` построчно (роль `parapet`/`floor_2`, разные `context` на уровень).
**Приоритет — выше, чем у большинства других находок в этом файле**, потому что это уже
production-поле, подключённое к реальной цене кладки газоблока (не diagnostic-only), и подтверждено
минимум в 2 из 3 реальных проектов — то есть сейчас для большинства проектов эта строка сметы вообще
не считается автоматически, требует ручной правки каждый раз.
**MVP:** правка промпта/target-заметок (`calculator_targets_compact.json`/`target_aliases_ru.yaml`) —
научить модель распознавать "несколько уровней парапета/стен надстройки без общего итога" как триггер
для `wall_block_items[]`, а не для скаляра-с-кандидатами. Изменений в `load_bearing_walls_lintels_calculator.py`
не требуется — механизм суммирования уже есть.

**Находка (пользователь):** третий подтип ПР3 (=вероятно ПМ3 из JSON, разное распознавание Р/М) —

**Точные числа (пользователь, по скринам):**

- ПР3 (перегородка, штроба): арматура ф12=11,3 м.пог, бетона нет.

- ПБ2 (2,6м): бетон 0,16 м3; арматура ф6=13,3, ф12=5,2, ф16=7,8.
- Опалубка под ПБ1+ПБ2: нижняя 1,32 м2, вертикальная 2,7 м2.

**Проверка — важное разрешение открытого вопроса.** ПБ1/ПБ2 (=ПМ1/ПМ2 из ранее рассмотренного JSON,

риск**, поднятый ранее в вопросе Елене №2 (не ошибка ли, что ПМ1/ПМ2 попадают в приоритетную цель
несущих перемычек) — похоже, что классификация в JSON верна, тревога была ложной. Оставить вопрос
Елене как есть или отозвать — решение пользователя.

**Проверка группы:** `lintel_groove_rebar_items` **уже существует** как отдельная группа именно для
случая "перемычка без бетона/опалубки/ЭППС, только арматура" (шипнута 20 июля, diagnostic-only).
**MVP:** архитектура готова. Реально новое — перевести группу из diagnostic-only в priced, если нужно

## Ключевой принцип, ранее нигде явно не зафиксированный — "факт данных вместо текстового признака"

**Обнаружено 2026-07-23 при разборе этажности, но принцип общий, не только про `floors_count`.**

Старый способ везде в этом пайплайне неявно строился так: найти в PDF текстовый признак ("этажность —
2 этажа", "количество этажей" и т.п.) и по нему решить, нужно ли считать какой-то блок сметы. Проблема
этого подхода — не в качестве поиска текста, а в том, что **текстовый признак и реальная инженерная
необходимость посчитать что-либо — это два разных понятия**, которые архитекторы называют по-разному
от проекта к проекту, а иногда не называют вообще (см. три разных случая ЮСВ/ТРЦ/АРК ниже).

**Правильный способ, уже проверенный на стенах (20 июля) и работающий одинаково хорошо на всех трёх
реальных проектах**: не спрашивать текстовый признак вообще. Вместо этого проверять **факт наличия
реальных структурированных данных** для того, что нужно посчитать (например: "есть ли в
`wall_block_items` строка с ролью `floor_2` с реальными числами?" вместо "что написано про этажность в
пояснительной записке?"). Если данные реально есть — считать. Если данных нет — не считать. Текст PDF
для этого решения больше не нужен вообще, ни как основной источник, ни как запасной.

**Почему это универсально устраивает разные манеры записи у разных архитекторов**: вопрос "есть ли
реальные данные" не зависит от того, как именно и в каких словах архитектор описал этажность (или не
описал вовсе) — он зависит только от того, есть ли фактически нужные цифры в спецификации. Три реальных
проекта (ЮСВ: текст вводит в заблуждение; ТРЦ: текст верен; АРК: текста нет вообще) — все три
корректно обрабатываются одним и тем же способом без специальных случаев под каждый из них.

**Где это уже применено:** стены (`floor_2`-роль в `wall_block_items`, шипнуто 20 июля).
**Где это уже применено (2026-07-24):** леса/scaffolding (п.10 ниже) — второе применение принципа,
подтверждает, что он универсален, не разовое решение для стен.
**Где стоит проверить в будущем:** любое другое место в пайплайне, где решение "считать или нет"
принимается по тексту PDF (этажность, наличие раздела, тип конструкции), а не по факту наличия
структурированных данных — по той же логике может скрываться та же проблема, что и с `floors_count`.

## 10. Этажность (`floors_count`) — РЕАЛИЗОВАНО, 2026-07-23/24

**Статус: сделано для стен (было готово с 20 июля) И для лесов (реализовано только что).** Оба пункта
ниже помечены как решённые — история проблемы и обоснование оставлены для контекста.

**Проблема, подтверждена на всех трёх проектах по-разному:**
- **ЮСВ**: PDF прямо говорит "Этажность - 1 этаж" (лист 3), но на листе 15 есть отдельная
  "Спецификация несущих стен 2-го этажа" — потому что у дома второй свет, и для расчёта кладки нужен
  второй ярус стен, хотя архитектурно дом однозначно одноэтажный. Модель честно поймала конфликт:
  `needs_review: true`, два кандидата (1 — прямой текст, 2 — по факту отдельной спецификации).
- **ТРЦ**: PDF прямо говорит "3.1. Этажность - 2 этажа" (лист 3) — и это действительно два полных
  этажа, без противоречий. Здесь текстовое извлечение работает корректно.
- **АРК**: слова "этажность" в PDF нет вообще — `floors_count` полностью `missing`, зацепиться не за
  что.
**Вывод:** три реальных проекта — три разных случая (текст вводит в заблуждение / текст верен / текста
нет). Дело не в качестве поиска слова "этажность" — "этажность" из пояснительной записки и "сколько
ярусов стен нужно посчитать для сметы" физически разные понятия, которые иногда совпадают, а иногда
нет. Текстовый парсинг не может отличить одно от другого надёжно ни при каких улучшениях промпта.

**Для стен эта проблема уже решена (20 июля), не нужно ничего чинить повторно.** Проверила код
`load_bearing_walls_lintels_calculator.py`: если `wall_block_items[]` содержит строку с ролью
`floor_2`, второй ярус стен считается автоматически, **независимо от значения `floors_count`** —
именно так был исправлен случай АРК (`floors_count` отсутствует физически). Второй этаж/второй свет
собирается корректно вне зависимости от того, распознана ли этажность текстом.

**Но `floors_count` всё ещё напрямую управляет лесами (scaffolding)** — отдельная строка сметы,
количество ярусов и объём пиломатериала считаются как `floors_count × норма_на_этаж`, это не завязано
на `wall_block_items` вообще.

**Ранее согласованный план (память `floor_2_walls_incomplete_and_floors_count_risk`, 8 дней назад) —
неполный.** Предлагал сделать `floors_count` чисто ручным полем, убрав автопарсинг. Проблема: это не
убирает риск, а переносит его — по умолчанию в калькуляторе `floors_count = 1`, и если забыть
выставить руками, леса тихо посчитаются на один ярус меньше именно для тех же случаев (второй свет,
второй этаж), где раньше подводило автоизвлечение.

**Сделано, 2026-07-24.** Вместо отдельного ручного поля `floors_count` для лесов — количество ярусов
лесов теперь выводится из того же признака, что уже используется для стен: наличие `wall_block_items`
с ролью `floor_2`. `calculate_scaffolding()` в `load_bearing_walls_lintels_calculator.py` принимает
`wall_block_totals` и, если он передан (то есть `wall_block_items` реально используется в этом
расчёте), берёт количество ярусов из факта наличия `floor_2`-роли (2, если есть; 1, если нет) —
**значение `floors_count` при этом полностью игнорируется**. Если `wall_block_items` не используется
(старые/простые проекты) — поведение байт-в-байт как раньше, `floors_count` работает как обычно.

Новое поле в результате `scaffolding.floors_count_source` показывает, откуда взято число
(`"wall_block_items"` или `"floors_count"`), `floors_count_input` сохраняет исходное значение
`floors_count` для прозрачности, даже когда оно было проигнорировано.

Добавлен новый регрессионный кейс `test_scaffolding_from_wall_block_items`, специально
воспроизводящий сценарий АРК: `floors_count = 1` (заведомо неверное/устаревшее значение), но
`wall_block_items` содержит реальную строку `floor_2` (12,5 м3) — подтверждено, что леса корректно
считаются на 2 яруса, а не на 1. Полная регрессия: 19 из 19 успешно выполняемых кейсов (3 отдельных
негативных кейса на некорректный ввод по-прежнему падают ожидаемо, не связаны с этой правкой) — 0
расхождений.

**Статус:** и стены, и леса теперь определяются одинаково — по факту наличия данных, не по тексту PDF
и не по отдельному ручному полю, которое можно забыть заполнить.

## 22. Находка 3.2 — подоконное армирование в общую сумму, перегородки — никогда, найден риск коллизии кода (2026-07-26)
