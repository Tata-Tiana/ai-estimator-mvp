## 1. Фундамент

### 1.1. Стены фундамента как отдельная конструкция
**Находка (пользователь):** КР1 стр.10 — бетон 33,0 м3 (стены) + 1,6 м3 (подколонники), верт.
опалубка 163,0/6,9 м2, гидроизоляция 134,3/11,9 м2.
**Проверка:** подтверждено в реальном JSON АРК. **Уже реализовано** — `foundation_wall_items[]` и
`column_footing_items[]` в контракте `foundation_slab`, шипнуто 20 июля 2026. Ничего менять в

**Остаётся сделать:** доставить данные до листа 01 (известный баг №1/№2, см.
`SECTION_WITHIN_SECTION_AND_CAPTURE_STATUS_PLAN.md`) и добавить туда арматуру (см. ниже, п.1.1a).

### 1.1a. Арматура стен фундамента/подколонников — не имеет пути захвата
**Проверка:** подтверждено (найдено этой сессией на свежем прогоне АРК). `foundation_wall_items`/

Реальная ведомость армирования ПК1 (сетка Ø12, П-хомуты Ø10, вертикальные Ø16, хомуты Ø6, выпуски,
точные длины, плотность 107,83 кг/м3) сохраняется только текстом.
**MVP:** нужно добавить вложенную арматурную группу или отдельные `foundation_wall_rebar_items`/

### 1.2. Две отдельные плиты ФП1/ФП2 вместо одной
**Находка (пользователь):** ФП1 — бетон 49,5 м3, обмазочная гидроизоляция ТОЛЬКО по торцу 7,2 м2,
PLANTER 256,0 м2. ФП2 — бетон 10,5 м3, обмазочная гидроизоляция по торцу **и по верху** 39,3 м2,

`waterproofing_extent` там нет, хотя оно уже есть в соседних `foundation_wall_items`/
`column_footing_items` (тот же паттерн, просто не применён к `slab_zones`).
**MVP:** точечно добавить `waterproofing_extent` (и, возможно, отдельные площади PLANTER/обмазочной
гидроизоляции на зону, если сейчас они общие скаляры, не по зонам — проверить перед правкой) в

### 1.3. Термовставка Т1 — нестандартная геометрия
**Находка (пользователь):** у АРК термовставка 100×400×160 (не 50/100мм раздельно, как у ЮСВ/ТРЦ),

**MVP:** нужен generic-список термовставок произвольного типоразмера — но приоритет ниже, чем казалось
изначально, т.к. только один из трёх проектов от этого страдает.

### 1.4. Земляные работы — приямки подпятников, типы песка, точка отсчёта глубины
**Находка (пользователь):** площадь котлована 413,8 м2, приямков 15,7 м2, выемка 185,0+27,5 м3, песок

## 3. Стены — новые контексты газоблока

### 3.1. Стены второго света и парапет — РАЗНЫЕ уровни, не просто "2-й этаж" — СДЕЛАНО, см. раздел 21
**Находка (пользователь):** "Стены надстройки" (h=1250мм, между +3,730 и +4,980) = 13,0 м3, арматура
114,8 м.пог. "Парапет" на уровне ПМ1 (+3,730…+4,230) = 14,8 м3, арматура 153,8 м.пог. Ещё парапет на
уровне ПМ2 (+5,160…+5,660) = 8,2 м3, арматура 85,2 м.пог, отдельный лист 22.
**MVP-предложение (пользователь):** заменить `parapet_masonry_volume_m3` (один скаляр) на
`wall_block_items[]` с контекстами `floor_1_external`, `floor_1_internal`, `floor_1_partitions`,
`second_light_walls`, `parapet_level_1`, `parapet_level_2`, `vent_cladding`.
**Проверка, уточнено 2026-07-23 — решение дешевле, чем казалось изначально.** `wall_block_items[]`
уже существует (шипнут 20 июля), роли — `WALL_BLOCK_ITEM_ROLES = {"main_walls", "floor_2", "parapet",
"partitions"}`. Проверила `wall_block_items_totals()` в коде калькулятора: она **уже суммирует
несколько строк с одинаковой ролью** (`parapet`, `floor_2`) в один общий объём для расценки — именно
то, что нужно для многоуровневого парапета. **Новые роли `parapet_level_1`/`parapet_level_2` НЕ
нужны** (беру назад более раннюю версию этого пункта) — механизм суммирования одной роли по нескольким
строкам уже реализован и протестирован.
**Подтверждено системно, не специфика АРК:** у ТРЦ та же болезнь — `parapet_masonry_volume`/
`floor_2_masonry_volume` оба `value: null, needs_review: true`, модель нашла парапет 1 этажа (5,94 м3,
арматура 47,36 м.пог) и парапет 2 этажа (13,21 м3, арматура 105,68 м.пог), не смогла выбрать одно
число для скаляра. У АРК — три отдельных зоны (стены надстройки 13,0 м3, парапет ПМ1 14,8 м3, парапет
ПМ2 8,2 м3). **ЮСВ проверено 2026-07-23, чисто**: `parapet_masonry_volume` = 22,74 м3, одно значение,
`needs_review: false`, источник — одна спецификация ("Спецификация парапетов кровли", лист 15), без
разбивки по уровням. Подтверждено дословным совпадением с реальной сданной сметой (`Сметный расчет
_ЮСВ_28.04.2026.xlsx`, лист "РС 29.04.26", строка 51: "Кладка... м3 22,74"). Значит правка промпта под
`wall_block_items[]` не должна задеть ЮСВ — он и так проходит по простому скалярному пути, регрессия
по нему должна остаться чистой.
**Реальный корень проблемы — не калькулятор, а промпт извлечения.** Модель до сих пор пытается
заполнить старое скалярное поле `parapet_masonry_volume_m3`/`floor_2_masonry_volume_m3` и корректно
сдаётся (value: null + candidates), вместо того чтобы направить данные в уже готовый
`wall_block_items[]` построчно (роль `parapet`/`floor_2`, разные `context` на уровень).
**Приоритет — выше, чем у большинства других находок в этом файле**, потому что это уже
production-поле, подключённое к реальной цене кладки газоблока (не diagnostic-only), и подтверждено
минимум в 2 из 3 реальных проектов — то есть сейчас для большинства проектов эта строка сметы вообще
не считается автоматически, требует ручной правки каждый раз.
**MVP:** правка промпта/target-заметок (`calculator_targets_compact.json`/`target_aliases_ru.yaml`) —
научить модель распознавать "несколько уровней парапета/стен надстройки без общего итога" как триггер
для `wall_block_items[]`, а не для скаляра-с-кандидатами. Изменений в `load_bearing_walls_lintels_calculator.py`
не требуется — механизм суммирования уже есть.

### 3.2. Кладочная арматура иногда общей строкой на два типа блока — ДОРАБОТАНО, см. раздел 22

**Находка (пользователь):** общие данные КР2 — "перегородки 125мм", кладочная спецификация и

## 4. Перемычки — три подтипа, не два — ДОРАБОТАНО, см. раздел 23

**Находка (пользователь):** третий подтип ПР3 (=вероятно ПМ3 из JSON, разное распознавание Р/М) —
перегородочная перемычка, арматура ф12=11,3 м.пог, **бетона нет вообще** — арматура в штробе 25×25мм,
предзаполненной клеем, не в залитом бетоне.

**Точные числа (пользователь, по скринам):**
- U-блок ПР1,ПР2 (8,5м): бетон 0,13 м3, арматура ф6(хомут)=21,6 + ф12=34,0 м.пог.
- ПР3 (перегородка, штроба): арматура ф12=11,3 м.пог, бетона нет.
- ПБ1 (2,8м): бетон 0,21 м3 + ЭППС100 0,07 м3; арматура ф6=15,8, ф12=5,6, ф16=8,4.
- ПБ2 (2,6м): бетон 0,16 м3; арматура ф6=13,3, ф12=5,2, ф16=7,8.
- Опалубка под ПБ1+ПБ2: нижняя 1,32 м2, вертикальная 2,7 м2.

**Проверка — важное разрешение открытого вопроса.** ПБ1/ПБ2 (=ПМ1/ПМ2 из ранее рассмотренного JSON,
где они шли в `floor_1_lintel_monolithic_concrete_volume`) по свежей сверке пользователя со скринами —

перемычки перегородок.** Только ПР3/ПМ3 (штроба, без бетона) относится к перегородкам. Это **снимает
риск**, поднятый ранее в вопросе Елене №2 (не ошибка ли, что ПМ1/ПМ2 попадают в приоритетную цель
несущих перемычек) — похоже, что классификация в JSON верна, тревога была ложной. Оставить вопрос
Елене как есть или отозвать — решение пользователя.

**Проверка группы:** `lintel_groove_rebar_items` **уже существует** как отдельная группа именно для
случая "перемычка без бетона/опалубки/ЭППС, только арматура" (шипнута 20 июля, diagnostic-only).
**MVP:** архитектура готова. Реально новое — перевести группу из diagnostic-only в priced, если нужно

## 6. Кровля

**Находка (пользователь):** Тип А = ЭППС CARBON PROF 200мм + LOGICROOF V-GR. Тип Б = ЭППС CARBON PROF

`roof_types[]`, у каждого свой `membrane_brand`, свой набор ЭППС-слоёв, свои примыкания/воронки.
Крупнее, чем расширение `wall_block_items` ролей (п.3.1).

гранулярность внутри одного уровня.

## Ключевой принцип, ранее нигде явно не зафиксированный — "факт данных вместо текстового признака"

**Обнаружено 2026-07-23 при разборе этажности, но принцип общий, не только про `floors_count`.**

Старый способ везде в этом пайплайне неявно строился так: найти в PDF текстовый признак ("этажность —
2 этажа", "количество этажей" и т.п.) и по нему решить, нужно ли считать какой-то блок сметы. Проблема
этого подхода — не в качестве поиска текста, а в том, что **текстовый признак и реальная инженерная
необходимость посчитать что-либо — это два разных понятия**, которые архитекторы называют по-разному
от проекта к проекту, а иногда не называют вообще (см. три разных случая ЮСВ/ТРЦ/АРК ниже).

**Правильный способ, уже проверенный на стенах (20 июля) и работающий одинаково хорошо на всех трёх
реальных проектах**: не спрашивать текстовый признак вообще. Вместо этого проверять **факт наличия
реальных структурированных данных** для того, что нужно посчитать (например: "есть ли в
`wall_block_items` строка с ролью `floor_2` с реальными числами?" вместо "что написано про этажность в
пояснительной записке?"). Если данные реально есть — считать. Если данных нет — не считать. Текст PDF
для этого решения больше не нужен вообще, ни как основной источник, ни как запасной.

**Почему это универсально устраивает разные манеры записи у разных архитекторов**: вопрос "есть ли
реальные данные" не зависит от того, как именно и в каких словах архитектор описал этажность (или не
описал вовсе) — он зависит только от того, есть ли фактически нужные цифры в спецификации. Три реальных
проекта (ЮСВ: текст вводит в заблуждение; ТРЦ: текст верен; АРК: текста нет вообще) — все три
корректно обрабатываются одним и тем же способом без специальных случаев под каждый из них.

**Где это уже применено:** стены (`floor_2`-роль в `wall_block_items`, шипнуто 20 июля).
**Где это уже применено (2026-07-24):** леса/scaffolding (п.10 ниже) — второе применение принципа,
подтверждает, что он универсален, не разовое решение для стен.
**Где стоит проверить в будущем:** любое другое место в пайплайне, где решение "считать или нет"
принимается по тексту PDF (этажность, наличие раздела, тип конструкции), а не по факту наличия
структурированных данных — по той же логике может скрываться та же проблема, что и с `floors_count`.

## 10. Этажность (`floors_count`) — РЕАЛИЗОВАНО, 2026-07-23/24

**Статус: сделано для стен (было готово с 20 июля) И для лесов (реализовано только что).** Оба пункта
ниже помечены как решённые — история проблемы и обоснование оставлены для контекста.

**Проблема, подтверждена на всех трёх проектах по-разному:**
- **ЮСВ**: PDF прямо говорит "Этажность - 1 этаж" (лист 3), но на листе 15 есть отдельная
  "Спецификация несущих стен 2-го этажа" — потому что у дома второй свет, и для расчёта кладки нужен
  второй ярус стен, хотя архитектурно дом однозначно одноэтажный. Модель честно поймала конфликт:
  `needs_review: true`, два кандидата (1 — прямой текст, 2 — по факту отдельной спецификации).
- **ТРЦ**: PDF прямо говорит "3.1. Этажность - 2 этажа" (лист 3) — и это действительно два полных
  этажа, без противоречий. Здесь текстовое извлечение работает корректно.
- **АРК**: слова "этажность" в PDF нет вообще — `floors_count` полностью `missing`, зацепиться не за
  что.
**Вывод:** три реальных проекта — три разных случая (текст вводит в заблуждение / текст верен / текста
нет). Дело не в качестве поиска слова "этажность" — "этажность" из пояснительной записки и "сколько
ярусов стен нужно посчитать для сметы" физически разные понятия, которые иногда совпадают, а иногда
нет. Текстовый парсинг не может отличить одно от другого надёжно ни при каких улучшениях промпта.

**Для стен эта проблема уже решена (20 июля), не нужно ничего чинить повторно.** Проверила код
`load_bearing_walls_lintels_calculator.py`: если `wall_block_items[]` содержит строку с ролью
`floor_2`, второй ярус стен считается автоматически, **независимо от значения `floors_count`** —
именно так был исправлен случай АРК (`floors_count` отсутствует физически). Второй этаж/второй свет
собирается корректно вне зависимости от того, распознана ли этажность текстом.

**Но `floors_count` всё ещё напрямую управляет лесами (scaffolding)** — отдельная строка сметы,
количество ярусов и объём пиломатериала считаются как `floors_count × норма_на_этаж`, это не завязано
на `wall_block_items` вообще.

**Ранее согласованный план (память `floor_2_walls_incomplete_and_floors_count_risk`, 8 дней назад) —
неполный.** Предлагал сделать `floors_count` чисто ручным полем, убрав автопарсинг. Проблема: это не
убирает риск, а переносит его — по умолчанию в калькуляторе `floors_count = 1`, и если забыть
выставить руками, леса тихо посчитаются на один ярус меньше именно для тех же случаев (второй свет,
второй этаж), где раньше подводило автоизвлечение.

**Сделано, 2026-07-24.** Вместо отдельного ручного поля `floors_count` для лесов — количество ярусов
лесов теперь выводится из того же признака, что уже используется для стен: наличие `wall_block_items`
с ролью `floor_2`. `calculate_scaffolding()` в `load_bearing_walls_lintels_calculator.py` принимает
`wall_block_totals` и, если он передан (то есть `wall_block_items` реально используется в этом
расчёте), берёт количество ярусов из факта наличия `floor_2`-роли (2, если есть; 1, если нет) —
**значение `floors_count` при этом полностью игнорируется**. Если `wall_block_items` не используется
(старые/простые проекты) — поведение байт-в-байт как раньше, `floors_count` работает как обычно.

Новое поле в результате `scaffolding.floors_count_source` показывает, откуда взято число
(`"wall_block_items"` или `"floors_count"`), `floors_count_input` сохраняет исходное значение
`floors_count` для прозрачности, даже когда оно было проигнорировано.

Добавлен новый регрессионный кейс `test_scaffolding_from_wall_block_items`, специально
воспроизводящий сценарий АРК: `floors_count = 1` (заведомо неверное/устаревшее значение), но
`wall_block_items` содержит реальную строку `floor_2` (12,5 м3) — подтверждено, что леса корректно
считаются на 2 яруса, а не на 1. Полная регрессия: 19 из 19 успешно выполняемых кейсов (3 отдельных
негативных кейса на некорректный ввод по-прежнему падают ожидаемо, не связаны с этой правкой) — 0
расхождений.

**Статус:** и стены, и леса теперь определяются одинаково — по факту наличия данных, не по тексту PDF
и не по отдельному ручному полю, которое можно забыть заполнить.

### 11.3. wall_block_items — та же дыра, что и slab_zones, но с находкой посерьёзнее (этаж 2, D500) — РЕШЕНО

По просьбе Елены проверила, есть ли у `wall_block_items` та же дыра, что была у `slab_zones` — да, есть:
в `calculator_targets_compact.json`/`target_aliases_ru.yaml` этой цели не было вообще, только старые
скаляры `floor_2_masonry_volume`/`parapet_masonry_volume`/`parapet_gas_block_d500_250_volume`. В JSON
ТРЦ и АРК тот же симптом (`value: null` + несуммированные `candidates`) для парапета на 2 уровнях — но
дополнительно нашла кое-что серьёзнее.

**Парапет (случай А, безопасный, как slab_zones):** ТРЦ парапет 1эт 5,94 + 2эт 13,21 = смета
«Парапет» 19,15 м3 одной строкой; АРК ПМ1 14,8 + ПМ2 8,2 = смета 23,0 м3. Оба чистый D400, калькулятор
уже умеет и суммировать, и считать цену — только цели извлечения не было.

**Этаж 2, D500 (случай Б, требовал калькулятор до extraction-фикса):** прочитала PDF ТРЦ
(`КР2_ТРЦ_30,06,2026`, стр. 8) напрямую — этаж 2 реально имеет и D400 (50,71 м3, наружные стены), и
D500 (10,95 м3, внутренние несущие стены — тот же принцип "снаружи D400/внутри D500", что и на 1
этаже). Реальная смета ТРЦ (`НС 29.06.26`, строка 116) уже сегодня вручную считает эту D500-строку:
10,8 м3 × 5500 = 59 400₽. Проверила код: `WALL_BLOCK_ITEM_PRICED_KEYS` **намеренно** не включал
`("floor_2","D500")` — калькулятор упал бы с `ValueError` вместо того, чтобы молча потерять объём
(это доказывал негативный тест `test_wall_block_items_unsupported_combination_rejected`). Проверила
АРК — там "Надстройка 2 света" только D400 (13,0 м3, ни в PDF, ни в смете D500 нет), этой проблемы у
АРК нет.

**Правка внесена в 2 шага, с полным подтверждением пользователя ("давай это дорабатывай, чего уж
ждать"):**
1. **Калькулятор** (`load_bearing_walls_lintels_calculator.py`) — добавила `("floor_2","D500")` в
   приоритетные ключи; `floor_2_total_masonry_volume_m3` (D400+D500 объединённо) теперь двигает
   единую строку кладки (совпало с реальной сметой ТРЦ день-в-день: 61,66 м3 = 50,71+10,95); материал
   остаётся раздельно по плотности — новая строка `floor_2_gas_block_d500_material` (тот же прайс-код
   `gas_block_d500_m3`, что и D500 у основных стен/парапета); клей теперь считается от объединённого
   объёма. Старый негативный тест удалён (он проверял именно то поведение, которое теперь намеренно
   изменено), заменён новым позитивным `test_floor_2_d400_d500_mixed`, построенным на реальных цифрах
   ТРЦ. Полный прогон: 20/20 кейсов, 0 расхождений — легаси-путь (без `wall_block_items`) не задет.
2. **Extraction** — только после того, как шаг 1 закрыл ценовой разрыв, добавила `wall_block_items`
   как цель извлечения (`calculator_targets_compact.json`/`target_aliases_ru.yaml`), с указанием: какие
   сочетания role+density уже посчитаны (main_walls/floor_2/parapet × D400/D500), что несколько строк
   с одинаковой role+density суммируются автоматически, и когда использовать эту группу вместо старых
   скаляров.

Отвечая на вопрос "там только конкретные блоки принимаются или любые размеры?" — калькулятор понимает
только `block_density` D400/D500 (`WALL_BLOCK_ITEM_DENSITIES = {"D400","D500"}`), каждая плотность
жёстко привязана к одному размеру блока и одной цене (D400 = 600×400×250, D500 = 600×250×250 — правило
Елены от 15.07: другого размера у этих плотностей не бывает). Поле `block_size` в данных есть, но это
просто текст для справки, на расчёт не влияет. Если в проекте встретится действительно другая
плотность/размер (не D400/D500) — калькулятор откажется считать (сделано специально, чтобы не терять
деньги молча), это отдельный, ещё не встречавшийся случай.

**ОТВЕТ ЕЛЕНЫ, 2026-07-28: могут быть другие размеры/плотности, но очень редко.** Вопрос был задан
2026-07-24 — жёсткая привязка "D400 всегда 600×400×250, D500 всегда 600×250×250" не универсальна,
есть редкие исключения для `main_walls`/`floor_2`/`parapet`.

**Реализовано, 2026-07-28 (пользователь: "давай делать вариант, когда принимает любые блоки").**
`wall_block_items[].block_density`, отличный от D400/D500, теперь разрешён — но только если строка
несёт свою собственную `material_unit_price` (новое опциональное поле `WallBlockItem`). Без цены на
такой строке — калькулятор по-прежнему падает с понятной ошибкой (та же философия "не терять деньги
молча", просто теперь есть законный выход из неё). D400/D500 полностью не тронуты — если проект их и
не использует, поведение побайтово прежнее.

Редкий блок получает свою собственную ценовую строку (`wall_block_other_<role>_<index>`) — цена
берётся прямо из данных проекта, без округления по поддонам (это не стандартный SKU с известным
объёмом поддона, а одноразовый материал). Работа кладки (одна строка независимо от плотности,
существующий принцип для D400+D500) теперь суммирует и редкий объём тоже — во всех трёх ролях
(`main_masonry_volume`, `floor_2_total_masonry_volume`, `parapet_total_masonry_volume`).

**Попутно нашла и исправила тот же класс риска, что и у "фактов данных вместо текстового признака"
(принцип выше) — в двух местах гейтинг проверял только D400:**
1. `floor_2_enabled` (решает, считать ли весь раздел 2-го этажа вообще) проверял только
   `wall_block_totals["floor_2_d400"] > 0` — если 2-й этаж целиком из редкого блока, раздел бы
   тихо не включился вообще (не просто леса, а вся кладка/клей/арматура 2-го этажа).
2. **Леса** (`calculate_scaffolding`, тот самый вопрос "могут ли леса ещё как-то ловить второй

   (раз D400/D500-объём есть, условие всё равно истинно).
3. `parapet_enabled` уже проверял D400 ИЛИ D500 (не только D400) — дополнен третьим условием

Новый регресс-кейс `test_wall_block_items_rare_other_density` (floor_2 целиком из условного блока
D350/600×350×250 с явной ценой) подтверждает разом: `floor_2_load_bearing_walls.enabled = true`,

`floors_count_input: 1`), новая строка `wall_block_other_floor_2_4` посчитана по данной цене. Пара
негативный кейс `test_wall_block_items_rare_density_missing_price_rejected` подтверждает падение без

ожидаемо (было 3, +1 новый).

### 11.5. К2/К3 на листе 14 ТРЦ — на самом деле дренаж под чужим ярлыком — БЕЗ ИЗМЕНЕНИЙ (по решению Елены)

Находка Елены: ТРЦ, стр. 10 — «К2,К3 (в 1-й траншее)» 31,85 п.м / 13,37 м3, реально канализация К2

Проверила JSON: extraction уже не поверил ярлыку слепо — вторая строка сохранена под отдельным

не стоит стремиться к автоматической точности выше текущей — `needs_review` + запись в служебную
записку уже достаточны, т.к. Елена всё равно пересобирает эти строки руками при финализации. Не значит
"не искать баги" — просто не предлагать доработки точности захвата коммуникаций/траншей без явного

## 22. Находка 3.2 — подоконное армирование в общую сумму, перегородки — никогда, найден риск коллизии кода (2026-07-26)

Раньше (07-23) вопрос про комбинированную строку «Блок 400+250» был снят — `component` описывает роль
стены, не ширину блока, конфликта схемы нет. Осталось решить только «подоконное армирование» (4,4

главное собрать всю сумму по арматуре... Перегородки не берем и не считаем в общую сумму, подоконное
армирование пишем в общую сумму (пусть в 1 этаж, если не указано другое)».

**Побочная находка при проверке — реальный, ранее не документированный риск коллизии в
`main_wall_rebar_items`.** `calculate_main_wall_reinforcement()` в `load_bearing_walls_lintels_calculator.py`
кладёт контрольные суммы в словарь `controls`, ключ — авто-сгенерированный `line_code` из
`floor+component+steel_class+diameter_mm`. Если добавить подоконное армирование как ещё одну строку с
тем же floor/component/диаметром, что и основная комбинированная строка (оба ф10, этаж 1), без явного
`code` — обе строки получат ОДИНАКОВЫЙ `line_code`, и вторая тихо перезапишет контрольные значения
первой (`main_wall_rebar_base_length_m`/`order_length_m`/`delivery_weight_kg`). Проверила: сами
ценовые строки сметы (`rebar_lines`) при этом не теряются (не дедуплицируются), то есть деньги не
портятся, но контрольные/отладочные цифры станут неверными. `main_wall_rebar_delivery_weight_kg` нигде
больше в файле не используется для расчёта — риск ограничен контрольными числами, не ценой.

**Перегородочная арматура — это тот же баг, что уже описан в `HANDOFF.md` (2026-07-22, ещё не
исправлен):** реальный прогон извлечения когда-то пометил арматуру перегородок как `load_bearing_walls`
вместо `partitions`, и она тихо прошла мимо гвардрейла калькулятора (`validate_spec_rebar_item` жёстко
отклоняет только явный `component == "partitions"`), попав в цену несущих стен.

**Правка — только промпт** (`chat_extraction_poc/data/target_aliases_ru.yaml` +
`calculator_targets_compact.json`, живой источник):
- комбинированная строка 400+250 — без изменений, уже работает;
- подоконное армирование — включаем в `main_wall_rebar_items`, `component: load_bearing_walls`, этаж 1
  по умолчанию, но с явно заданным уникальным `code` (например с суффиксом `_subwindow`), если floor+
  component+диаметр совпадают с другой строкой — закрывает найденный риск коллизии;
- в `negative_context` добавлено «перегородк»; в notes — явный запрет заносить арматуру перегородок в
  эту группу под `component: load_bearing_walls`/`lintels` ни в каком виде, с прямой ссылкой на
  известный прошлый случай, чтобы не повторился.

Изменений в `load_bearing_walls_lintels_calculator.py` не потребовалось — риск коллизии решается на
уровне промпта (уникальный `code`), без правки кода. Гигиена данных проверена — чисто.

**Структурная защита в коде добавлена, 2026-07-27 (пользователь: "надо сделать").** Промпт-инструкция
снижает риск, но не устраняет его физически — если модель (или ручной ввод) когда-нибудь не выставит
уникальный `code`, тихая перезапись контрольных чисел была бы всё ещё возможна. Теперь
`calculate_main_wall_reinforcement()` явно проверяет коллизию `line_code` в цикле построения `controls`

  перекрытия 1 этажа (Балки)») балки поимённо есть (Б1.1, Б1.2, Б2, Б3, Б4, Б5, Б6, Б7, Б8) с сечениями
  в подписях («Б2 400х700» и т.п.), но их **длина** — это повёрнутый размерный текст на чертеже,
  который через текстовый слой PDF читается перевёрнуто/склеенно (та же проблема, что была с Б4/Б4-1

**Суть проблемы**: с 28.07 работа «Бетонирование балки» считается по суммарной длине балок (мп × 1500
руб, см. правило Елены выше) — а для ТРЦ эту суммарную длину физически неоткуда взять из текущего PDF
ни автоматически, ни вручную через текстовый слой. Это не решается доработкой парсера или промпта —
нужен либо исходный CAD-файл, либо отдельная спецификация балок от проектировщика/Елены с длиной
каждой балки (как у ЮСВ на л.22), либо ручной замер по чертежу.

быть посчитана корректно — блокирует счёт по этому проекту, не только диагностика. Секционный override

пока НЕ добавлен в код — решили не делать, пока не появится реальный источник данных для его
заполнения (см. раздел 39, что сделано вместо этого сейчас).

## 39. `beam_items` — ширина необязательна, готовый объём/опалубка на строку принимается как есть (2026-07-28)

Продолжение разбора Б4/Б4-1 (раздел 27) и сверки с ЮСВ/ТРЦ (раздел 38). Пользователь спросила: зачем
вообще требовать длину/ширину/высоту у каждой балки, если готовые числа часто уже даны в спецификации?
Разбор показал — да, во многих реальных случаях (ЮСВ полностью, АРК частично) готовый объём бетона на
конкретную балку уже есть в PDF, а `beam_items` раньше **всегда** пересчитывал его из `длина×ширина×
высота`, игнорируя готовое число и требуя ширину обязательно (`width = d(item["width_m"])` — падал при
`null`).

**Изменение**: `width_m` стало необязательным полем. Если у строки дан готовый `concrete_volume_m3` —
берём его как есть, не пересчитываем. Если ширины и готового объёма нет одновременно — ValueError
(бетон для строки должен быть определим хоть как-то). Аналогично `formwork_area_m2` — готовое число
имеет приоритет; если и его, и ширины нет — опалубка для этой строки просто 0 (не блокирует), реальные
деньги по опалубке в этом случае берутся из секционного override `beams_formwork_area_m2`.

Длина и высота остаются обязательными всегда — они не зависят от ширины и нужны для работы
«Бетонирование балки» (мп) и утепления балок, которые считаются независимо от объёма бетона.

Закрывает: АРК Б4/Б4-1 (ширина неизвестна, но готовый бетон 5,3 есть — теперь можно вписать как есть)
и ЮСВ (готовые числа по каждой балке теперь используются напрямую, без риска расхождения из-за
округления при пересчёте). НЕ закрывает ТРЦ — там нет длины ни в каком виде, см. раздел 38.

**Побочная находка при тестировании на реальных числах ЮСВ**: наивный пересчёт опалубки
(`длина×(ширина+2×высота)`) даёт 27,992 м2 для трёх балок ЮСВ, а готовые числа из спецификации —
только 22,04 м2 (Б-1/Б-2/Б-3: 3,8+10,1+8,14). Разница ~6 м2 — реальные деньги. Теперь, когда готовое
число дано на строку, оно побеждает пересчёт, что и должно точнее соответствовать факту из PDF.

Изменения в `floor_slab_1_calculator.py` и `floor_slab_2_calculator.py` (парность) + обновлены
extraction-таргеты (`calculator_targets_compact.json`, `claude_extraction_output_schema.json` —
добавлены поля `concrete_volume_m3`/`formwork_area_m2` в `beam_items`/`floor_slab_2_beam_items`,
заметка про необязательную ширину), чтобы ChatGPT-извлечение знало пользоваться готовыми числами, а не
только код калькулятора.

Полная регрессия зелёная: floor_slab_1 — 14/14 кейсов (включая 2 новых:
`test_floor_slab_1_beam_items_ready_values` на реальных числах ЮСВ КР2 л.22,
`test_floor_slab_1_beam_items_no_width` на реальных числах АРК КР2 л.14 с Б4/Б4-1); floor_slab_2 —
11/11 кейсов (аналогичная пара новых кейсов, порт той же логики). Плюс отдельно проверено, что
`ValueError` корректно срабатывает в обоих калькуляторах, если у строки нет ни ширины, ни готового
`concrete_volume_m3` одновременно.

### Дополнение 2026-07-29 — Б4/Б4-1 у АРК не делим без проектировщика

Пользователь уточнила: в АРК бетон есть по каждой балке, кроме Б4 и Б4-1 — они в спецификации даны
общей строкой. Раздельную спецификацию Б4/Б4-1 пользователь запросила у проектировщика.

Решение для production:

- не выдумывать разбиение общего бетона Б4/Б4-1 между двумя балками;
- если PDF даёт одну объединённую строку Б4/Б4-1, хранить её как одну строку `beam_items` с
  `needs_review`/manual split note;
- `width_m` для такой строки можно оставлять `null`, если есть готовый `concrete_volume_m3`;
- `count: null` в калькуляторах теперь трактуется как 1, потому что строка спецификации уже является
  одной позицией/маркой, а не нулевым количеством;
- работа «Бетонирование балки» считается по длине в м.п. — для неё ширина и бетонный объём не нужны;
- утепление торца балок считается от длины и высоты, ширина не нужна;
- бетон как материал берётся из готового `concrete_volume_m3`; если его нет и ширины нет, калькулятор
  должен падать/требовать ручного уточнения, а не подтасовывать.

Что изменено: оба калькулятора плит принимают `count: null` как 1; `section_contract.yaml` для
floor_slab_1/floor_slab_2 показывает в строках балок колонки `concrete_volume_m3` и `formwork_area_m2`;
`target_aliases_ru.yaml` явно говорит модели класть готовый бетон/опалубку в строку балки и не делить
объединённые Б4/Б4-1 без отдельной спецификации.

## 40. Балки и монолитные перемычки — утепление отдельной длиной, не всей длиной элемента (2026-07-29)

Елена уточнила универсальное правило:

> монолитные перемычки и балки не всегда утепляются; если утепляются, то не всегда по всей длине.
> У Г-образных и Т-образных балок может утепляться только часть, которая находится с улицы.

Что это меняет в production:

- `beam_items.length_m` используется для работы по бетонированию балок в м.п.;
- `beam_items.length_m` **нельзя** автоматически использовать как длину утепления балок;
- для утепления балок добавлены отдельные optional-поля:
  `floor_slab_1_beams_eps_work_length`, `floor_slab_1_beams_eps_material_area`,
  `floor_slab_2_beams_eps_work_length`, `floor_slab_2_beams_eps_material_area`;
- если PDF/смета дают отдельную длину или площадь утепления балок — использовать её;
- если балки не утепляются — значение должно быть 0 или отсутствовать с явной проверкой, а не
  автоматически равно общей длине балок;
- монолитные перемычки уже разведены на две длины:
  `floor_X_lintel_monolithic_total_length_m` для бетонирования и
  `floor_X_lintel_monolithic_insulation_length_m` для утепления;
- `floor_X_lintel_monolithic_insulation_length_m` — это только утеплённая часть, не общая длина всех
  монолитных перемычек.

Что изменено:

- оба калькулятора плит принимают optional override для утепления балок:
  `beams_eps_work_length_m` и `beams_eps_material_area_m2`;
- если override отсутствует, старый fallback по всем балкам пока сохранён для обратной совместимости
  старых тестов/кейсов, но contracts/aliases требуют искать фактическую утеплённую часть;
- `section_contract.yaml` для floor_slab_1/floor_slab_2 получил новые review parameters по утеплению
  балок;
- `calculator_targets_compact.json` и `target_aliases_ru.yaml` получили новые target_code и правило:
  не подставлять общую длину балки вместо утепляемой части;
- в `load_bearing_walls_lintels/section_contract.yaml` и aliases убрана старая формулировка
  «монолитные перемычки всегда утепляются».

## 41. Лист 01: `required` ничем не подкреплён + план "секция применима ли к проекту" (2026-07-29)

Пользователь попросила проверить на свежем извлечении АРК (файлы `gpt_arkadia_extraction(2).json` /

полную цепочку по балкам и монолитным перемычкам: бетон (материал+работа), опалубка (материал+работа),

**Структура подтверждена правильной** — у балок и перемычек действительно есть все три пары
(материал/работа) и они верно связаны с калькулятором. Найдено при этом:

### 41.1 Реальный баг — асимметричная проверка в `calculate_monolithic_lintel_block`

```python
if concrete_volume > 0 and total_length_m is None:
    raise ValueError(...)
enabled = concrete_volume > 0 or total_length > 0
```

Проверка работает только в одну сторону. Реальный кейс АРК: `floor_1_lintel_monolithic_concrete_volume`
= null (общего бетона ПБ1+ПБ2 в PDF нет, только 0,21+0,16 раздельно — оставлено needs_review по
правилу «не складывать самой»), `floor_1_lintel_monolithic_total_length` = 5,4 — есть. Результат:
`enabled=True` по длине, **бетон-материал молча = 0**, а работа по бетонированию (по длине 5,4 мп)
**считается и оплачивается**. Реальные деньги на бетон монолитных перемычек теряются молча, без
единой ошибки. **Статус: НЕ ИСПРАВЛЕНО, план ниже.**

### 41.2 Мелкий баг — минимум клей-пены заказывается даже без утепления

`foam_units = max(min_units, ceil(foam_raw)) if enabled else 0` — `enabled` общий с бетоном/длиной, а
не свой у утепления. Если у монолитной перемычки нет утепления вообще (`insulation_length_m=0`), но
блок всё равно `enabled` (из-за бетона/длины), клей-пена всё равно закажется по минимуму (обычно 1
баллон). Небольшая сумма, но неверная. **Статус: НЕ ИСПРАВЛЕНО, план ниже.**

### 41.3 Главная находка — `required` в `section_contract.yaml` нигде не читается

Пользователь спросила: «почему калькулятор может падать, если он всё получит на 100%?» — проверка
показала: **поле `required: true/false` и `status_if_missing` не читаются НИ В ОДНОМ .py-файле пайплайна**
(`build_review_workbook_from_contracts.py`, `populate_review_workbook_from_extraction.py`) — это чистая
документация в YAML, ничего не проверяет и ничего не подсвечивает. Статус на листе 01 —
только «Найдено» / «Проверьте (needs_review)» / «Не найдено» — зависит исключительно от того, нашла ли
модель значение при извлечении, а не от того, обязательно ли поле физически. «Не найдено» у
по-настоящему нужного поля и «Не найдено» у неприменимого к проекту поля выглядят одинаково — Елена не
может отличить одно от другого, не читая PDF заново.

## 46. Реальная причина «ошибки чтения» в Excel — конфликтующие merge_cells (2026-07-29)

Пользователь удалила предыдущий xlsx: "старую я удалила, там была ошибка чтения какая-то". Не стал
просто пересобирать вслепую — сначала проверил файл на структурные проблемы.

**Нашёл настоящую причину, не догадка**: `openpyxl` при чтении собранного файла показал реальные
пересекающиеся диапазоны `merge_cells` на нескольких листах — например строка 5 листа 01 имела
ОДНОВРЕМЕННО `A5:N5` и `A5:S5`. Причина: и `append_section_band` (в момент создания строки, когда
финальная ширина листа ещё не известна — она растёт позже, когда добавляются item-блоки с
дополнительными колонками), и `restyle_section_bands` (в конце, уже с финальным `ws.max_column`)
мерджили одну и ту же строку — но на РАЗНУЮ ширину. `openpyxl.merge_cells` не кидает исключение при
повторном мердже на другую ширину (только при точном дубликате того же диапазона) — он молча
записывает второй, пересекающийся диапазон. Это делает xlsx структурно невалидным для Excel (хотя
`openpyxl` сам читает такой файл без единой жалобы) — отсюда "ошибка чтения" у пользователя. Тот же
баг нашёлся и на листе 05 (`style_block_title_row`/`restyle_block_sheet`, тот же паттерн двойного
мерджа, независимо обнаружен тем же способом).

**Исправлено системно, не точечно**: вместо try/except вокруг повторного мерджа (это ловило только
идентичный повтор, не разную ширину — старый баг, введённый мной же в этой сессии раньше, при первом
design-проходе), новая функция `_merge_row_full_width(ws, row_idx, max_col)` — сначала снимает ЛЮБОЙ
существующий merge, затрагивающий эту строку, потом мерджит заново. Безопасно при любом порядке и
количестве вызовов, не только для текущих двух путей (section band + block title). Используется и в
`_style_section_band_row`, и в `style_block_title_row`.

**Проверено**: прогнал по всем 8 листам (и пустой шаблон, и реальный ARK) программную проверку всех
`merged_cells.ranges` попарно на пересечение — 0 пересечений на обоих билдах (было 8 на реальном ARK
до фикса). `unzip -t` подтверждает валидность zip-контейнера (это не проверяет xlsx-специфичную XML-
валидность, но пересекающиеся merge — это именно XML-уровня проблема, которую нашёл).
