# Отчёт по Earthworks Parser Google Stage 1

Дата: `2026-06-19`.

## Кратко

В проекте `ai-estimator-mvp` создан и доведён до рабочей формы отдельный изолированный контур:

```text
experiments/earthworks_parser_google_stage1/
```

Он нужен для честной проверки параметров раздела **Земляные работы** по PDF проекта, сборки review workbook и публикации Google Sheet для Елены.

Главная идея stage1:

```text
PDF проекта
→ parser / адаптер данных
→ review workbook для проверки
→ Google Sheet с human-review и diagnostics
```

Этот контур не считает смету и не пишет данные обратно в общий `price_registry`. Его задача - подготовить проверяемые входные данные, показать источники и сомнения, а затем дать удобную Google Sheet для ручной проверки.

## Что уже сделано

Собран изолированный review-flow именно для `earthworks`:

- `prepare` строит свежий `review_workbook.xlsx`;
- `clean` удаляет только generated jobs и не трогает секреты, исходные PDF и код;
- Google Sheet публикуется через OAuth Desktop App;
- workbook и builder синхронизированы по утверждённой структуре;
- anti-cheat проверяет, что workbook не расходится с кодом;
- stage1 не запускает расчёт сметы;
- stage1 не изменяет общий `price_registry`.

## Структура workbook

Актуальный workbook stage1 сейчас строится с такими листами:

```text
00_Конструктор сметы
01_Проверка проекта
02_Цены себестоимости
03_Детали объемов
04_Инструкция
05_Кандидаты parser
06_Сырые данные parser
```

Лист `07_Лог parser` не используется.

### Листы 01–04

Это человекочитаемая часть для Елены:

- `00_Конструктор сметы` - каркас будущего конструктора разделов;
- `01_Проверка проекта` - проектные параметры и объёмы с action-based статусами;
- `02_Цены себестоимости` - плоский список реальных ценовых компонентов с ручной правкой цены;
- `03_Детали объемов` - справочная детализация траншей и коммуникаций без колонок ручных исправлений;
- `04_Инструкция` - краткая инструкция по работе с таблицей.

### Лист 05

`05_Кандидаты parser` - технический, но читаемый лист для разработчика:

- короткие значения вместо JSON-простыней;
- понятные статусы кандидатов;
- правила поиска;
- короткие фрагменты;
- evidence и candidate ids.

### Лист 06

`06_Сырые данные parser` - raw-технический лист:

- summary запуска;
- logical sheets;
- extracted parameters raw;
- evidence raw contexts;
- full JSON values.

Этот лист хранит полный raw OCR и full JSON отдельно от коротких диагностических значений.

## Clean-run и публикация

Для stage1 добавлен безопасный рабочий цикл:

- можно удалить только generated jobs;
- можно заново прогнать `prepare`;
- можно опубликовать свежую Google Sheet;
- можно проверить workbook локально и по ссылке.

В последнем чистом прогоне:

- создан новый job;
- собран свежий `review_workbook.xlsx`;
- опубликована новая Google Sheet;
- анти-чек прошёл без ошибок.

## Что проверяет anti-cheat

Анти-чек этого stage1 подтверждает:

- что workbook и builder совпадают;
- что лист 05 не содержит JSON-простыней;
- что лист 06 хранит summary/raw/full JSON в отдельных блоках;
- что листы 01–04 не сломаны;
- что stage1 не использует запрещённые legacy-пути как source of truth;
- что technical sheets не скрыты и пригодны для диагностики.

## Что сознательно не входит в stage1

- Telegram-бот;
- общий `price_provider` для всего проекта;
- расчёт сметы после review;
- back-write найденных цен в общий `price_registry`;
- изменения `parser core` вне этого review-flow;
- интеграция с другими разделами сметы.

## Результат последнего прогона

Последний clean-run сформировал опубликованную Google Sheet и проверочный workbook в job-папке.

Проверенные листы:

- `01_Проверка проекта` - action-based статусы, источник и фрагменты;
- `02_Цены себестоимости` - один список реальных ценовых компонентов;
- `03_Детали объемов` - единая справочная таблица без ручных исправлений;
- `05_Кандидаты parser` - читаемые candidates без JSON-простыней;
- `06_Сырые данные parser` - raw evidence и full JSON в отдельных блоках.

## Зачем это важно

Этот слой закрывает промежуточную проверку между извлечением данных из PDF и будущим расчётом сметы.

Именно здесь мы добиваемся:

- честного извлечения данных;
- прозрачных источников;
- читаемого human-review;
- отсутствия тихих подстановок;
- reproducible clean-run;
- стабильного Google Sheet для Елены и разработчика.

## Следующий шаг

После stage1 логичный следующий слой - подключение этих данных к расчётному контуру и будущему Telegram-боту, но без потери разделения ролей:

→ проверенные параметры
