содержащий полный АР (архитектурные решения) + КР1 + КР2 в одном PDF, а не

Диагностические категории (report-only, не меняют `section_code`,

## A4.2.7 — generic candidate cleanup (два воспроизводимых бага)

Оба бага воспроизводились на всех трёх проектах (USV/TRC/MKP1), значит не
являются подгонкой под MKP1.

### 1. Dimensions-filter gap

`_has_useful_primary_quantity()` вызывалась на сырых `quantities` (до
фильтрации), которые могут содержать элемент `kind='dimensions'`
(например, "90х195"). Такой элемент проходил проверку "есть полезное
значение", но затем отбрасывался при построении `value_candidates` —
кандидат оставался `route_summary`/`pipe_item`/`material_quantity`, хотя
реально сохранённых полезных значений в нём не было.

Фикс: проверка теперь выполняется на уже отфильтрованных
`value_candidates`. Для `route_summary`/`pipe_item` при провале проверки —
кандидат становится `diameter_spec` (как и раньше для чистого
диаметра/отметки). Для `material_quantity` естественного запасного типа
нет — кандидат просто не создаётся.

### 2. Route-label / АР opening-code collision

Короткие коды-маршруты (К1, В1, ЭО) генерик-паттерна совпадают с кодами
проёмов из ведомостей АР (например, "В-1" как обозначение двери). На
USV/TRC (КР-only) это не проявлялось — ведомостей проёмов там просто нет.

Фикс: короткие коды-маршруты теперь требуют инженерный контекст рядом
(трасса/канализация/водоснабжение/дренаж/труба/ввод/инженерные сети/
коммуникации — либо уже существующие в модуле сигналы длины/глубины/
объёма/площади/итого) и никогда не считаются маршрутом рядом с
АР-контекстом ведомости проёмов (ведомость дверных/оконных проёмов,
габариты проемов, фасад, коды ОК-/ДН-/ДВ-). Полнословные метки
(Дренаж, Канализация, Водоснабжение, Эл. кабель) по-прежнему не требуют
доп. контекста, но тоже подавляются рядом с ведомостью проёмов.

## A4.2.7.1 — guard на марку бетона (В22/В25 vs В1/В2 route label)

Марка бетона (`Бетон В22,5`, `В25` — ГОСТ 26633) проходила как route_summary,
потому что рядом обычно есть объём в м³, который удовлетворял
engineering-context guard'у из A4.2.7. Добавлена отдельная проверка:
короткий код `В<число>` рядом со словом "бетон"/"ГОСТ 26633"/суффиксами
марки (`W6`, `F150`, `П4`) не считается route label вне зависимости от
остального контекста на той же строке/странице.

4 новых теста (два подтверждают подавление марки бетона, два — что
легитимные `В1 трасса водоснабжения`/`В1 длина... глубина...` по-прежнему
создают route_summary). Тесты: 217 + 35, все зелёные.

Все прямые случаи "Бетон В22,5 W6 F150 П4 ... м3" / "Бетон В25 ... м3" в
USV/TRC/MKP1 подтверждены исправленными (адресная проверка по кандидатам,
не только по счётчикам).

### Остаточные "В+число" route_summary — другая причина, не в этом шаге

После фикса в USV/TRC остаётся по несколько `route_summary` с
subject_hint вида `В0`, `В505`, `В1`, `В0029` — это **не** марка бетона:

- часть — искажённый при PDF-экстракции текст со схем генплана (наложенные/
  повёрнутые подписи превращаются в цифровой шум при линейном
  text-extraction, не парсер-баг в строгом смысле);
- часть — похоже на ссылки на координационные оси чертежа (А/Б/В/Г/Д ×
  1–7) или на смешанные данные из ведомостей помещений/вертикальных
  поверхностей, склеенные с буквой "В" при экстракции.

Ни то ни другое не входило в согласованный скоуп A4.2.7.1 (только марка
бетона) — фиксирую как возможный кандидат для A4.2.8, отдельно от
concrete-grade и door-schedule коллизий.

### Независимая проверка закрытия A4.2.7.1 (2026-07-06)

Внешний ревью (GPT) предложил 7 тестов на закрытие A4.2.7.1. Проверка
показала: 6 из 7 уже проходили на уже закоммиченном коде без единой

### Про unknown и "review table" — точная формулировка

`resolver_engine.py` не блокирует `section_code=unknown` жёстко —
`_apply_section_scoring()` для `unknown`/`floor_slab_unknown` возвращает
`(score, needs_review=True)`, то есть такой кандидат может быть выбран
resolver'ом как значение параметра, просто с пометкой на проверку.

Но: **это пока design intent, а не факт.** Ни одна таблица, которую видит
человек (Елена), сейчас не подключена к этому evidence/candidate/resolver
слою — см. п.0.12 `current_project_state.md`. Правильная формулировка:

- unknown-кандидаты не потеряны технически — они лежат в JSON и могут быть
  выбраны resolver'ом с `needs_review=True`;
- но пока не построен A5 (review table), человек их не видит;
- **требование к A5**: review table обязана явно показывать
  resolved unknown-section кандидатов как строки `needs_review`, а не
  молча их прятать.

### Границы: старый Google Sheet / Telegram-flow (0.11) не трогаем

Экспериментальный evidence/candidate/resolver слой (0.12) — параллельный
контур. На этом шаге и далее, пока явно не решено иначе:

- не меняем структуру существующей Google-таблицы земляных работ, формулы,
  ручной flow;
- не меняем `earthworks_v3_adapter.py` и действующий production
  Telegram-flow (0.11);
- можно менять/добавлять только в новом слое: candidates, raw_text/source/
  evidence, resolver output, новые отчёты.

Будущая all-sections review table (A5) — отдельный новый экспорт, не
замена текущей Google-таблицы на этом шаге.
