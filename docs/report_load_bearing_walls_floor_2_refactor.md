# Отчёт: блок несущих стен 2-го этажа вместо legacy second_light

Дата: 2026-06-10

## Что было

В старом ЮСВ-кейсе использовались поля:

- `second_light_masonry_enabled`;
- `second_light_masonry_case_specific`;
- `second_light_masonry_volume_m3`.

Фактически этот блок использовался как кладка верхнего уровня / 2-го этажа, но название `second_light` было case-specific и не подходит для production.

## Что стало

Production поддерживает только:

- `floors_count = 1`;
- `floors_count = 2`.

`floors_count = 3` запрещён validation:

```text
floors_count must be 1 or 2. Three-storey houses are out of MVP scope.
```

Для production добавлен режим:

```text
upper_floor_calc_method = floor_2_spec_volume
```

Логика:

```text
if floors_count == 1:
    floor_2_load_bearing_walls_enabled = false

if floors_count == 2:
    floor_2_load_bearing_walls_enabled = true
```

Объём кладки 2-го этажа берётся из спецификации:

```text
floor_2_masonry_volume_m3
```

## Парапет

Старое поле `parapet_enabled` оставлено для legacy.

Production-режим:

```text
parapet_calc_method = flat_roof_spec_volume
parapet_enabled_calculated = flat_roof_enabled and parapet_masonry_volume_m3 > 0
```

`parapet_masonry_volume_m3` является проектным параметром из спецификации кровли.

## Вентканалы

Старое поле `vent_chimney_cladding_enabled` оставлено для legacy.

Production-режим:

```text
vent_chimney_cladding_calc_method = flat_roof_spec_volume
vent_chimney_cladding_enabled_calculated = flat_roof_enabled and vent_chimney_gas_block_spec_volume_m3 > 0
```

`vent_chimney_gas_block_spec_volume_m3` является проектным параметром из спецификации вентканалов.

## Найденная проблема: `floor_2` — усечённый сценарий, не годится для полноценного 2-го этажа (2026-07-13)

Найдено при разборе реального проекта ЮСВ для отчёта Елене (`experiments/full_estimate_review_pipeline/reports/report_for_elena_usv_pdf_discrepancies.md`) и в последующем обсуждении с пользователем и Еленой в этом чате.

### Контекст находки

В КР2 ЮСВ на стр. 3 сказано «Этажность — 1 этаж», а на стр. 15 есть отдельная,
самостоятельная таблица «Спецификация несущих стен 2-го этажа» с реальными
объёмами газобетона (13,44 м³) и арматуры (152 м/п). Изначально это выглядело как
противоречие в проекте. Разбор показал, что противоречия в самом проекте нет:
ЮСВ — дом в 1 этаж, но с **вторым светом** (двусветным пространством, по
предположению пользователя — над кухней-гостиной; это предположение не
подтверждено чертежами марки КР, там помещения не подписываются — нужны
чертежи марки АР для точного подтверждения). Поле `floor_2_masonry_volume_m3` в
калькуляторе исторически и есть переименованное `second_light_masonry_volume_m3`
(см. основной текст этого файла выше, раздел «Что было») — механика для «2-го
этажа» и для «второго света» в коде одна и та же.

Дальнейшая проверка (по прямому запросу пользователя, «иди разбирайся, это
важно») вскрыла две отдельные, реальные и на данный момент неисправленные
проблемы.

### Проблема А: `floors_count` вычисляется парсером из текста «Этажность», а не выбирается человеком

В `experiments/full_estimate_review_pipeline/sections/load_bearing_walls_lintels/section_contract.yaml`
поле `floors_count` имеет `source_class: AUTO_PROJECT` и `parser_mapping.aliases_ru:
["количество этажей", "этажность", "2 этажа", "1 этаж"]`, а `review_behavior.status_if_missing:
"manual_required"` — то есть ручная проверка требуется только если значение
**не найдено**, а не всегда.

Проверено на реальном (тестовом) `extraction_output.json` для ЮСВ: парсер
уверенно (confidence 0.98) взял `floors_count = 1` прямо из текста «Этажность» на
стр. 3 КР2 и **не** проставил `needs_review`. Если бы этот путь (парсинг → лист 01
→ калькулятор) уже был подключён к продакшену, калькулятор тихо занулил бы весь
блок 2-го этажа/второго света — при том что правильное значение для ЮСВ уже
осознанно выбрано человеком как `floors_count = 2` (второй свет нужно посчитать).

Архитектурная «этажность» дома (сколько там жилых уровней по документам) и
`floors_count` калькулятора (сколько ярусов кладки нужно посчитать) — это два
разных понятия, которые в проекте ЮСВ расходятся (1 vs 2) по уважительной причине
(второй свет), и контракт сейчас ошибочно считает их одним и тем же полем.

**Предложенное решение (согласовано с пользователем, ещё не внесено в код):**
убрать у `floors_count` привязку к парсингу («aliases_ru», `source_class:
AUTO_PROJECT`) и сделать поле чисто ручным выбором на листе `00_Конструктор
сметы` — по аналогии с тем, как уже устроено включение разделов `floor_slab_1` /
`floor_slab_2` (два независимых, самостоятельных калькулятора, а не одно поле
«сколько этажей»).

### Проблема Б: даже при правильном `floors_count = 2`, блок `floor_2` физически не может посчитать полноценный 2-й этаж

Прочитан `experiments/load_bearing_walls_lintels_calculator/load_bearing_walls_lintels_calculator.py`
целиком (строки ~793–1090, функции `calculate_blocks` / `calculate_lines`).
Сравнение объёма детализации:

- **Основные (1-й этаж) стены** — около 19 строк сметы: леса/подмости,
  гидроизоляция под первый ряд блоков, кладка, газоблок **D400 и D500** (два
  разных материала), клей, пескобетон под первый ряд, резка U-блока под
  перемычку, штробление под арматуру Ø10, сама арматура кладки, доставка блоков,
  разгрузка манипулятором, кран — и отдельно весь блок перемычек (каркас
  арматуры, бетонирование, бетон, доставка бетона, ручной подъём бетона).
- **`floor_2` (production-режим, `upper_floor_calc_method = floor_2_spec_volume`)**
  — ровно 3 строки: `floor_2_masonry_work` (кладка), `floor_2_gas_block_d400_material`
  (**только D400**, варианта D500 для 2-го этажа в коде нет вообще), `floor_2_masonry_glue`
  (клей). Нет своей гидроизоляции под первый ряд, нет своего штробления/арматуры
  кладки, нет своих перемычек, нет отдельной строки доставки/крана (доставка
  блоков считается одной суммой сразу по всем блокам: 1 этаж + floor_2 + парапет +
  вентканалы — физически материал довезут, но отдельной строки в смете на это
  для 2-го этажа не будет).

Иными словами, `floor_2` в текущем виде — это осознанно маленький,
«довесочный» блок, спроектированный именно под масштаб ЮСВ-подобного второго
света (немного газоблока сверху, без окон/дверей, требующих перемычек). Для
проекта с **полноценным вторым этажом** этого недостаточно.

Прямая цитата Елены из этого чата (2026-07-13), в ответ на вопрос «а если два
этажа полноценных, что тогда»:

> «да раздел будет для каждого этажа, но они могут отличаться — например на 1м
> этаже могут быть бетонные перемычки а на 2м их может не быть и наоборот. но как
> правило такие дома редкие, в основном это полноценный 2й этаж»

Это прямо демонстрирует ещё один пробел: перемычки в калькуляторе (`lintel_total_length_m`,
`lintel_concrete_spec_volume_m3`, `lintel_rebar_items`) — это **одно** значение на
весь раздел, не разделённое по этажам. Если у 1-го этажа перемычки есть, а у
2-го — другие (или их нет), текущая схема физически не может это выразить: есть
только одна общая цифра на весь дом.

**Нужно (не сделано, требует расширения контракта и калькулятора, не просто
починки парсинга):** отдельный D500-объём для `floor_2`, отдельные перемычки по
этажам (или явное осознанное решение оставить перемычки общими, если по факту
для 2-этажных домов это приемлемо — нужно уточнять у Елены на реальном примере).

### Парапет — независим от `floors_count`, не «повторяется» вместе с 2-м этажом

Отдельно прояснён вопрос «для 2-го этажа просто повторить расчёт 1-го вместе с
парапетом?» — нет. В коде `parapet_enabled_calculated = flat_roof_enabled and
parapet_masonry_volume_m3 > 0`: парапет включается по факту **плоской кровли**,
независимо от количества этажей. Одноэтажный дом с плоской крышей — парапет
посчитается; двухэтажный дом со скатной крышей — парапета не будет. Это два
независимых переключателя, их нельзя путать или считать, что один «включает»
другой.

### Дальнейшие шаги

Проверить то же самое на проекте ТРЦ, где, по словам пользователя, этажей
действительно два полноценных (не второй свет) и уже есть готовая смета для
сверки — см. предстоящий разбор в
`experiments/full_estimate_review_pipeline/reports/` (отчёт по ТРЦ, аналогичный
отчёту по ЮСВ). Ожидается, что на ТРЦ пробел из «Проблемы Б» проявится
конкретными несовпадающими цифрами (например, D500-кладка 2-го этажа или
перемычки 2-го этажа, которые сейчас некуда положить), а не только
теоретически.

## Перемычки: раскладка по этажам + монолитные перемычки (2026-07-15)

Пользователь прислала реальную смету ТРЦ (серую часть себестоимости, раздел
«Внешние и внутренние несущие стены, перемычки над проёмами») — это подтвердило
пробел из «Проблемы Б» именно по перемычкам конкретными цифрами, не только
теоретически, как и ожидалось выше. У 2-го этажа в реальной смете оказался
**полноценный, зеркальный 1-му этажу блок перемычек**: своя длина U-блока
(20,5 м.п., 35 шт резки), свой бетон, своя арматура — включая диаметр Ø16,
которого нет на 1-м этаже.

Заодно в смете нашлась **третья категория, которой не было вообще нигде** —
монолитные перемычки (заливаются на месте, в отличие от сборных U-блочных):
своё бетонирование, опалубка (фанера + доска), утепление торца (Пеноплэкс
Основа + клей-пена). У ЮСВ монолитных перемычек нет — на чертеже КР2 стр.16
прямо написано «Ж/б перемычки в U-блоках», то есть все перемычки ЮСВ одного
типа. Именно поэтому этот пробел не был виден раньше.

Уточнено у Елены (2026-07-15):
- монолитные и U-блочные перемычки могут сочетаться как угодно — только
  монолит, только U-блок, оба вместе — независимо, на любом этаже;
- монолитные перемычки есть минимум в 50% проектов — не редкий случай;
- U-блочные перемычки не требуют опалубки; монолитные требуют только
  материал (фанера + пиломатериал), **отдельной строки работы на устройство
  опалубки в себестоимости нет**;
- монолитные перемычки утепляются всегда — утепление не отдельное условие, а
  часть того же самого блока, что и монолитный бетон.

**Сделано** (`load_bearing_walls_lintels_calculator.py`,
`sections/load_bearing_walls_lintels/section_contract.yaml`, парсер, каталоги):

- Существующие поля `lintel_total_length_m`/`lintel_concrete_spec_volume_m3`
  (де-факто всегда представляли 1-й этаж) сделаны **опциональными** — раньше
  были `required: true`, калькулятор падал без них. Теперь перемычек может не
  быть вовсе, на любом этаже, ни U-блочных, ни монолитных — по прямому
  требованию пользователя: «перемычки могут быть или нет, поэтому ни в один
  этаж этот блок не зашивается жёстко».
- Добавлены свои поля для 2-го этажа (`floor_2_lintel_ublock_total_length_m`,
  `floor_2_lintel_concrete_spec_volume_m3`), зеркальные 1-му этажу.
- Добавлен целиком новый блок монолитных перемычек — 5 новых
  скалярных полей на этаж (объём бетона, длина утепления, фанера,
  пиломатериал, объём ЭППС) × 2 этажа.
- Все новые блоки (U-блок 2-го этажа, монолит 1-го этажа, монолит 2-го этажа)
  — независимо гейтированы: строка появляется только если значение > 0, иначе
  просто отсутствует в смете, ровно как уже было устроено для parapet/floor_2
  masonry/vent_chimney.
- Закупка бетона (материал) объединяет U-блок + монолит на каждом этаже в одну
  строку (одна машина бетона привозит и то, и другое), а вот строки работы
  («Бетонирование перемычек в U-блоке» и «Бетонирование монолитных перемычек»)
  остаются раздельными по методу — так же, как в реальной смете ТРЦ.
- Максимум одновременных строк сметы вырос с 30 до 48 (посчитано эмпирически
  прогоном калькулятора со всеми опциональными блоками включёнными
  одновременно, не выведено вручную).
- Обратная совместимость: коды строк 1-го этажа не менялись, старые ЮСВ-кейсы
  (0 расхождений, 16/16 живых кейсов + 2 корректных негативных) не затронуты —
  для ЮСВ монолитных перемычек и перемычек 2-го этажа просто нет, эти новые
  блоки не формируются.

**Не сделано, всё ещё открытая часть «Проблемы Б»:** кладка несущих стен 2-го
этажа (не перемычки) — `floor_2_masonry_volume_m3` по-прежнему даёт только
D400-материал, без D500, без своего штробления/арматуры кладки, без своей
отсечной гидроизоляции. Сегодняшняя работа закрыла именно перемычки; кладка
стен 2-го этажа ждёт отдельного захода.

Новые тест-кейсы: `test_lintel_floor_split_ublock_and_monolithic` (оба этажа,
оба типа перемычек, числа основаны на реальной смете ТРЦ) и
`test_lintel_no_lintels_at_all` (полное отсутствие перемычек — раньше упало бы
на валидации, теперь корректно даёт пустой блок).
