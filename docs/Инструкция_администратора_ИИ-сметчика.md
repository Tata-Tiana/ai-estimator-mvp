# Инструкция администратора ИИ-сметчика

Дата: 29.09.2026.

## 1. Что реально работает на сервере

На момент последней проверки 29.09.2026 подтверждено:

1. `calc.service` запущен и имеет статус `active`.
2. Сервис включён в автозапуск: `enabled`.
3. Процесс работает от пользователя `calc` в отдельном `.venv`.
4. При аварии systemd повторит запуск через 10 секунд.
5. Telegram API доступен с сервера через HTTP-прокси; проверка `getMe`
   вернула `ok=true`.
6. Google OAuth, Google Drive и Google Sheets работают под пользователем
   `calc`.
7. Сервер читает все 120 рабочих строк прайса.
8. Семь калькуляторов прошли серверный smoke-test.
9. Итоговый Excel собран с 2631 формулой и печатной областью `A:I`.
10. Тестовое создание папки job на Google Drive под пользователем `calc`
    прошло успешно.
11. Локальный Telegram-poller на Mac остановлен; production-бот не
    конфликтует со вторым poller.
12. Повторная попытка перевести `calc` на SOCKS5 откачена: одиночный `getMe`
    прошёл, но постоянный polling получил `Malformed reply`. Текущая рабочая
    production-схема — HTTP-прокси.
13. Telegram-код после этого переведён на `python-telegram-bot 22.7` и штатный
    `HTTPXRequest`, как у действующих ботов. Новый код запущен через HTTP:
    `Application started`, `NRestarts=0`.
14. SOCKS URL и версии библиотек совпадают, но отдельный PTB `getMe` для `calc`
    получает `Malformed reply` на SOCKS-аутентификации. На endpoint уже работают
    три соединения, включая отдельный `/root/photobot/bot.py` из `cron.service`
    (PID 578). Не останавливать его без решения директора.
15. Повторный ручной SOCKS5 handshake установил TCP-соединение, но endpoint не
    ответил на greeting `05 01 02`; через 10 секунд наступил timeout. Проверка
    credentials и соединение с Telegram при этом ещё не начинались. Тот же endpoint
    как HTTP proxy работает. Вопрос передан поставщику на проверку серверных логов.
16. Поставщик подтвердил: endpoint и доступ верны, но его SOCKS5 не работает с
    Telegram, если исходный сервер находится в РФ. Порт `63475` не закрыт — TCP
    connect с сервера проходит. По GeoIP/ASN сервер относится к РФ, поэтому для
    `calc` оставлен рабочий HTTP proxy. Не переводить `calc` на SOCKS5 без нового
    endpoint или изменения сетевого размещения.
17. При последующей проверке endpoint перестал принимать и новые HTTP-соединения:
    timeout воспроизводится на Telegram, Google и `example.com`, а также с Mac.
    Три старых SOCKS-соединения остаются `ESTAB`, но нового соединения `calc` нет.
    До ответа поставщика считать `calc.service=active` только состоянием процесса,
    а не подтверждением доступности Telegram.
18. Перезапуск прокси через панель поставщика не помог: повторные SOCKS5- и HTTP-
    проверки с сервера и SOCKS5-проверка с Mac снова завершились timeout.
19. Mac во время контрольной проверки выходил через VPN с IP в Эстонии. SOCKS5
    timeout воспроизвёлся и с зарубежного IP, поэтому ограничение только для РФ
    не объясняет отказ новых соединений; требуется диагностика endpoint поставщиком.
20. На скриншоте успешной проверки поддержки использован порт `64357`, тогда как
    пользователю выдан и ранее подтверждён порт `63475`. С выданными credentials
    порт `64357` не выполняет CONNECT: curl 97 / SOCKS reply code 2. Не менять
    production-порт до подтверждения поддержки, что тестировалась та же учётная
    запись и какой из двух портов относится к ней.

Это подтверждает работоспособность инфраструктуры и сборки. На момент
последней проверки на production ещё не был пройден целиком реальный
пользовательский сценарий: Telegram → первый JSON → исправленный JSON →
Google Sheet → `/build` → получение Excel в Telegram. Поэтому формулировка
«всё полностью проверено пользователем» пока будет неверной.

## 2. Быстрая проверка сервиса

Первая проверка без перезапуска:

```bash
systemctl is-active calc
systemctl is-enabled calc
systemctl show calc -p ActiveState -p SubState -p NRestarts -p MainPID
journalctl -u calc -n 100 --no-pager
```

Ожидаемый результат:

- `active`;
- `enabled`;
- `ActiveState=active`;
- `SubState=running`;
- нет цикла постоянных перезапусков;
- в журнале есть `Bot started. Polling...` и `Telegram proxy enabled.`.

Живой просмотр системного журнала:

```bash
journalctl -u calc -f
```

Нельзя запускать `telegram_bot.py` вручную параллельно с `calc.service`: два
poller с одним Telegram-токеном начнут конфликтовать. Перезагрузка самого
сервера, изменение firewall, SSH и установка системных пакетов без
согласования запрещены.

## 3. Какие логи есть

Логирование есть, но оно состоит из нескольких независимых слоёв.

### 3.1. Системный журнал systemd

Хранит запуски и остановки процесса, traceback, общие `stdout` и `stderr`:

```bash
journalctl -u calc -n 200 --no-pager
```

Это первое место для проверки, если бот не отвечает вообще или сервис
падает сразу после запуска.

### 3.2. Структурированные события бота

Путь:

```text
/home/calc/ai-estimator-mvp/experiments/earthworks_review_to_calculator/
  data/telegram_logs/events/YYYY-MM-DD.jsonl
```

Здесь записываются тип события, время, `chat_id`, `job_id`, уровень
`INFO`/`WARNING`/`ERROR` и безопасное краткое сообщение. Для нового JSON-процесса
значимы, например:

- `extraction_json_invalid`;
- `extraction_json_wrong_shape`;
- `extraction_json_processed`;
- `notes_report_failed`;
- `populate_workbook_failed`;
- `publish_sheet_exception`;
- `publish_sheet_result`;
- `build_download_sheet`;
- `build_failed`;
- `build_completed`;
- `recreate_started`, `recreate_failed`, `recreate_completed`.

Перед записью события проходят санитизацию: бот пытается удалить из строк
Telegram-токен, API-ключи, Bearer-токены, private key и пароль прокси.

### 3.3. Логи внутренних команд

Путь:

```text
/home/calc/ai-estimator-mvp/experiments/earthworks_review_to_calculator/
  data/telegram_logs/<chat_id>/<timestamp>_<operation>.json
```

Каждый файл хранит:

- код возврата внутренней команды;
- `stdout`;
- `stderr`;
- имя операции;
- время запуска.

`stdout` и `stderr` обрезаются до 10 000 символов. Этот слой нужен для разбора
ошибок калькуляторов, Google API и сборки Excel. В отличие от events, записи
внутренних команд сейчас не проходят через тот же фильтр секретов. В коде
не печатаются реквизиты прокси, но единый фильтр для этого типа логов
ещё нужно добавить.

### 3.4. Файлы состояния

Это не журналы, а рабочая память бота:

```text
data/telegram_extraction_sessions/<chat_id>.json
data/telegram_user_jobs/<chat_id>.json
data/telegram_sessions/<chat_id>.json
backups/telegram_sessions/
data/admin_exports/
```

- `telegram_extraction_sessions` — текущий JSON-job и двухчасовое окно для
  исправленного JSON;
- `telegram_user_jobs` — реестр job, ссылок на Google Sheet и Google Drive;
- `telegram_sessions` — старые PDF-сессии;
- `backups/telegram_sessions` — архивы старых PDF-сессий;
- `admin_exports` — Excel-выгрузки диагностики.

Сами файлы job и итоговые Excel лежат в:

```text
/home/calc/ai-estimator-mvp/experiments/chat_extraction_poc/outputs/<job_id>/
```

### 3.5. Что было в логах на момент последней проверки

На 29.09.2026 был один дневной events-файл. В нём были только события
запуска бота и режима `ALLOW_ALL_USERS=true`. Подробных command-logs,
extraction-sessions, реестров пользовательских job, архивов sessions и
admin-exports не было.

Это не ошибка записи логов. Это означает, что после деплоя ещё не было
полноценной пользовательской JSON-операции, которая должна была создать эти
файлы. После первого полного теста этот снимок нужно обновить.

## 4. Административные команды Telegram

Команды этого раздела выполняются только для `chat_id`, внесённых в
`TELEGRAM_ADMIN_CHAT_IDS`. Обычные команды сейчас открыты всем, так как
`ALLOW_ALL_USERS=true`.

### 4.1. Команды, полезные для нового JSON-процесса

| Команда | Что делает | Статус |
|---|---|---|
| `/admin_help` | Показывает список админских команд | Работает |
| `/admin_status` | Показывает uptime, commit, диск, события и режим доступа | Частично: счётчик sessions относится к legacy PDF |
| `/logs [1-50]` | Показывает последние структурированные события | Работает |
| `/tail_errors [1-30]` | Показывает последние `WARNING` и `ERROR` | Работает |
| `/export_logs today` | Отправляет Excel-диагностику за сегодня | Работает |
| `/export_logs yesterday` | Отправляет выгрузку за вчера | Работает |
| `/export_logs 7d` | Отправляет выгрузку за 7 дней | Работает |
| `/export_logs all` | Выгружает всю доступную диагностику | Работает, events ограничены 10 000 строками |
| `/recreate <job_id>` | Пересобирает Google Sheet из последнего JSON | Работает для JSON-job; также доступно автору job |
| `/build <job_id>` | Скачивает Google Sheet и собирает итоговый Excel | Работает для JSON-job; админ имеет доступ ко всем job |

Команда `/start` сама по себе не пишет отдельное событие в JSONL.
Если бот ответил на `/start`, это само по себе подтверждает входящую связь и
ответ Telegram, даже если `/logs` не показал событие `start`.

### 4.2. Команды с ограниченной полезностью

| Команда | Ограничение |
|---|---|
| `/sessions` | Собирает сводку из legacy PDF-sessions, их архивов и events. Текущий JSON-job из `telegram_extraction_sessions` полноценно не показывает. |
| `/sessions <chat_id>` | Подробная карточка старой PDF-session; не является надёжной карточкой нового JSON-job. |
| `/job_status <job_id>` | Вызывает старый Stage 1 status-script. Для нового JSON-job его ответ нельзя считать полным статусом. |

### 4.3. Legacy PDF-команды

Эти команды остались от старой схемы прямой загрузки PDF. Они не управляют
основным production-процессом JSON:

- `/active_sessions`;
- `/reset_session <chat_id>`;
- `/recover_sessions`;
- `/done`;
- `/cancel`;
- `/rerun <job_id>`;
- `/confirm_rerun <job_id>`.

Их не нужно использовать для починки JSON-job. `/reset_session` и
`/recover_sessions` работают только с `telegram_sessions`, а не с
`telegram_extraction_sessions`.

## 5. Как проверить весь production-маршрут

Проверку нужно проводить в таком порядке:

1. Отправить боту `/start` и убедиться, что пришла инструкция.
2. Отправить `/admin_status` и убедиться, что админский доступ работает.
3. Отправить `/logs 30` и увидеть `admin_command_started` и
   `admin_command_completed`.
4. Отправить контрольный первый extraction JSON.
5. Получить от бота отчёт замечаний и записать `job_id`.
6. Проверить, что на сервере создалась папка `outputs/<job_id>/`.
7. Отправить исправленный JSON в тот же Telegram-чат в течение двух часов.
8. Проверить создание папки `<ПРОЕКТ> — <ДД.ММ.ГГГГ>` и Google-таблицы внутри.
9. Открыть Google-таблицу, внести одно контрольное изменение и сохранить его.
10. Отправить `/build <job_id>`.
11. Получить итоговый `.xlsx` в Telegram.
12. Проверить, что контрольное изменение из Google Sheet попало в Excel.
13. Открыть Excel, проверить формулы, левую и правую части, серую зону и печатную область.
14. Отправить `/tail_errors 30` и затем `/export_logs today`.

Только после этого чек-листа production-маршрут можно считать проверенным целиком.

## 6. Что делать при ошибке

### Бот вообще не отвечает

1. Проверить `systemctl is-active calc`.
2. Просмотреть `journalctl -u calc -n 200 --no-pager`.
3. Проверить, нет ли ошибки proxy, timeout, `409 Conflict` или traceback.
4. При `409 Conflict` найти и остановить второй poller; не запускать третий.
5. Не перезагружать весь сервер без согласования.

### JSON не принимается

1. Проверить `/logs 30` и `/tail_errors 30`.
2. Проверить, что файл является валидным JSON.
3. Проверить корневое поле `sections`.
4. Проверить путь `outputs/<job_id>/` и текущую extraction-session.

### Google Sheet не создалась

1. Проверить `/tail_errors 30`.
2. Проверить свежесть Google OAuth token.
3. Проверить доступ к корневой папке Drive.
4. После устранения причины запустить `/recreate <job_id>`.

### `/build` завершился ошибкой

1. Прочитать единый список проблем, который вернул бот.
2. Проверить `/tail_errors 30`.
3. Просмотреть файлы `build_all_sections` и `build_export_estimate` в папке
   `data/telegram_logs/<chat_id>/`.
4. Исправить данные в Google Sheet.
5. Повторить `/build <job_id>`.

## 8. Важные правила безопасности

1. Не писать в чаты, отчёты, git и скриншоты Telegram-токен, пароль прокси,
   OAuth client secret и Google refresh token.
2. Секреты хранятся только в `/home/calc/.config/ai-estimator/` с правами
   `600`.
3. Не включать в архив деплоя `.env`, OAuth-файлы, логи, job и файлы
   пользователей.
4. Не менять `/root/Snab_Bot`, `/root/photobot`, `snab_bot` и `photo_bot`.
5. Не ставить Python-зависимости глобально.
6. Не запускать `apt`, не менять firewall и SSH без предварительного согласования.
7. Не перезагружать сервер самостоятельно.
